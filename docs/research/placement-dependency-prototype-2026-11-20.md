# 배치 의존성 조건 그래프 초안

작성일: 2026-11-20 KST. 기준 main: `fb795810535e6b85dcb201c0f5c5ea8d6a3fad8d`.

## 목적과 구현 범위

미노의 구체적 배치 사이에서 도달성에 영향을 주지 않는 조건을 증명하고,
동일한 조건을 만족하는 다른 보드에서 기존 판정을 재사용한다. 같은 종류의
미노, 다른 공급 경로, 다른 삭제 행 프레임을 임의로 합치지 않는 것이 전제다.

이 초안은 Rust `clearra-core-executor`의 `wasm_cpu` 경로에 연결했다.
일반 빌드에서는 제외되며, `local-search-ab` feature로 빌드한 호스트 실행에서
`CLEARRA_PLACEMENT_DEPENDENCY=1`로 활성화할 수 있다. 테스트는 환경 변수 대신
스레드별 scoped mode를 사용한다. 테스트의 worker 1은 A/B 격리를 위한 fixture
설정이며 제품의 worker 선택 정책 변경이 아니다.

기존 `reachability_local_relation.rs`의 검사 셀 추출기를 재사용한다. 새로
추가한 부분은 canonical placement와의 연결, ILC 조건 공유, 삭제 행 조건의
특수화, 보드와 무관한 목표 배치 영향 범위, 기존 역방향 탐색에서 얻은 조건을
저장하고 사용하는 경로다. 새 global pruning 권한이나 공급 순서 축약은 없다.

## 타일링 전에 만드는 정보

`placement_conditions.rs`는 GeometryCatalog가 완성된 직후, 후보 타일링을
열거하기 전에 다음 정보를 만든다.

| 정보 | 의미 |
| --- | --- |
| Canonical row ID | 종류와 원래 좌표계의 셀 집합으로 구별하는 구체적 배치 |
| Exact ILC domain | 각 삭제 행 집합 D에서 가능한 realization이 하나 이상 존재하는지 |
| Shared domain ID | 완전히 같은 허용 D 비트셋의 공유 ID |
| Cell incidence | 원래 셀을 차지하는 canonical placement ID 목록 |

높이 1–6, Board64 범위에서 최대 64개의 D를 직접 표현한다. 서로 다른
realization의 가능성은 OR로 유지한다. 공유하는 것은 같은 조건식이며,
배치 노드나 realization 목록 자체를 합치지 않는다. 조건 캐시는 기존
instantiations를 읽어 만들어지며, 컴파일 도중 자신을 다시 참조하지 않는다.

삭제된 행에 걸친 이미 실행된 미노의 잔여 셀도 의존성에 포함한다. 앞으로
실행할 수 없는 배치라는 이유로 이미 존재하는 잔여 셀의 영향을 지우지 않는다.
지원하지 않는 입력, 용량 초과, 검증 실패는 기존 계산으로 돌아간다.

## 타일링 선택 이후의 줄 삭제 조건

선택 여부 X와 실행 여부 E를 분리한다. 이 초안에서는 선택된 canonical ID
목록을 고정한 뒤, 각 원래 행의 contributor 집합으로 E에 대한 조건을 만든다.

원래 행 r을 채우는 contributor 집합이 P(r)라면, 초기 셀을 상수로 처리한
완전한 행에 대해서만 다음 조건을 사용한다.

```text
Clear(r, E) = 모든 p ∈ P(r)가 실행되었음
D(E) = Clear(r, E)를 만족하는 원래 행 r의 비트 집합
```

같은 contributor ID 집합을 가진 행들은 하나의 AND 조건과 복수 행 마스크로
표현한다. 같은 종류의 서로 다른 배치는 서로 다른 ID로 남는다. 여러 행이
동시에 지워지는 경우에도 원래 행 ID를 원자적으로 반환한다. 일부만 채워지는
목표 행은 삭제 조건이 되지 않는다.

현재 BuildUp의 `expected_deleted_rows`에 이 계산을 연결했다. APDP의 부분
선택 X에 대한 전파, 선택/되돌리기 때의 dirty 목록 갱신, watcher 카운터를
이용한 실행 E의 증분 갱신은 아직 연결하지 않았다. 따라서 전체 조건 그래프를
타일링 전에 완성했다는 구현은 아니다.

## 킥 영향 범위의 증명

최대 킥 이동 거리만으로 독립을 판정하지 않는다. 중간 이동 경로, 착지 지지,
spawn/sky 진입, 먼저 검사하는 킥 후보의 실패 조건도 결과를 바꿀 수 있다.

`reachability_independence.rs`의 정적 분석은 실제 forward template에서 모든
가능한 이동·킥 간선을 만든 뒤 목표 배치의 선행 상태 폐쇄를 계산한다. 여기에
선행 상태에서 검사하는 모든 킥 후보를 포함한다. 목표에 도달하지 않는 앞쪽
킥 후보도 뒤쪽 후보의 선택을 바꿀 수 있으므로 생략하지 않는다.

정적 마스크 M에 대해 같은 규칙과 목표 배치를 사용하는 보드 A, B가

```text
(A XOR B) AND M == 0
```

을 만족하면 해당 목표 배치의 가능 여부가 같다. 교집합이 있다는 사실은
의존성이 있다는 증명이 아니라 판정을 재사용할 수 없다는 뜻이다.

상향 킥과 긴 이동 경로 때문에 정적 마스크가 보드 전체가 될 수 있다.
그 경우 안전하지만 쓸모없는 조건이므로 더 작은 조건부 증명이 필요하다.
정적 계산기는 보드를 받지 않는다. 실행 경로에서는 이미 전체 탐색이 필요한
경우에 목표별로 지연 생성하며, 모든 후보에 대해 선계산하지 않는다.

## 탐색 결과를 관측해 만드는 조건

실행 순서는 기존 hard-drop 검사, 기존 exact-board cache, 조건 재사용,
기존 primitive 탐색, primitive 결과 관측 순이다. 증명 캐시 miss만으로
추가 BFS를 시작하지 않는다.

| 증명 종류 | 생성 자료 | 재사용 가능한 결과 |
| --- | --- | --- |
| 정적 선행 상태 범위 | 보드와 무관한 이동·킥 template | 목표 pose 하나의 Boolean |
| 역방향 탐색 조건 | 실제 처리한 reverse queue prefix와 검사 조건 | 목표 pose 하나의 Boolean |
| 전체 전방 탐색 조건 | 실제 sky seed와 완전히 닫힌 도달 상태 집합 | 전체 grounded-lock 집합 |

역방향 탐색 조건은 target의 충돌·착지 검사, 처리한 상태의 역방향 이동 후보,
역방향 회전 source와 앞선 킥 후보를 포함한다. 성공 조기 종료의 조건을 다른
배치나 전체 lock family의 부정 결과로 확대하지 않는다. 실패한 역방향 탐색도
폐쇄된 탐색의 해당 목표 결과만 저장한다.

전체 전방 탐색 조건은 도달한 집합에서 나가는 모든 결정과 seed의 점유 검사를
포함한다. 다른 보드가 이 셀들에서 같으면 같은 집합에 진입하고 같은 간선이
선택되며 같은 grounding 결과를 얻으므로 전체 lock 집합이 같다.

각 조건을 cell incidence로 canonical placement 목록에 연결한다. 현재
재사용 비교는 occupancy bit mask로 수행하고, 영향 placement ID 목록을 함께
보관한다. 이 목록을 사용하는 dirty propagation은 다음 단계다.

## 잘못된 prune을 막는 경계

- Catalog owner는 Arc allocation의 동일성을 Weak로 고정하고, 부착 시 종류·
  원래 셀·차원·초기 보드·required cells 전체를 확인한다. 이전 catalog의
  벡터 저장소를 캐시 때문에 계속 보유하지 않으며 Weak의 고정 비용도 계산한다.
- Kick profile이 바뀌면 기존 조건을 버린다.
- 삭제된 원래 행 집합 D가 같아야 재사용한다. D가 바뀌어도 물리 보드가 같다는
  이유로 조건을 적용하지 않는다.
- 목표 하나의 증명과 전체 lock family의 증명은 타입 내 scope로 구별한다.
- 최대 128개 relation, 2,048개 정적 목표 마스크, 128K개 influence ID를 유지한다.
  용량 한계는 exact fallback을 사용하며 결과를 false로 바꾸지 않는다.
- 영향 범위 바깥의 미노라도 줄 삭제를 일으킬 수 있다. 그 경우 frame이 바뀌므로
  기존 증명의 적용 대상에서 벗어난다.
- 결과는 기존 도달성 Boolean 질의를 대체한다. 같은 종류의 공급 분기,
  CountAll multiplicity, 확률의 분모, scoring/replay 증거를 축약하지 않는다.

## 측정에서 확인한 설계 수정

처음에는 조건 cache miss마다 전체 도달성 탐색을 수행했다. 4개 미노 표준
7가방 fixture에서 조건 재사용 138회, 서로 다른 보드 재사용 8회가 발생했으나,
전체 방문 상태는 기존 1,724개에서 27,512개로 늘었다. 재사용 횟수만으로는
이득을 판단할 수 없었다.

이에 기존의 짧은 역방향 탐색 결과를 관측하는 방식으로 변경했다. 전체 전방
탐색은 기존 cache 정책이 필요로 할 때에만 실행한다. 방문 상태 감소는 실행
시간 단축과 별개이며, metadata
컴파일·조건 추출·조건 검색·추가 메모리 비용까지 포함한 성능 검증이 필요하다.

## 검증 결과

Rust 1.98.1, Linux 호스트의 debug test 빌드에서 비교했다. 다음 수치는 작은
정확성 fixture의 결과이며 대표 workload 벤치마크가 아니다.

### 4개 미노 / 표준 7가방

입력은 높이 4, 초기 보드 `0xfc3f_0fc3_f0`, 사용 미노 4개, hold off,
CountAll, worker 1이다. 동일 환경에서 기존 모드와 실험 모드를 실행했다.

| 항목 | 기존 | 최종 초안 |
| --- | ---: | ---: |
| 정규화된 해 | 135 | 135 |
| Build variant count | 2,060 | 2,060 |
| 성공 공급 패턴 | 173 / 840 | 173 / 840 |
| Coverage probability | 0.20595238095238097 | 0.20595238095238097 |
| Total reachability states | 1,724 | 1,693 |
| Peak reachability states | 170 | 170 |

방문 상태는 31개, 약 1.8% 감소했다. 기존 cache를 통과한 조건 조회 218회 중
재사용 9회, 그중 서로 다른 보드 사이의 재사용은 4회였다. 기존 reverse
탐색 결과에서 조건을 209회 만들었고 추가 full BFS는 없었다. 이 fixture에서
whole-family 조건이나 정적 조건은 생성되지 않았으며, 관측형 target 조건만
활용했다. 209는 생성 관측 횟수이고 동시에 209개를 보관했다는 뜻이 아니다.

타일링 전 canonical placement 218개에 필요한 exact ILC domain은 15개였다.
나머지 203개 배치는 동일한 domain 저장소를 공유한다. 타일링 후보별 행 조건
특수화는 456회, 생성된 contributor 조건은 합계 1,744개, 그중 복수 원래 행을
묶는 그룹은 80개였다. 이 값들은 메모리 압축 가능성과 조건 반복을 보여 주며
그 자체가 실행 시간 개선 배수는 아니다.

### 반복 미노, 공급 경로, 줄 삭제

| Fixture | 보존한 결과 |
| --- | --- |
| 빈 10×2 / IIOOO / CountUnique | 정규화 해 4개, coverage 1/1 |
| 같은 입력 / CountAll | 정규화 해 4개, build variants 6,144 |
| current I, hold off | 정규화 해 1개, build variants 2 |
| current I와 held I | 정규화 해 1개, build variants 4; 다른 supply action의 배수 보존 |
| II / `0xfc3f0` | 정규화 해 1개, build variants 4; replay 두 단계가 각각 한 줄 삭제 |
| scored I | 정규화 해 1개, build variants 2; 실제 scoring batch와 replay 일치 |

단순 fixture들은 hard-drop에서 해결되어 새 도달성 조건 조회가 0회다.
이 경우에도 ILC domain과 행 조건의 연결은 실행된다. 전체 placement identity,
coverage bitset, 해별 coverage와 probability, replay, scoring batch,
completeness/truncation과 패턴 가중치를 기존 결과와 비교한다.

### 독립성·경계 검증

- 새 테스트 33개와 기존 도달성 회귀 테스트 29개가 통과했다.
- 기존 외부 생성 pack이 필요한 테스트 2개는 원래의 ignored 상태다.
- SRS90, SRS+, SRS-X, Jstris180, NoKick의 5개 profile을 사용했다.
- 전체 lock family 조건의 영향 범위 바깥에서 한 셀을 바꾼 보드 479개를 독립
  BFS와 비교했다. 35개 profile/piece 조합 중 27개가 실제 바깥 셀을 가졌다.
  나머지 8개는 전체 보드 마스크여서 재사용 실험의 성공 사례로 세지 않았다.
- 역방향 target 조건은 영향 범위 바깥 셀 변화에 대해 1,142회 독립 oracle과
  비교했다. 각 profile에서 실제 성공과 exhaustive negative 사례를 요구했다.
- O shelf fixture는 5개 source family로 2,400개 질의를 재사용했고, 1,200개는
  보드가 달랐다. 이것은 제어된 증명 실험이며 일반 PC의 성능 수치가 아니다.
- J를 추가하면 T의 SRS+ 킥이 가능해지는 반례, 앞선 킥이 선행 폐쇄 바깥에
  있는 반례, 원래 행 frame 변경, owner/profile 변경, 캐시 포화, stale scratch,
  불완전 negative, 다른 목표 pose로의 오용, obsolete owner 수명을 검사했다.

```sh
cargo test --locked -p clearra-core-executor --lib placement_conditions:: -- --nocapture
cargo test --locked -p clearra-core-executor --lib backend::wasm_cpu::reachability:: -- --nocapture
cargo test --locked -p clearra-core-executor --lib placement_dependency_integration_tests -- --nocapture
cargo fmt -p clearra-core-executor -- --check
cargo check --locked -p clearra-core-executor --target wasm32-unknown-unknown
cargo check --locked -p clearra-core-executor --features local-search-ab --target wasm32-unknown-unknown
cargo clippy --locked -p clearra-core-executor --lib --features local-search-ab,parallel
```

기본 및 실험 feature의 wasm32 컴파일, format 검사를 수행했다. 브라우저에서
WASM을 실행한 검증은 아니다. Clippy 일반 실행은 완료했으며 기존
`search_prune_policy.rs`의 precedence/needless_return 경고 10개가 남아 있다.
`-D warnings`를 추가한 엄격한 Clippy gate는 이 기존 경고 때문에 통과하지
못한다. 기본 lib test 빌드의 기존 parallel 관련 dead-code 경고 3개도 남아 있다.

## 엄격한 Boolean 대체 실험: 원래 행별 pose 관계

`symbolic_prefix_orders.rs`는 구체 Board64 PC 타일링 하나에서 최대 10개
배치의 Boolean 순서를 계산한다. 일반 BuildUp 우회율을 재는 기존 혼합
실험과 달리 미지원·취소·관계 예산 초과·좌표 불일치를 별도 실패로 남긴다.
기존 BuildUp으로 돌아가지 않으며, 어떤 실패도 해법 없음이 아니다.
제품 경로에는 연결하지 않는다.

- 실행한 구체 배치 집합을 `E`, 원래 행 `r`의 배치 기여자를 `C_r`로
  두면 `D(E) = {r : C_r ⊆ E}`가 이미 삭제된 행이다. 정규화된
  초기 필드와 정확히 분할된 타일링에서 아직 놓지 않은 `q`의 ILC
  realization이 동일한 투영 셀을 차지하면, 잠금 직후 새롭게 사라지는
  행은 정확히 `D(E ∪ {q}) − D(E)`다. 배치별 물리 행 삭제
  탐색 없이도 이 관계가 유지된다.
- 삭제 행을 contributor들의 논리곱으로 비트셋에서 원자적으로 분할하고,
  각 프레임에서 원래 셀 소유자의 실행 비트만 물리 좌표로 옮긴다.
  prefix마다 물리 보드를 복원할 필요가 없다. 착지 지지와 수직 통로도
  같은 점유 비트로 계산하며, 하드드롭으로 해결된 lane은 pose 검색에
  넣지 않는다.
- 미해결 도달성에는 forward 기준군과 목표별 reverse 후보가 있다.
  reverse는 같은 구체 배치의 유효 ILC pose들에서만 시작하고 실제
  spawn seed를 찾은 lane을 즉시 완결한다. 역방향 회전은 출발 칸이
  비어 있고 **모든 앞 킥이 막혀 있을 때**만 통과한다. 다른 회전은
  같은 구체 배치 안에서만 합치며, 같은 미노 종류의 다른 배치에는
  성공을 공유하지 않는다. 큐 고갈 전의 미확정 상태, 취소, 관계 한도,
  다른 프레임이나 잘못된 pose는 음성 결과가 아니다.
- `A_q`를 `q`가 가능한 원래 prefix의 비트셋이라 하면, 비트의 인덱스는
  배치 집합의 정수 표현이다. 미실행 `q`를 추가하면 인덱스가 정확히
  `2^q` 증가한다. 따라서 `(L >> (2^q)) & A_q`와
  `(R & A_q) << (2^q)`의 합집합으로 각각 완성에서 역방향,
  초기에서 순방향을 계산한다. 상위 배치 비트(6~9)는 64비트 블록 사이를
  이동하며 블록 안의 lane은 바뀌지 않는다. 둘 다 만족하는 prefix만
  역순으로 interning한다. 같은 종류라도 서로 다른 배치를 먼저 합치지 않는다.

비용은 표현된 prefix와 블록 수, 행 조건 분할, 셀 소유 비트,
frame/kind 또는 배치별 relation 수, 정적 검사,
관계를 만든 셀·pose·lane·이동·ordered kick 처리량, 순서 합성 word 연산,
suffix 상태와 전이, 단일 pose 관계의 논리 메모리를 나누어 센다.
이 실험은 배치 순열을 따라가는 물리 검증이나 prefix별 물리 보드
투영을 호출하지 않지만, 여전히 최대 `2^n − 1`개의 prefix를
비트셋으로 표현한다. 관계 생성은 블록·프레임·미해결 배치에 비례해
늘 수 있다. 자세 bitmap 한 번의 처리도 모든 lane과 동일한 CPU 비용이 아니다.
따라서 일반 경로의 pose 방문 수와 새 경로의 worklist pop 수 중
하나만 비교해 순절감이나 RSS 개선을 판정하지 않는다.

검증 상태: Windows 정책 오류 4551 이후 사용자가 허용한 Ubuntu의
유한 감독 빌드에서 실제 Rust 차등을 수행했다. 다섯 킥 프로필과
7개 미노의 물리 oracle, 반복 미노와 동시/연속 행 삭제, 장애물 때문에
후순위 킥이 열리는 경우, 취소와 범위 밖 상태를 비교했다. 4L 공동
줄 삭제의 원본 큐 2,520개와 빈 홀드의 840개 큐에서 기존 공급 및
해법별 커버리지와 일치했다(홀드 fixture의 해당 해법은 성공 80개,
홀드가 필요한 성공 64개). 수용 경계는 완전한 단일 파티션의
명시 1워커, compact CPU Boolean/coverage로 좁혀져 있고 증거 유형을
충족하지 않으면 별도 경로를 조용히 교체하지 않는다.

공동 줄 삭제 fixture에서 동일한 셀 점유 계산을 전방/역방향에
사용했다. 비교 값은 CPU 시간이나 RSS가 아닌 실제 내부 처리량이다.

| 진단 항목 | 전방 (같은 kind의 전체 lock) | 역방향 (해당 배치의 목표 lock) |
| --- | ---: | ---: |
| 자세×lane 처리 | 3,826 | 150 |
| 작업 큐 pop | 965 | 59 |
| 계산한 pose 점유 domain | 1,800 | 296 |
| 이동 조건 항 | 2,671 | 159 |
| ordered-kick 조건 항 | 2,145 | 633 |

이 fixture의 기존 BuildUp은 그래프 노드 20개와 스칼라 자세 164개를
기록했다. 엄격 실험은 기존 그래프·스칼라 탐색을 호출하지 않았지만,
새 관계 및 언어 비용을 별도 기록하므로 전체 속도 개선을 뜻하지 않는다.

10배치 경계는 빈 4L Jstris 180, P7P4, enabled-empty hold의 독립적으로
구성한 canonical 타일링 **하나**로 검사했다. Geometry 열거 없이 그
타일링을 공통 검증기에 공급했고, 기존 경로와 엄격 경로의 원본 큐
4,233,600개 중 성공한 **113,216개 전체 비트셋**과 확률이 일치했다.
엄격 경로는 16개 단어에 1,023개 실행 전 상태를 표현했고,
기존 BuildUp 그래프와 스칼라 도달성 카운터는 모두 0이었다.
다만 별도 비용에서는 기존이 그래프 344노드·스칼라 자세 5,218개,
엄격 경로가 배치별 자세 관계 154개·자세×lane 34,135개·순서 언어
245개 상태를 처리했다. 적용 도메인과 정확성 증거는 넓어졌지만 이
입력의 병목은 해결되지 않았다.

같은 소스 스냅샷(감독 게스트 트리
`cc7fbe1adf09d6c1e7ff7708915486ddc43cc891`)에서 집중 테스트 26개
(중복 실행 한 건 제외)와 기능 플래그 없는 Core `cargo check`가
통과했다. 이는 Windows나 배포 WASM 실실행 검증이 아니다.

### 완성 가능한 전이의 상한을 이용한 관계 생성 제한

동일한 원래 행 프레임에서 ILC 형상과 착지 필요조건을 만족하는 전이는
먼저 **가능한 전이의 상한**에 넣는다. 하드드롭 통로가 막혔다는 것은
이동이나 킥으로도 불가능하다는 뜻이 아니므로 미확정으로 남긴다.
모든 실제 완성 경로가 이 상한에 포함되므로, 시작에서 도달 가능하고
완성까지 갈 수도 있는 상한 간선만 검증해도 완성 언어는 보존된다.
남은 미확정 간선은 기존의 정확한 ordered-kick 관계로 확인한다.
상한 때문에 제외된 개별 전이는 물리 불가능 판정이 아니며,
상한 모드는 별개의 단일 전이 조회에 답하지 않는다.

같은 10배치 Jstris P7P4 타일링에서 전체 113,216개 성공 큐 비트셋과
확률, 최종 언어 상태 245개·전이 778개가 일치했다. 세 arm 모두
기존 BuildUp과 스칼라 도달성을 호출하지 않았다.

| 진단 항목 | 상한 없음 | 상한 적용 | 상한 + 동종 질의 묶음 |
| --- | ---: | ---: | ---: |
| 물리 확인 대상으로 간 미확정 간선 | 2,360 | 496 | 496 |
| 자세×상태 처리 | 34,135 | 5,461 | 5,279 |
| 역방향 관계 호출 | 154 | 117 | 23 |
| 자세 큐 pop | 6,730 | 2,143 | 881 |
| ordered-kick 조건 항 | 60,791 | 23,529 | 8,867 |
| 셀 점유 plane 항 | 1,126 | 2,100 | 1,764 |

상한 합성은 2,604번의 word 전이 연산을 추가했고, 미확정 간선이 남은
39개 (블록, 삭제 행 프레임) 쌍의 점유를 다시 만들었다. 묶음은 동일한
삭제 행·프로필·구체 목표 배치에서만 여러 블록에 흩어진 lane을
최대 64개씩 재배치한다. 승인 비트는 원래 블록에 정확히 펼치며,
같은 타일링에서도 다른 배치나 프레임과 관계를 공유하지 않는다.
프레임 투영은 이 입력에서 39회에서 5회로 줄었고, 묶음 경로는
최대 8 KiB의 프레임별 블록 소속 마스크와 비트 좌표 변환을 추가했다.
이 값은 전체 소유량이나 피크 RSS가 아니다.

감독 Ubuntu 트리 `acfbe465e5235dfdafe9d4126e9527b4e77a22fd`에서
이 표와 집중 테스트 17개를 확인했다. 기존 경로의 스칼라 자세
5,218개와 새 5,279개는 단위가 달라 직접적인 성능 판정이 아니다.
같은 프로세스의 정확성 테스트를 시간 ABBA 표본으로 사용하지 않는다.

다음 채택 조건은 같은 실제 입력의 엄격 대체 경로에서 후보 누락·무음
fallback이 없고, 관계 생성까지 포함한 움직임 및 배치 순서 검사 비용이
기존보다 실제로 작다는 것이다. 다음은 홀드/줄 삭제/후순위 킥 성격이
다른 타일링을 사전 고정한 세트에서 원본 ordinal 집합과 비용 분포를
비교하고, 이후 계획의 전체 P7P4 family 및 ABBA+BAAB로 넘어가는 것이다.
전체 P7P4 identity family, 24L,
CountAll, 스핀, 점수, 리플레이는 이 실험의 입증 범위가 아니다.
공급의 union memo 및 실제 피크 메모리 최적화는 검증 경로를 대체하고
새 소유권을 다시 계측한 뒤 판단한다.

### 기존 CTK3 입력의 P7 전체 정확성 검사

`ctk3_w0kCQBjwwAMPPAD37g`는 `0x3c0f03c0f`이고, 이전 패리티
probe의 `0x3c0f03c0`나 좌우 반전 필드가 아니다. 네 원래 행이 모두
초기 셀을 가지므로 정확한 4L PC에서는 그 네 행이 모두 지워져야
한다. 이는 물리 pose를 원래 삭제 행을 삽입해 되돌린 독립 타일링
열거의 범위 근거다.

원본 7개 미노의 모든 순열 5,040개를 사용한다. 완성에는 6개 미노가
필요하고, CountUnique exact cover를 부분 공급/홀드 선택과 따로
검사한다. 사전선정한 identity는 전달하지 않는다. 일반 경로와 엄격
경로가 각각 Geometry 후보 전체를 받아 완주했는지 확인하고, 순서가
있는 전체 identity/비트셋 행을 대조한다.

| 킥 프로필 / 홀드 | 해법 수 | 커버하는 원본 큐 | (해법, 큐) 전체 쌍 |
| --- | ---: | ---: | ---: |
| Jstris 180 / 빈 홀드 | 246 | 5,040 / 5,040 | 78,792 |
| SRS / 빈 홀드 | 245 | 5,040 / 5,040 | 78,664 |
| SRS+ / 빈 홀드 | 246 | 5,040 / 5,040 | 79,288 |
| SRS-X / 빈 홀드 | 289 | 5,040 / 5,040 | 102,408 |

각 arm의 Geometry 후보 2,260개 모두 엄격 검증에 진입·완료했고,
기존 BuildUp 그래프와 스칼라 도달성 방문 수는 0이었다. 효과상 1명이
되더라도 자동/2워커를 요청했거나 부분 파티션인 입력은 엄격 검증
권위로 받아들이지 않는다. 일반 경로와 사전입력 경로의 공통 입구에
이를 적용했다.

독립 오라클에도 표의 여섯 조건을 모두 실행했다. 제품 Geometry의
산출물을 받아 검증하는 방식이 아니다. 표준 미노의 물리 자세를
원래 행으로 올리는 별도 구현에서 skeleton 400개를 만들고, 첫 빈
셀을 덮는 방식으로 138,464개 열거 노드와 2,260개 exact cover를
완주했다. 각각은 제품의 BuildOrderGraph나 symbolic relation을
호출하지 않고 스칼라 ordered-kick 도달성·물리 행 삭제·독립 홀드
상태 전이로 평가했다. 다섯 규칙과 두 홀드 설정의 해당 여섯 조건
모두 기존·엄격 경로 각각의 해법 집합, 해법별 원본 5,040비트,
큐 합집합과 일치했다.

엄격 경로의 `CoverageSummary`는 표시용 해법별 확률 행을 생성하지
않는다. 원본의 동일 가중치와 정확한 비트셋으로 각 확률의 분자·분모를
확인했고, 실제 보고 값은 별도 일반 `Summary` 실행에서 같은 분수와
대조했다. 숫자 보고용 출력의 부재를 계산 실패나 엄격 경로의 산출물로
세지 않는다.

최종 Ubuntu 감독 트리 `61612f2a2af40b39b2c60d964c9a621a20551c75`에서
독립 전수 대조, 전체 P7 차등, 범위 거부, 이전 P7P4 단일 identity 회귀
네 테스트를 모두 통과했다. 이는 해당 CTK3 입력에 대한 정확성 증거이며
다른 초기 필드, 전체 P7P4 family, 병렬 실험, ABI/공개 제품 배포 검증이나
시간·메모리 채택 기준을 닫지 않는다.

### P7의 마지막 홀드 해제와 원래 행 순서

동일 독립 오라클에 서로 다른 두 초기 필드를 추가했다. 마지막 원본
미노까지 소진하는 경우에는 다음 가방의 미배치 미노를 홀드 교환에만
쓴다. 오라클도 **원본 7개를 다 읽었고 남은 배치가 하나뿐일 때**만
알려진 홀드 미노의 마지막 배치를 허용한다. 보이지 않는 미노를
직접 놓거나 원본 큐 수를 늘리지 않는다. 별도 공급 예제에서는 같은
7개 드로우로 빈 홀드의 순서 64개와 홀드 비활성의 순서 1개를 확인했다.

7배치 필드의 처음 세 원래 행에는 초기 셀이 있다. 네 번째로 지워질
행은 바로 위의 원래 행 3이다. 그 행을 건너뛰면 영구적으로 비어
있는 틈이 생겨 연결된 미노가 틈 위에 처음 접지할 수 없다.
5배치 필드는 네 원래 행에 모두 초기 셀이 있어 네 행을 지워야 한다.
따라서 이 두 필드에도 4행 독립 열거를 사용할 수 있다.

| 초기 필드 / 규칙 / 홀드 | 배치 | 독립 기하 후보 | 해법 | 원본 큐 합집합 |
| --- | ---: | ---: | ---: | ---: |
| `0x3c0f03c0` / SRS+ / 없음 | 7 | 288 | 21 | 1,403 / 5,040 |
| `0x3c0f03c0` / SRS+ / 빈 홀드 | 7 | 288 | 21 | 5,016 / 5,040 |
| `0x90747d83e5` / SRS / 빈 홀드 | 5 | 3 | 3 | 956 / 5,040 |

독립 오라클·기존 검증기·엄격 검증기가 해법별 원본 비트셋까지
일치했다. 7배치에서는 성공한 순서의 첫 삭제가 네 원래 행 각각에서
가능했고, 비대칭 5배치에서는 첫 삭제의 원래 행 비트셋이
`0100`, `0110`, `1100`으로 달랐다. 단일·동시 줄 삭제를 모두
포함한다. 일반 출력의 해법별 확률 보고도 원본 비트셋 분자와 맞췄다.
엄격 경로는 해당 Geometry 후보를 전부 인증했고 기존 BuildUp이나
스칼라 도달성 호출은 없었다.

Ubuntu 감독 트리 `acc6d3989ccd28e46795fa265b6b4a783d3529ad`에서
두 새 필드의 독립 대조와 기존 6배치 CTK의 6조건 회귀를 모두 통과했다.
검증 범위를 다른 필드·공급 경계로 확장한 결과이며, 전체 P7P4나
시간·메모리의 채택 근거로 사용하지 않는다.

### 실제 네이티브 워커와 리플레이 없는 원본 큐 스트림

네이티브 `local-search-ab`와 `parallel`을 모두 켠 실험 전용 빌드에서,
하나의 요청 토큰을 워커 풀과 호출 스레드에 동일하게 전달한다.
각 스레드는 자신의 후보 검증만 엄격 모드로 수행하고 정확한 결과를
한 번 보고한다. 모든 후보의 시도·완료·검증 수가 일치하고 실제 후보를
받은 워커가 두 개 이상이 아니면 봉인하지 못한다. 오류·취소·직렬
전환은 기존 실행으로 조용히 대체되지 않는다. 실험이 끝나면 워커의
모드가 복원된다. P7P4에서 32비트를 넘을 수 있는 누적 계수는
`u64`로 넓혔다.

6배치 CTK의 SRS+ P7에서 실제 2워커로 후보 2,260개가 모두 검사됐다.
해법 246개의 원본 5,040비트와 큐 합집합은 기준군·엄격 경로·
워커를 재사용한 다음 기준군에서 일치했다. 검사 요청에 명시적
자원 상한을 주어 제품의 직렬 전환 조건을 일부러 만들었을 때에는
엄격 경로가 성공하지 않았다.

같은 입력을 명시적인 증거 수집기로도 비교했다. 실험 수집기가
설치된 `CoverageSummary`에만 canonical ID를 보존하고, 대표
리플레이와 해법별 결과 행을 만들지 않는다. 각 후보의 원본 큐는
살아 있는 워커의 증거를 통해 수집기로 넘긴다. 기준군과 엄격 경로
모두 이 방식으로 246개의 ID와 각각의 큐 비트를 정확히 전달했고,
엄격 경로의 기존 BuildUp/스칼라 검증 카운터는 0이었다. 수집기가
실패하면 엄격 영수증은 봉인되지 않는다. 기본 출력에는 이 변화가
없고, 기존 별도 권한/메모리 제한 경로를 새 캡처로 승격하지 않는다.

감독 Ubuntu 트리 `503e02996e28194fd6f099d4f451d41b146bed78`에서
요청 소유권·2워커/스트림·직렬 캡처·기존 캡처·P7 경계 회귀를
확인했다. 이 결과는 P7 증거 스트림의 실제 연결이지, 전체 빈 필드
P7P4의 압축 매핑·시간·피크나 대표 리플레이 동등성을 입증하지
않는다. 남은 작업은 같은 조건의 양 arm을 쓰는 별도 source-bound
매핑 전용 실행과 전체 해법 대조다.

### 엄격 병렬 경로 구조 정리와 전체 검증 계약

워커 풀 큐, 요청 토큰과 읽기 전용 입력을 한 소유자로 묶었다. 각
풀 작업은 소유권을 한 번만 확보하고, 작업 배열·포즈 큐는 워커
자신이 재사용한다. 포즈 상태는 질의 경계마다 초기화하되 저장 용량만
보존한다. 한 보드의 방문 기록이나 킥 결과를 다음 보드에 넘기지 않는다.

삭제된 원래 행 집합은 실행된 부분집합으로 결정된다. 따라서 살아
남은 lane으로 재분할한 결과는 최초 분할과 해당 lane의 교집합이다.
상한 검사에서 목록을 할당하지 않되 모든 ILC 실현의 실제 셀 집합은
계속 확인한다. 워드 간 전이는 실행하지 않은 상위 비트 하나를
추가하므로 워드 번호가 엄격히 증가한다. 뒤에서 앞으로 완성 가능성을,
앞에서 뒤로 도달 가능성을 계산하면 워드 간 간선은 방향당 한 번이면
충분하다. 워드 안에는 최대 여섯 비트의 간선만 남는다. 이 최적화는
상한을 물리 판정으로 승격하지 않으며, 살아남은 미결 간선은 같은
ordered-kick 검증을 거친다.

`strict-prefix` 정확성 비교는 같은 네이티브 release 바이너리에서
기존 BuildUp과 엄격 경로의 정렬된 해법 ID 및 원본 큐 ordinal 집합을
직접 비교한다. 짧은 SRS+ P7에는 해법 246개와 79,288개 해법–큐 쌍을,
Jstris 180 빈 4L P7P4에는 해법 456,459개와 전체 4,233,600개 원본 큐를
요구한다. 기준군과 후보군 모두 대표 리플레이를 만들지 않는다.
엄격 비교에서만 실행당 누적 spill 5 GiB와 최종 파일 3 GiB로
제한하고, WSL은 실제 VHD의 Windows 볼륨 여유도 확인한다. 파일
한도에 걸리면 정확성 실패나 완료 표본이 아닌 검증 미완료다.

전체 매핑 비교가 통과한 바이너리와 호스트에서만 파일 쓰기를 뺀
ABBA 네 표본을 직렬 실행한다. AB와 BA 순서가 이미 포함되므로
이 실험에서는 후속 BAAB를 실행하지 않는다. 이 비교는 기존 BuildUp 대비 개선된
엄격 경로의 효과를 보여 주며, 개별 구조 변경의 시간 효과나
브라우저·제품 기본 경로의 채택을 입증하지 않는다.

Ubuntu 8워커 네이티브 스냅샷
`086cd28616e49b928484b842a6c83f4d78b49ff3`의 짧은 P7 비교는
후보 2,260개, 해법 246개, 전체 5,040개 원본 큐, 해법–큐 79,288쌍을
직접 대조해 통과했다. 양쪽에서 8워커가 모두 실행했고 엄격 경로의
기존 BuildUp 노드·스칼라 포즈는 0이었다. 이 결과는 P7P4 판정이나
성능 채택과 별개다.

같은 바이너리의 P7P4 정확성 영수증
`strict-p7p4-v2-20261121-proof`는 `completed-exact-per-solution`이다.
Jstris 180 빈 4L에서 양쪽 후보 29,856,840개를 8워커로 검증했다.
정렬된 해법 456,459개의 원본 큐 집합과 정수 가중치가 모두 일치했다.
전체 큐가 4,233,600/4,233,600이고 해법–큐 쌍은 15,800,311,980개다.
후보는 기존 BuildUp 대신 역방향 관계 8,528,265개를 완결했고, 상한
그래프에서 끝까지 이어지지 않는 미결 간선 38,339,781,205개를
제외했다. 이 수는 독립 배치나 탐색 시간 절감 수치가 아니다.
비교기는 각 해법의 정확한 집합을 읽어 검증했으며 파일 해시 일치는
부가 증거다. 파일을 쓰는 캡처 시간과 peak RSS는 ABBA에 넣지 않는다.

이 소스의 ABBA 첫 네 실행만 비교하면 탐색 시간은 A 99.578·100.481초,
B 119.171·119.806초다. 중앙값 100.029초 대비 119.489초로 초기 B는
19.45% 느렸다. 이전 스케줄이 시작한 추가 BAAB는 중단했으며, 이미
끝난 첫 추가 표본도 집계에 넣지 않았다. 실제 사용 워커는 모두 8개다.

관리자 표본 peak RSS의 중앙값은 A 4,629,276,672 B, B 4,691,171,328 B
(+59.0 MiB), 최고 표본은 A 4,732,104,704 B, B 4,706,430,976 B였다.
워커 종료 시점의 논리 용량 추정에서 B의 도달성 저장공간 합계는
65 KiB지만 표준 가방의 워커별 저장공간은 3.292 GiB였다. 두 값은
서로 다른 생명주기의 논리 용량이며 실제 RSS에 더하지 않는다.

후속 단계 진단은 기존 BuildUp(A), 워드마다 상한을 만들던 이전
엄격 경로(B0), 원래 삭제 행 프레임마다 지원·직하강 차단 소유자만
준비하는 경로(B1)를 비교한다. 프레임의 점유 조건은 교차하는 배치
소유자의 비트 OR로 계산할 수 있다. 역방향 킥 검증과 원래 ordinal
결과는 그대로다. 이 진단은 측정된 워커 경과 시간의 표본 합계를
포함하므로, 별도 ABBA 시간이나 채택 증거로 사용하지 않는다.

네이티브 소스 `e0230be71d8ad0c9da2005e15a5a5294684e9d25`의

표에 나타난 개별 구간은 호출 스레드와 풀 워커의 표본 경과 시간의

### 남은 병목과 손실 없는 의존성 축소

위 진단에서 개선 B의 큰 항목은 상한 구성(152.6 표본초), 표준 백
공급과 큐 커버리지(149.9 표본초), 순서 언어(50.0 표본초), 역방향
도달성(46.1 표본초) 순이다. 순서 언어는 각 후보의 워커 안에서
역순으로 구성된다. 워커들에 합산된 50초는 50초짜리 전역 직렬
구간이 아니며, 합산 구간 자체에 다시 여러 스레드를 붙이기보다
그 구간이 만들거나 방문하는 상태 수를 줄여야 한다.

1. **상한 구성의 공유 단위를 카탈로그로 올린다.** 현재 한 후보의
   동일 삭제 행에서만 공유하는 투영, ILC 실현 유무·투영 일치 검사,
   지지 셀과 직하강 통로는 불변 카탈로그의
   `(row_id, 원래 삭제 행 마스크)`에 결박해 재사용할 수 있다.
   후보마다 달라지는 다른 배치 소유자와의 교차는 계속 계산한다.
   실현 없음과 투영 불일치는 다른 상태로 유지한다. 단순 캐시 hit가
   아니라 제거한 투영·실현 검사 수와 신규 공유 peak를 기록한다.
2. **순서 언어에서 같은 글자를 내는 선택을 집합으로 묶는다.** 현재
   bottom-up intern은 이미 같은 `(미노 종류, 자식 언어 ID)`를
   중복 제거한다. 더 강한 후보는 같은 종류 소모량 좌표에서 가능한
   구체 배치 부분집합을 frontier 비트마스크로 가지고, 다음 글자에
   대해 모든 허용 successor를 OR하는 것이다. P7P4의 빈 홀드
   fixture는 두 번 나오는 종류가 최대 네 개이므로 같은 소모량
   좌표의 가능한 배치 부분집합은
   `∏ C(종류별 전체 개수, 소모 개수) ≤ 16`이다. 좌표만 합치면
   계속 가능한 배치가 달라 해법을 잃거나 추가한다. 폭 16은 생성할
   frontier 수의 상한이 아니므로, 요청된 상태만 만들고 한도를
   넘으면 원래 언어로 되돌린다. 언어와 백 곱 단계의 합산 비용과
   실제 생성 frontier·OR 수를 함께 비교한다. 작은 비교 후보는
   실제로 남은 간선만 순회하는 방식과, 미노 배열·정확 간선 마스크
   전체가 동일할 때만 같은 워커/epoch에서 언어 루트를 재사용하는
   제한된 메모다. 해시나 노드 수만 같은 경우에는 재사용하지 않는다.
3. **증명된 경로들의 합집합에 덮이는 물리 검사를 먼저 생략한다.**
   같은 canonical 후보에서 증명된 간선만으로 이루어진 그래프를
   `H`, 참일 수도 있는 간선까지 포함한 상한을 `U`라고 둔다.
   미결 간선 `s --p--> t`에 대해 `t`에서의 상한 후속 언어가
   `s`의 이미 증명된 같은 종류 `p`의 다른 successor들의
   `H` 후속 언어 합집합에 포함되면, 그 미결 간선은 검사하지
   않아도 같은 종류 순서(따라서 같은 조건의 원래 큐 집합)를
   보존한다. 예를 들어 상한이 `{IJ, JI}`이고 검증된 두 경로가
   각각 `{IJ}`, `{JI}`를 제공하면 함께 덮을 수 있다. 미결 간선이
   서로를 근거로 없어지면 안 되며 증명 비용이 한도를 넘거나 하나라도
   덮지 못하면 원래 물리 검사를 수행한다. 먼저 정렬된 정규 자식
   간선의 구조적 포함처럼 빠른 충분조건만 시도한다. 반복 종류가
   있는 synthetic 입력에서 합집합 포함과 비포함을 검증하고,
   실제 P7P4에서 제거한 lane 외에 **완전히 피한 역방향 batch**를
   계측한다. 한 종류씩만 등장하는 P7 시험으로 이 최적화를 닫지 않는다.
4. **증명 결과의 중복 계산은 동일 질의만 공유한다.** 정확한 압축
   물리 필드, 스폰·경계와 ordered-kick을 고정한 템플릿, 목표 pose
   집합이 같은 경우에는 동일 Boolean 물리 결과를 원래 프레임·후보에
   각각 돌려줄 수 있다. 같은 그래프에서 작은 목표 집합의 검증된
   양성은 상위 집합에도, 큰 목표 집합의 완결된 음성은 하위
   집합에도 유효하다. 중단·한도 초과는 음성이
   아니다. 점유 비트의 단순 포함은 대체 근거가 아니다. 장애물이
   앞선 킥을 막으면 뒤 킥을 열 수 있다. 여러 목표가 실제로 같은
   보드에 모이는지 확인 전에는 전체 pose 폐포나 큰 공용 캐시를
   무조건 만들지 않는다.

위의 언어 대체와 생략은 동일 해법의 Boolean 및 원래 큐 증거에
한한다. 다른 canonical 해법의 큐 집합이 같거나 포함되어도 그 해법
ID를 버리지 않는다. CountAll, 리플레이, 점수, 스핀의 증거 수준은
이 등식으로 대체하지 않는다.

### 메모리: 7-bag 합집합만 독립 비교

`local-search-ab`의 `CLEARRA_STANDARD_BAG_UNION_MEMO=reference|compact`
를 추가했다. 미지정 시 기존 선택을 상속한다. 유니온의 완전한
64비트 키와 32비트 값을 유지하면서 슬롯의 payload padding만
16바이트에서 12바이트로 바꾼다. 공급 상태와 언어의 product memo
형식/레이아웃, 용량의 논리적 재활용 기준, 기본 동작은 고정한다.
기존 strict-prefix 정확성/성능 수집기와 기존 memo 비교의 상속
환경에서 이 새 축을 제거해 타 비교에 섞이지 않게 했다.

이전 1,879,048,192바이트 union payload와 같은 슬롯 수라면
448 MiB의 논리 payload가 줄지만, 이것은 RSS나 사용자 시간의 실측
이득은 아니다. 다음 독립 비교는 같은 binary, 공급 정책, 워커와
기존 product layout에서 union 저장 표현만 바꾼 뒤 정확한 원래
큐 집합, 슬롯 수, 재활용, sampled peak RSS, 경과 시간을 확인한다.
워커 또는 epoch가 다른 숫자형 결정 노드 ID를 같은 키로 사용하지
않는다. 구조적 후속은 같은 원본 큐 분기가 이미 전체 suffix를
수용했을 때만 나머지 홀드/같은 종류 분기를 생략하고, 얕은
합집합이 재귀 없이 정확히 계산된다면 실제 적중을 확인한 뒤
메모에 넣지 않는 것을 비교하는 것이다.

집중 Ubuntu 소스 트리 `a0b055d6cd2ef82deb42829e6a2988b5a147086a`의
Rust 검증은 저장 형식/재활용 회귀 4개, 유니온만 compact로 지정한
P7 독립 oracle 및 실제 2워커 P7 비교를 통과했다. oracle은 다섯
프로필의 원래 큐 집합을 해법별로 대조한다. 실험용 예제와 실험
기능을 끈 병렬 라이브러리는 각각 컴파일 확인했고, 관련 Node
테스트는 46개가 통과했다. 전체 P7P4 메모리/시간 실측은 아직 없다.

### P7P4 최적화 축의 독립 ABBA

빈 4L, Jstris 180, 표준 P7P4, 빈 홀드, `CountUnique`의 네이티브
8워커 strict-prefix의 변경별 진단에서는 앞 절의 프레임 소유자 기반
strict 경로를 A로 썼다. 당시에는 옵션별 효과만 보는 진단이었다.
이후 고정 회귀 기준선은 아래의 `strict-frame-owner-v1`으로 정했다. B는
카탈로그 가드 공유, 합집합 메모 압축, 완전히 수용된 큐 분기
생략, 순서 언어 frontier, 증명된 언어를 이용한 미결 의존성
생략 중 한 가지 옵션만 변경한다. 한 축마다 같은 바이너리로
`A → B → B → A`를 직렬 실행하고 BAAB는 추가하지 않는다.

실험 실행기는 실제 작업한 8워커와 완료 영수증, 후보
29,856,840개, 정렬된 해법 ID 456,459개와 전체 원래 큐
4,233,600개의 지문을 확인한다. 표본 peak RSS는 감독 프로세스
그룹의 관측값이며, 워커별 논리 용량의 합이나 커널 최고값이
아니다. 캡처·리플레이·구간 프로파일링은 배제한다. 따라서
해법 ID와 큐 합집합의 일치는 해법별 큐 매핑의 일치를 대신하지
않으며, 방문량 변화만으로 구간별 시간 차이를 확정하지 않는다.

| 단일 변경 | A₁ / B₁ / B₂ / A₂ (초) | 시간 중앙값 변화 | 표본 peak RSS 중앙값 변화 |
| --- | --- | ---: | ---: |
| 카탈로그 가드 공유 | 71.246 / 74.049 / 78.880 / 80.682 | +0.66% | +68.6 MiB |
| 합집합 메모 압축 | 79.971 / 79.560 / 78.267 / 91.699 | −8.06% | −490.9 MiB |
| 완전히 수용된 큐 분기 생략 | 79.850 / 89.438 / 85.349 / 76.072 | +12.10% | −55.5 MiB |
| 순서 언어 frontier | 76.098 / 77.618 / 85.006 / 82.403 | +2.60% | −70.7 MiB |
| 증명된 언어로 미결 의존성 대체 | 77.839 / 78.923 / 77.294 / 78.181 | +0.13% | +22.4 MiB |

카탈로그 가드는 B 표본마다 391,168바이트의 불변 테이블에서
990,708,432회 적중했으나 탐색 시간 개선으로 이어지지 않았다.
메모 압축은 동일한 슬롯 수에서 union payload를 1,792→1,344MiB로
줄였고, 실제 sampled peak도 AB·BA 양쪽에서 줄었다. 첫 시간 쌍은
0.41초 차이인 데 반해 A끼리는 11.73초 차이가 있어 8.06%를 확정
가속으로 해석하지 않는다. 큐 분기 생략은 이 입력에서 방문량을
일관되게 줄이지 못했다. Frontier는 두 적용군 모두 1,289,564번
성공했으며 큐 간선 검사 약 8.03억→6.43억, product 상태 약
1.56억→1.32억으로 줄였으나 두 쌍 모두 탐색은 느렸다. 집합 구성의
비용 절감은 방문량과 별도로 검증해야 한다.

같은 미노 후속 언어의 증명된 합집합으로 대체한 두 표본은 모두
미결 lane을 47,237개 줄였다(124,505,112→124,457,875). 첫 AB의
역방향 관계 계산은 8,528,265→8,515,721회로 0.15% 줄었다. 실제
중복 계산을 피했지만 시간이 두 쌍에서 일관되게 줄지는 않았다.
다른 미결 결과를 근거로 사용하거나, 다른 canonical 해법의
큐 집합을 합쳐 검사 범위를 억지로 넓히지 않는다.

다섯 ABBA의 20표본은 로컬 소스
`d93626859581eae24334c12fe220a6e5fe202d35`에서 실제 8워커로
완료됐다. 집계 지문은 전부 일치했다. 영수증은 관리된
`placement-graph-coverage/strict-next-*-20261121-optimization-abba/`에
축별로 저장했다. 이후 사용자가 **합집합 메모 압축만** 성능 채택으로
승인했다. 이 저장 표현의 시간 검증은 반복하지 않고, 정확성·지원 범위
검증은 새 바이너리에 별도로 결박한다.

기존 Rust BuildUp 대 strict+압축의 별도 ABBA는 사용자의 목표
일시중지 때 첫 실행을 종료했다. `strict-fixed-buildup-union-memo-20261121-optimization-abba/`
요약은 `incomplete`, 유효 표본 0개이며 임대는 해제되었다. 이 비교는
재개하지 않는다. B1의 71.122초는 압축을 켠 표본이 아니라 이전
`reference` 저장 형식의 단일 구간 진단이다. 이번 ABBA의 각 쌍은
압축군이 더 빨랐지만 서로 다른 실행의 시간만으로 자원 경합을
확정하지 않는다. 별도 성능 재실행 없이 압축을 채택했고, 아래
정확성 비교를 마친 뒤 **`strict-frame-owner-v1-compact`**를 고정했다.
기준 실행은
`CLEARRA_STANDARD_BAG_MEMO=reference`, `CLEARRA_STANDARD_BAG_PRODUCT_MEMO_LAYOUT=adaptive`,
`CLEARRA_STANDARD_BAG_UNION_MEMO=compact`를 명시한다. 기존 BuildUp은
검증용 독립 비교기이며 성능 기준군이 아니다. 과거 영수증을 재현할
때만 명시적 `strict-frame-owner-v1`로 `reference`를 선택한다.

또는 시간을 증명하지 않는다.
