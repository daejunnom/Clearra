# BuildUp 소형 도달성 자산의 검증 및 A/B 계획

> 작성일: 2026-09-22
> 상태: 실행할 검증의 계획이다. 신규 자산 생성, 솔버 구현, 제품 테스트, 성능 개선을 완료했다는 기록이 아니다.
> 기준 소스: `dbc2140213214f96f8c705a5237441dc008ca5c2`.
> 연결: [현재 기획](compact-board-conditioned-reachability-plan.md), [미해결 문제 대장](build-up-acceleration-issue-register.md).

## 1. 검증 목적

ILC/APDP의 도면·시간적 실현 의미를 보존하면서, 작은 보드 조건부 관계가
실제 BuildUp 연산을 줄이는지 확인한다. 생성 시간이 아니라 런타임 비용이 평가 대상이다.

채택에는 정확성, 소형 자산, 실제 성능의 세 증거가 모두 필요하다.
파일이 작아졌거나 초당 노드가 늘었다는 이유만으로 제품을 전환하지 않는다.
생성 시간이 오래 걸렸다는 이유로만 정확한 후보를 포기하지도 않는다.

## 2. 검증할 의미를 먼저 고정한다

다음 질의들은 서로 다른 계약이다.

| 질의 | 검증 범위 |
| --- | --- |
| 조건부 한 단계 전이 | 특정 source pose에서 이동/회전 요청의 실제 결과 |
| 국소 입출구 관계 | 지정 pose 영역과 의존 셀 아래 진입→출구/내부 lock |
| 전체 목표 lock 도달 | 실제 시작 pose 집합부터 목표까지의 경로 존재 |
| 전체 reachable-lock 집합 | 모든 가능한 목표 lock의 완전 집합 |
| 도면 BuildOrder | 해당 ILC 도면의 모든 합법 구축 순서 |
| 공급 커버리지 | BuildOrder와 공급·홀드 조건의 정확한 결합 |
| 스핀/finesse/CountAll | 요구된 실행 증거·비용·다중 경로 의미까지 포함 |

한 단계 표의 통과를 전체 도달성의 통과로, Boolean 도달성을 스핀/개수 검증으로
승격하지 않는다. 최종 API와 manifest에 실제로 지원하는 범위를 기록한다.

## 3. 독립 기준 계산

작은 유한 domain에서 단순한 기준 탐색기를 사용해 primitive 전이를 직접 실행한다.
새 lookup·압축 그래프·생성 결과를 기준 탐색기가 그대로 읽어 정답을 만드는 순환 검증은 금지한다.
공통 규칙 입력의 출처는 기록하되, 비교할 도달 알고리즘과 인덱스 디코더는 분리한다.

독립 비교의 단위는 미노 종류·source pose·입력 행동·보드 점유·경계·규칙이다.
킥 후보를 순서대로 실제 충돌 검사하여 처음 성공한 목적지를 구한다.
불가능한 source, 모든 후보 실패, 이동 실패의 의미도 기준 계약에 맞춘다.

국소 서명에 반영되지 않은 셀은:

- 해당 관계의 모든 primitive 판정에 영향을 주지 않는다는 근거가 있거나,
- 유한 검증 domain에서 가능한 외부 조건을 전수하여 등가성이 확인되어야 한다.

실제 dependency halo가 너무 커 전수가 불가능하면 범위를 줄이거나 기존 검색으로 처리한다.
임의의 몇 개 외부 보드를 검사한 결과만으로 보편적 negative 권한을 주지 않는다.
무작위/차등 검사는 추가 결함 탐지이며 전 범위 증명의 대체물이 아니다.

## 5. 기존 좌표 문제의 우선 회귀 검사

문제 대장 LB-001의 산식은 현재 소비자의 원래 행 재삽입과 생성기의 bottom-prefix
정규화를 같은 입력에서 비교한다. 두 키의 bit count가 같아도 서로 다름을 보여준다.
이 산식은 문서 작성 중 재계산했으며 결과는 다음과 같다.

```text
physical board = 0b11 << 20
deleted rows   = 1 << 2
consumer key   = 0x00fff00000
prefix key     = 0x00c00003ff
popcount       = 12 (둘 다)
```

이는 작은 산술 검사만 수행한 결과다. 실제 생성기나 제품 solver를 실행한 것은 아니다.
후속 회귀 검사는 실제 생성 fixture를 소비자에 연결하고 각 삭제 마스크에서
codec 왕복, membership, 전체 도면 및 coverage를 비교해야 한다.
수동으로 소비자 표현에 맞춘 목록만으로 통과시킨 테스트는 생성/소비 일치를 증명하지 못한다.

## 6. 자산과 네트워크 실패 검사

| 상황 | 기대 동작 |
| --- | --- |
| 블록 미다운로드/미생성 | Unknown, 기준 계산 또는 다른 작업 진행 |
| 완전 domain 안의 검증된 부재 | 그 domain의 의미에 한해서 부정 근거 |
| 손상·잘린 파일·잘못된 offset/ID | 자산 거절, 결과를 불가능으로 바꾸지 않음 |
| 선언 해제 크기 초과·참조 순환/범위 밖 | 로드 중단 및 기준 경로 |
| profile/shape/frame/seed 의미 불일치 | 해당 기록 미사용 |
| CDN의 manifest/payload 세대 불일치 | 세대 혼합 차단 |
| 캐시 용량 초과/eviction | miss로 전환, 탐색 상태 보존 |
| worker가 읽는 동안 자산 교체 | 세대 고정·수명 보존 |
| HTTP 실패/redirect/부분 응답 기대와 불일치 | 실제 바이트·응답 범위 검증 후 처리 |
| 사용자가 다운로드를 거부 | 기존 정확 계산 계속 가능 |

Range/CORS/공유 메모리가 현재 서비스 경로에서 작동한다고 미리 가정하지 않는다.
실제 host 환경에서 필요한 경우에만 검증한다. hot loop의 전이마다 HTTP 요청하지 않는다.

무결성 실패가 prune 이후 발견되면 해당 작업을 재실행하거나 결과를 무효화해야 한다.
단순히 이후부터 fallback하는 것으로 이전에 잃은 상태가 복구되지는 않는다.

## 7. 크기 예산: 숫자는 아직 미확정

사용자의 거절 조건은 명확하다. 기존 약 600MB TB와 같은 부담이나 GB급 전량 자산을
반복하지 않는다. 그러나 새 허용 상한의 정확한 숫자는 아직 합의되지 않았다.
따라서 아래 값을 측정·제안·승인하기 전에는 제품 자산으로 승격하지 않는다.

| 예산/측정 | 기록 내용 |
| --- | --- |
| 전체 배포량 | 모든 profile pack의 합, 공통 사전의 중복 포함 여부 |
| 선택 pack | 압축 bytes와 디코딩 bytes |
| 콜드 요청 | 총 수신 bytes, 요청 수, 첫 사용 가능 시점 |
| 단일 검색 누적 | 필요한 블록을 끝까지 사용한 총량 |
| 세션 누적 | 여러 입력/프로필을 반복한 실제 총 수신량 |
| persistent cache | 디스크 cache 상한과 eviction 후 재다운로드 |
| resident/peak | 사전, 인덱스, 압축/해제 버퍼의 동시 보유 |
| worker별 복제 | 1·2·11 worker에서 실제 공유/복제 bytes |

작은 파일 개수나 압축률만 보고하지 않는다.
표가 전체 보드나 도면 목록에 비례해 계속 커지면 조건부 관계라는 이름이어도 재설계 대상이다.
예산 초과를 온라인 PC4 TB에 자동 위임하여 숨기는 것은 이번 소형 가속의 성공이 아니다.

## 8. 성능 A/B

### 8.1. 비교군

| 군 | 내용 | 분리하려는 효과 |
| --- | --- | --- |
| A | 동일 바이너리의 기존 ILC/APDP/BuildUp | 기준 |
| B | 같은 평탄/compact 표현의 CPU 참조, 자산 가속 없음 | 자료구조 개선 효과 |
| C | 보드 조건부 primitive 전이 기록 | 조건 추출/조회가 짧은 기존 루프를 이기는지 |
| D | 제한된 국소 입출구 macro 관계 | 반복 reachability 상태 확장을 생략하는지 |
| E | 효과가 있는 C/D + bounded cache/delta | 결합 비용과 재사용 효과 |

기존 legal-board 필터는 LB-001~004의 계약을 먼저 확인한 뒤 별도 대조군으로 사용할 수 있다.
불완전하거나 좌표가 다른 필터의 높은 prune율을 가속 근거로 사용하지 않는다.

primitive 조회만 느리다고 모든 macro 후보를 실패로 취급하지 않으며,
macro 처리율만 높다고 전체 BuildUp이 빨라졌다고 판단하지 않는다.

### 8.2. 실행 조건

- 동일 입력·규칙·미노/홀드·출력 모드·완료 종점을 고정한다.
- 같은 WASM의 옵션 전환을 우선하고, 바이너리가 다르면 hash와 차이를 명시한다.
- 콜드 다운로드와 웜 실행을 분리한다. 사전 생성은 런타임에서 제외하고 별도 기록만 한다.
- 1·2·11 worker를 각각 측정하며 worker 수 × 벽시계 시간으로 실제 CPU 작업량을 단정하지 않는다.
- 큰 패턴, 짧은 고정 큐, 비어 있지 않은 필드, 4L/6L, 중간 행 삭제,
  Build 목표를 포함한다. 고정 큐의 회귀를 큰 패턴의 평균으로 가리지 않는다.
- 완료 표본은 중앙값과 범위, 반복 수를 기록한다. timeout은 censored이고 정답 실패/UNSAT가 아니다.
- profiling on 측정과 실제 사용자 지연 측정을 분리한다.

### 8.3. 측정 항목

`CandidateProjection`, `BuildOrderReachability`, 구축 언어 정규화,
`CoverageLanguageProduct`, 재생/출력 및 전체 완료를 분리한다.
이 중 실제 계측이 없는 항목을 이미 존재하는 카운터라고 주장하지 않는다.

추가로 다음을 기록한다.

- 하드드롭/기존 캐시 hit, 새 관계 hit/unknown/fallback 및 질의 범위.
- 실제로 생략한 도달성 검색·pose 방문·전이 검사 수.
- 조건 추출, key 작성, 조회, macro 합성, 결과 복원 비용.
- 그래프 노드/간선 생성 및 정렬·중복 제거 비용.
- 자료 크기, 로드/검증/디코딩 시간, 메모리 peak, worker 복제량.
- 원본 도면 ID와 큐 coverage의 완전성, 출력 모드별 evidence 보존.

### 8.4. 손익과 채택

```text
순절감 = 실제 생략한 BuildUp 연산 시간
       - 조건 추출/조회/macro 합성/복원 시간
       - 사용자 실행에 들어간 다운로드/검증/디코딩 시간
```

웜 순절감과 콜드 사용자 시간을 함께 본다.
배포 전 생성 비용을 이 식에 넣지 않지만, 전송·메모리 비용을 숨기지도 않는다.
현재의 26.512초 저장 행렬 최소화, 별도 GUI canonical 시간, Qnia의 다른 경로 시간을
서로 나누어 이 가속기의 성능으로 보고하지 않는다.

## 9. 종료 기준

**정확성 Go:** 지원한다고 선언한 각 domain과 출력 모드에서 전이/도달성/도면/coverage가
독립 기준과 일치하고, 미지원·미적재·손상 상태의 부정 오판정이 없다.

**크기 Go:** 합의한 모든 크기 예산을 만족한다. 특히 누적 다운로드와 worker 복제를 포함한다.

**성능 Go:** 지원 대상 입력군에서 동일 조건 BuildUp 또는 제품 전체의 재현 가능한 이득이 있다.
회귀 입력의 범위와 가속 비활성 선택을 명시한다.

세 조건 전에는 실험 전용이며, 문서 작성·blob 업로드·정적 검사만으로 구현 완료나
릴리즈 게이트 통과 상태를 변경하지 않는다.

## 10. 작성 시 실제 수행 범위

- 고정 GitHub 소스와 기존 legal-board 문서를 재확인했다.
- LB-001의 두 좌표 변환 산식을 작은 독립 계산으로 재검산했다.
- 이 문서의 테스트 목록과 신규 가속기 A/B는 실행하지 않았다.
- source, WASM, PC4 TB, release workflow는 이 문서 변경의 대상이 아니다.
