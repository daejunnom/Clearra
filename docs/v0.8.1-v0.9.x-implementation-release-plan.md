# Clearra v0.8.1 Hotfix 및 v0.9.0·v0.9.x PC4 Online Tablebase 구현·배포 계획

## 1. 문서 목적과 권위

이 문서는 이미 배포된 v0.8.0 이후의 활성 계획을 한곳에 복원한다. 범위는
v0.8.1 알고리즘·제품 안정화, v0.9.0 PC4 Online Tablebase, 후속 데이터
generation을 수용하는 v0.9.x, 그리고 v1.0.0 승격 조건이다.

`docs/v0.8.0-v0.9.0-implementation-release-plan.md`와
`docs/v0.8.0-remaining-work-plan.md`는 당시 판단과 배포 이력을 보존하는 역사
문서다. 이 문서는 그 파일을 수정하거나 과거의 미완료 판정을 현재의 완료 증거로
재사용하지 않는다. 충돌 시 다음 순서로 현재 상태를 판정한다.

1. 최종 사용자 결정과 이 문서의 제품 계약
2. 현재 Git-tracked 소스와 테스트
3. 최종 exact source SHA에 결박된 CI·artifact·배포 증거
4. 과거 계획 및 연구 기록

계획에 적힌 타입명과 파일명은 책임 경계를 설명하는 기준이다. 구현 중 이름을
바꿀 수는 있지만, Core 권위와 adapter 책임을 합치거나 비활성 기능을 우회해
공개하는 변경은 별도 설계 승인을 받아야 한다.

### 1.1 현재 기준선

현재 기준선에는 다음 기반이 존재한다.

- PC Geometry는 `clearra-core-executor`의 inverse lock-clear(ILC) catalog,
  Geometry domain, APDP, component/projection 및 parallel search 경로를 사용한다.
- 최소 해법과 score-minimals의 typed product/result 경로가
  `clearra-app`에 있고 CLI, GUI host, Web, Discord가 이를 소비한다.
- 현재 `--tablebase`는
  `apps/clearra-web/static/tablebase/pc4-compact-exact-v12.bin`,
  `pc4_tablebase.rs`, `tablebase_runtime.rs`에 연결된 정적
  `CLR4TB12` 베타 자산이다.
- 현재 APDP나 v2 minimum 코드가 존재한다는 사실은 v0.8.1의 새 수학 필터,
  성능 목표 또는 전체 surface parity가 완료됐다는 뜻이 아니다.
- 현재 정적 베타가 존재한다는 사실은 muse918의 온라인 graph를 읽거나 전체
  PC 해법을 제공한다는 뜻이 아니다.

각 단계는 구현 후 새 증거로 다시 닫는다. 과거 benchmark, 한 번의 GUI 성공,
synthetic fixture 또는 특정 규칙의 성공을 다른 입력·규칙·surface의 권위로
확대하지 않는다.

### 1.2 릴리스 순서와 병렬 개발

개발은 다음 두 축을 독립 worktree/branch에서 병렬 진행할 수 있다.

- v0.8.1: 기존 exact solver의 수학 필터, minimum, parallelism, 제품 parity
- v0.9.0: feature-off PC4 graph reader, Range machine, manifest와 materializer

production mutation은 반드시 순차적이다.

1. v0.8.1 exact SHA를 acceptance하고 CLI·GUI·Discord에 배포한다.
2. 관찰 기간 동안 P0/P1 회귀가 없음을 확인한다.
3. v0.9.0 branch를 accepted v0.8.1 위로 재기준화하고 전체 gate를 다시 실행한다.
4. upstream 자격 조건이 모두 충족된 경우에만 v0.9.0 온라인 TB를 활성화한다.
5. 이후 호환 데이터 generation은 v0.9.x로 갱신한다.
6. 장기 안정성 조건이 충족되면 v1.0.0으로 승격한다.

서로 다른 branch의 소스 전체를 병합하지 않는다. 소유 모듈별 작은 커밋을 만들고,
공통 파일 충돌은 한 owner가 순서대로 통합한다. 실험·benchmark·외부 비교 코드는
local-only 또는 별도 research branch에 유지하며 release tree에 우연히 들어가지
않게 source-list gate로 막는다.

## 2. 공통 제품 원칙과 SRP

### 2.1 CLI-first 권위

제품 범위는 CLI, GUI(Web/Desktop), Discord다. 제품 의미의 권위는 다음 한 방향
흐름으로 고정한다.

`surface input -> canonical CLI/domain request -> App use case -> Core exact engine
-> typed result -> surface presenter`

- CLI/domain parser가 공개 옵션의 정규형과 기본값을 소유한다.
- `clearra-app`이 use case, cancellation, continuation, minimum/tie reducer와
  product result 계약을 소유한다.
- `clearra-core-executor`가 ILC Geometry, BuildUp/reachability, exact candidate,
  pruning proof와 worker-neutral 계산을 소유한다.
- GUI와 Discord는 명령 알고리즘을 복제하지 않는다. 입력 수집, 진행 표시,
  pagination, 복사·렌더링과 locale 표현만 소유한다.
- Web worker, native HTTP, Oracle/light lookup은 같은 typed port의 실행 adapter다.
- presenter는 내부 bitfield, CTK1, raw field ID, worker/session/cache key를 사용자
  설명에 노출하지 않는다.

surface별 편의 기능이 필요하면 Core 결과를 다른 의미로 다시 계산하지 않고
동일한 typed result의 projection을 추가한다. Discord의 명령 재설계와
`/help` 계약도 이 경계를 유지한다.

### 2.2 결과와 identity

- candidate identity는 규칙, 정규화된 초기 field, 목표 줄 수, piece/hold/queue
  provenance, concrete placement와 ILC realization을 포함한다.
- 정렬과 tie-break는 stable canonical candidate ID를 사용한다.
- 점수 동률에는 attack을 섞지 않는다. attack은 별도 표시 값이며 동등성,
  자격, 최소 집합 membership 또는 정렬 권위가 아니다.
- GUI/CLI의 명시적 tie 경로는 continuation으로 다음 집합을 조회한다.
  Discord는 가장 작은 canonical identity를 우선한 하나로 고정한다.
- 한 화면에 100개씩 lazy render할 수 있지만, 복사는 현재 선택한 해법 집합
  전체를 복사한다. 렌더링 page slice를 복사 의미로 사용하지 않는다.
- CTK3 변환과 GIF/이미지 생성은 결과 선택 이후 presenter에서만 실행한다.
  Geometry, minimum proof 또는 probability 계산 중 CTK3를 만들지 않는다.

### 2.3 상태와 실패

모든 장기 실행은 `preparing -> running -> terminal`로 수렴한다.
`complete`, `empty`, `cancelled`, `unsupported`, `resource_limit`,
`unavailable`, `data_invalid`를 구분하고, 하나의 실패에서 범용 오류 세 개를
중복 표시하지 않는다. 제품 hard timeout은 두지 않는다. 시간 제한은 명시된
test fixture, Discord 응답/Cloud Run 수명, 사용자가 설정한 예산에만 둔다.

## 3. v0.8.0 정리

v0.8.0은 이 문서의 구현 대상이 아니다. v0.7.4 이후 CLI-first 경계, GUI/Discord
제품 이관, 배포 자동화와 최소 해법 v2 기반을 제공한 배경 릴리스로만 취급한다.

- v0.8.0의 이미 배포된 source/tag/artifact를 다시 작성하지 않는다.
- v0.8.0에서 발견됐지만 허용된 성능 문제와 후속 수학 최적화는 v0.8.1에서
  새 acceptance를 거친다.
- v0.8.0의 정적 PC4 베타는 v0.9.0 전환 자격이 생길 때까지 유지한다.
- 과거 v0.8.0 gate 성공은 v0.8.1 또는 v0.9.0 Go 증거가 아니다.

## 4. v0.8.1 알고리즘·제품 안정화

### 4.1 범위와 완료 의미

v0.8.1의 목표는 기존 exact 의미를 유지하면서 다음 비용을 줄이는 것이다.

- ILC Geometry에서 불가능한 branch를 더 일찍 제거
- minimum의 첫 정확한 canonical 집합을 빨리 반환
- worker 준비·분할·steal·종료 tail 개선
- PC와 Build probability가 같은 reducer와 진행 계약 사용
- CLI, GUI, Discord 결과·pagination·copy·i18n parity 보장

수학 필터는 모두 필요조건 기반의 negative filter다. 필터가 통과했다고 해법을
증명하지 않으며, 실패했을 때만 해당 branch를 제거한다. 하나라도 false negative가
나오면 해당 필터는 기본 off로 되돌린다.

### 4.2 10-wide, 1~6L, 초기 field의 면적 조건

목표 너비는 10으로 고정하고 목표 줄 수 `l`은 1부터 6까지 모두 허용한다.
초기 field가 있을 수 있으므로 1/3/5L를 opening-PC 규칙으로 일괄 거부하지 않는다.

같은 scenario compiler와 line-clear normalization을 통과한 초기 점유 셀 집합을
`B`, 그 셀 수를 `b = |B|`, 앞으로 놓을 tetromino 수를 `m`, 목표 직사각형을
`R_l = {0..9} x {0..l-1}`로 둔다. 필요한 첫 조건은 다음과 같다.

`b + 4m = 10l`

따라서 빈 field의 홀수 줄 PC가 불가능하다는 사실과, 적절한 초기 field가 있는
1/3/5L scenario가 가능하다는 사실을 동시에 표현한다. `B`는 raw 입력 mask가
아니라 규칙에 맞게 정규화된 target frame의 점유 셀이어야 한다. target 밖 셀,
이미 지워졌어야 할 완성 줄, 높이 변환 오류는 parity 이전에 typed invalid input으로
처리한다.

면적 조건과 함께 다음 값도 cheap preflight로 계산한다.

- 남은 셀 수와 남은 piece 수
- 각 열의 정확한 수요
- 각 row/connected component의 4-cell 분해 가능성에 대한 안전한 하한·상한
- hold와 queue가 허용하는 piece multiplicity domain

### 4.3 수직 패리티

셀 집합 `S`에 대해 다음 signed column 합을 정의한다.

`V(S) = sum((x,y) in S) (-1)^x`

10-wide 완성 직사각형은 짝수·홀수 열이 각각 다섯 개이므로
`V(R_l) = 0`이다. 따라서 모든 완성 해법은 정확히 다음을 만족한다.

`V(B) + sum_j V(P_j) = 0`

면적 조건 때문에 `b`는 짝수이고 `V(B)/2`가 정수다. 이를 modulo 2로
내리면 다음 vertical parity가 된다.

`V(B)/2 + n_L + n_J + n_T_vertical = 0 (mod 2)`

여기서 `n_T_vertical`은 T의 세로 orientation, 즉 일렬인 세 칸에서 벗어난
한 칸이 좌우에 있는 orientation의 개수다. 빈 초기 field에서는 사용자가 제시한
`L/J 개수 + 세로 T 개수는 짝수` 조건으로 환원된다. 초기 field가 있으면
`V(B)/2`가 보정항이므로 단순 짝수 규칙을 그대로 적용하면 안 된다.

구현은 piece 이름만 세는 전역 shortcut보다 실제 Geometry row의
`V(P)` signature를 사용한다. 이는 kick table이나 같은 occupancy로 접히는
realization과 무관하게 셀 수준 필요조건을 보존하고, residual search에서도
남은 target과 남은 piece domain을 직접 비교할 수 있게 한다.

### 4.4 4색 패리티

셀 집합 `S`에 대해 열 번호의 modulo 4 합을 정의한다.

`M4(S) = sum((x,y) in S) x (mod 4)`

한 행에서 `0+1+...+9 = 45 = 1 (mod 4)`이므로 완성 직사각형은
`M4(R_l) = l (mod 4)`이다. 모든 완성 해법의 필요조건은 다음과 같다.

`M4(B) + sum_j M4(P_j) = l (mod 4)`

tetromino를 가로로 한 칸 평행이동하면 네 셀의 합이 4 증가하므로
`M4(P)`는 가로 위치와 무관하다. 실제 placement orientation별 residue를
catalog compile 시 한 번 계산한다.

- T/L/J는 돌출 셀이 오른쪽이면 `+1`, 왼쪽이면 `-1`인 orientation
  residue를 가진다.
- 세로 S/Z와 가로 I/O 계열에는 `2` residue가 나타날 수 있다.
- 나머지는 `0` 또는 shape/orientation에 맞는 실제 계산값을 사용한다.

위 설명은 사람을 위한 분류일 뿐, 제품 코드는 도형 이름별 상수를 권위로 삼지
않고 각 row의 네 좌표에서 residue를 계산한다. rotation convention이나
kick profile이 바뀌어도 occupancy signature가 같은 한 결과가 유지된다.

현재 `parity-report.v1`의 `four_color_counts`는 `(x mod 2, y mod 2)` 네 색을
세는 정적 문서 관찰값이다. 이 값은 여기서 정의한 열 방향 `M4 = sum(x) mod 4`와
이름만 비슷할 뿐 같은 invariant가 아니며 pruning 권위도 없다. 구현과 진단 필드는
내부적으로 `column_mod_four`처럼 두 의미를 구별하는 이름을 사용하고, 기존 정적
리포트를 새 PC feasibility 증거로 승격하지 않는다.

residual node에서는 이미 사용한 placement를 다시 합산하지 않는다. 남은 target
셀 `E'`의 `M4(E')`와 남은 piece별 가능한 residue bitset을 작은 modulo-4
convolution으로 비교한다. 가능한 합이 없을 때만 prune한다.

### 4.5 수직 패리티와 4색 패리티의 포함 관계

수직 패리티를 4색 패리티와 독립적인 두 번째 고비용 필터로 중복 실행하지 않는다.
짝수 크기 셀 집합 `S`에 대해

`V(S)/2 = |S|/2 + M4(S) (mod 2)`

이고, 각 tetromino는 `|P|/2 = 2 = 0 (mod 2)`다. 면적 조건
`b + 4m = 10l`까지 함께 쓰면 vertical parity는 4색 조건의 modulo-2
projection이다.

따라서 구현 순서는 다음과 같다.

1. 면적과 입력 정규화
2. residual 셀 한 번의 순회로 column signature, checker 값과 `M4`를 함께 계산
3. 하나의 modulo-4 domain을 합성해 target residue를 검사하고, vertical/modulo-2는
   그 domain의 파생 view 또는 무비용 조기 판정으로만 사용
4. 필요할 때만 더 강한 APDP·exact-column·component 분석

같은 정보를 별도 cache와 digest로 두 번 유지하지 않는다. 하나의 additive
signature owner가 `mod 2`, `mod 4` view를 제공한다.

### 4.6 APDP, checkerboard와의 관계

4색 패리티는 고정된 `x mod 4` additive invariant다. 전통적인 checkerboard
parity는 `(x+y) mod 2`를 사용하므로 서로 같지 않다. 4색 패리티를
checkerboard의 별칭으로 구현하지 않는다.

APDP는 placement/partial shape가 가질 수 있는 여러 additive 상태의 reachable
domain을 동적으로 합성하는 더 일반적인 틀이다. 적절한 weight와 state를 넣으면
vertical, 4색, checkerboard 또는 그 joint domain을 표현할 수 있지만, 현재 APDP가
자동으로 그 모두를 계산한다고 가정하지 않는다. 다음을 증명한 뒤 통합한다.

- APDP state가 사용하는 정확한 좌표계와 line-clear frame
- piece/partial-shape transition의 보존식
- `M4` 단독 및 `M4 x checkerboard` joint domain의 over-approximation 방향
- 기존 APDP와 새 fixed residue filter의 중복 비용

cheap fixed residue가 APDP보다 먼저 충분한 branch를 제거하면 그대로 분리한다.
APDP에 합쳤을 때 cache locality와 node당 비용이 개선되는 경우에만 단일 state로
통합한다.

### 4.7 ILC, line-clear, row 선택

패리티는 줄 지우기 순서를 직접 시뮬레이션하지 않아도 target frame의 완성
직사각형을 기준으로 성립한다. 다만 placement row는 반드시 ILC가 만든
inverse-clear realization을 target frame에 투영한 실제 셀을 사용한다.

- ILC catalog 이전에 raw board만 보고 concrete placement를 제거하지 않는다.
- ILC compile 뒤 Geometry row에 column, `V`, `M4`, checkerboard/APDP
  signature를 붙인다.
- 6L에서도 목표 row를 2/4L로 고정하지 않고 `l=1..6`의 실제 target을 쓴다.
- 4색 residue는 같은 orientation의 세로 위치를 구분하지 못한다. row 선택
  전체를 대체하지 않고 orientation/family domain을 먼저 줄이는 역할만 한다.
- exact cover, BuildUp, reachability와 terminal clear 검증이 최종 권위를 가진다.

### 4.8 legal-board 후보

legal-board는 규칙별 도달 가능한 board/placement domain을 미리 요약한 negative
filter 후보로 유지한다. SRS, SRS+, SRS-X, Jstris-180, no-kick의 kick table이
다르므로 하나의 index를 공유하지 않는다.

- generator 입력에 rule profile, kick-table identity, rotation convention,
  board height/width, spin/180 정책을 포함한다.
- kick table이 바뀌면 해당 index를 재생성하고 identity를 바꾼다.
- closed-world 생성 완전성과 no-false-negative KAT가 없으면 제품 filter로
  사용하지 않는다.
- 외부 구현은 알고리즘 아이디어와 공개 수학만 참고한다. 라이선스가 불명확한
  코드·생성 자산은 복사하거나 vendoring하지 않는다.
- first-use 대형 generation을 GUI나 Discord 요청 안에서 실행하지 않는다.
- 범위가 불완전하면 `unknown`으로 통과시키고 `illegal`로 prune하지 않는다.

legal-board는 ILC를 대체하지 않는다. A/B에서 compile/memory 비용을 포함한 p95
이득이 확인되고 exact result parity가 유지될 때만 규칙별로 opt-in한다.

v0.8.1에서는 제품 활성화를 명시적으로 보류한다. 2026-09-07의 독립 local-only
경계 실험은 generation key와 실패 폐쇄 계약을 검증했지만, 다섯 rule profile별
완전한 4L index generation·closed-domain 증명·재배포 가능한 자산 라이선스를
제공하지 않았다. 특히 arbitrary initial field는 empty-origin index의 부재만으로
불가능 판정을 내릴 수 없다. 따라서 이번 버전은 기존 cheap invariant와 ILC를
유지하고, 모든 미자격/누락/메모리 초과를 `unknown`으로 통과시킨다. 새로 독립
작성한 Clearra index와 규칙별 no-false-negative KAT가 마련되기 전에는 이 A/B를
반복하거나 제품 flag를 만들지 않는다.

### 4.9 minimum: 첫 정확한 canonical 집합과 lazy tie

최소 해법은 candidate가 덮는 queue/pattern universe의 exact set-cover 문제다.
v0.8.1의 공개 완료 단위는 모든 동률 집합이 아니라 다음 둘이다.

1. 최소 cardinality가 더 작을 수 없다는 정확한 증명
2. 그 cardinality에서 original canonical candidate ID 순으로 가장 앞선 집합 하나

첫 결과 전에 전체 동률 개수나 모든 portfolio를 세지 않는다. 내부 dense row ID,
worker partition 순서 또는 solver의 첫 feasible 해를 canonical 결과로 쓰지 않는다.
정규화된 original candidate identity에 대한 lexicographic refinement를 수행한다.

후속 동률 집합은 다음 continuation 계약으로 lazy하게 찾는다.

- accepted source/problem/candidate-family identity
- 증명된 최소 cardinality
- 직전 canonical portfolio와 exclusion frontier
- tie 정책과 정렬 schema version
- generation, cancellation 및 memory budget

다음 페이지는 직전 집합 이하를 제외하고 정확한 다음 canonical 집합을 찾는다.
미확정 tie 총수를 `N개`로 표시하지 않고 `추가 결과 확인 가능` 상태로 둔다.
GUI와 명시적 CLI 경로만 페이지를 넘기며 Discord는 첫 canonical 집합 하나로
고정한다.

Qnia/OR-Tools CP-SAT, HiGHS와 SAT/ILP의 branch ordering, presolve, dominance,
warm-start 아이디어는 동일한 normalized incidence matrix에서 local-only A/B한다.
외부 solver의 `Fast` 또는 첫 feasible 집합을 exact canonical 결과로 간주하지
않는다. 도입 후보는 다음처럼 분리한다.

- 알고리즘: dominance, forced row/column, lower bound, component decomposition,
  branch-and-bound, incumbent seeding, lexicographic proof
- 구현: bitset layout, allocation, memo, work queue, serialization
- 병렬화: partition grain, steal, shared incumbent, proof frontier merge

각 축을 따로 on/off 계측해 미세 최적화와 알고리즘 개선을 혼동하지 않는다.

### 4.10 parallelism과 tail

worker 수는 host 제어 thread를 포함하는 표시 숫자와 실제 계산 worker를 구분한다.
`사용 가능한 논리 프로세서 N`에 대해 기본 정책은 플랫폼별로 결정하되 다음
불변식을 지킨다.

- browser main thread는 UI, cancellation, message pump를 막는 긴 계산에 참여하지 않는다.
- 별도 coordinator worker는 관리 중에도 계산 worker의 준비를 직렬로 기다리지 않는다.
- 격리된 `모든 논리 프로세서 사용` 옵션은 계산 worker N 또는 host가 허용한
  별도 coordinator+N 구성을 명시하며, 몰래 N-1로 낮추지 않는다.
- Discord/Cloud Run처럼 UI thread를 남길 필요가 없는 격리 환경은 CPU quota와
  event loop를 해치지 않는 범위에서 N worker를 허용한다.
- 작은 탐색을 piece 수만으로 1 worker에 고정하지 않는다. 추정 작업량,
  branching, objective와 measured dispatch cost를 함께 사용한다.
- 큰 partition 하나가 남을 때 worker가 줄어드는 tail은 work stealing 또는
  재분할 가능한 frontier로 완화한다.
- 너무 작은 task의 steal storm, 공유 incumbent contention, clone/transfer 비용은
  최소 grain과 bounded mailbox로 막는다.

active worker 표시는 실제 계산 중인 수와 admitted maximum을 `active/max`로
고정 폭 영역에 보여 준다. 단계 전환 때 이전 단계 worker 수가 남지 않으며,
숫자 폭 변화로 경과 시간이 이동하거나 깜빡이지 않는다. 이 UI는 성능 증거가
아니므로 trace의 admitted, ready, active, stolen, completed, idle reason과 대조한다.

### 4.11 결과 집계와 surface parity

PC와 Build probability는 적용 가능한 공통 result reducer를 공유한다.

- 전체 해법
- Complete Replay Paths
- Minimum Solutions
- field별 score와 전체 score
- Field Average Score
- score-optimal minimum set
- tiling/build probability
- spin/search-specific 집계

`Field Average Score`는 최고 점수 최소 집합의 다른 이름이 아니다. 각 field의
점수와 전체 평균/집계를 보존한다. 최고 점수 최소 해법 집합은
`score-minimals`의 별도 typed contract다.

전체 replay는 첫 frame PNG가 아니라 전체 placement/clear 경로를 frame당 500ms의
GIF로 렌더링한다. 너무 많은 replay를 한 응답에 materialize하지 않고 canonical
grouping, lazy page와 명시적 export를 사용한다. 패턴 전체 replay와 고정 queue
replay의 입력 계약을 섞지 않는다.

GUI는 기존 간편 surface 수준을 유지한다. 결과 옵션이 실제 App request에 연결되지
않은 채 화면에만 존재하는 상태를 금지한다. locale별 label, 빈 field, 준비·취소,
복사, 페이지 전환을 같은 typed result로 테스트한다.

의존하지 않는다.

## 5. v0.9.0 PC4 Online Tablebase

### 5.1 핵심 의미 교정

v0.9.0은 V* optimal recommendation 제품이 아니다. muse918의
`tetris-4lpc-mdp-vstar-policy`에서 policy/value layer는 ZXCL-PC가 최선의
한 action을 고르는 데 사용할 수 있지만, 그 사실이 graph에 최적 해법 하나만
있다는 뜻은 아니다.

graph는 모델 domain의 `source field + piece`에 대한 모든 outgoing field
transition edge를 제공한다. v0.9.0은 policy 하나를 따르지 않고 모든 outgoing
edge를 순회해 인증된 1~4L PC terminal에 도달하는 전체 graph-level solution
family를 구한다.
V*, policy recommendation, optimal action UI·CLI·Discord 명령은 범위에서 제외하고
관련 value/policy 자산을 제품 경로에서 읽지 않는다.

v0.9.0의 검색 권위로 허용하는 데이터는 다음 둘뿐이다.

1. profile·generation·target별 완결성이 인증된 all-outgoing `graph.bin` 계열
2. 그 graph 또는 Clearra offline exact PC 탐색을 끝까지 실행해 만든, 동일한
   완결성 manifest에 결박된 전체 PC 해법 집합

두 번째 형태도 한 최선 수나 policy cache가 아니라 complete candidate family다.
V*, value, policy, Krylov state는 candidate 생성·prune·정렬·tie-break·확률·Setup
판정 어느 단계에도 참여하지 않는다. dormant future seam의 타입이 저장소에
존재하더라도 v0.9.0 Cargo/product dependency graph, capability registry, command,
network discovery와 runtime I/O에서 도달할 수 없어야 한다.

다만 다음 둘을 구분한다.

- graph-level completeness: 주어진 모델 domain과 queue/hold 조건에서 모든 outgoing
  state transition path
- Clearra product completeness: concrete rotation, x/y, kick/ILC realization,
  replay와 기존 duplicate semantics를 보존한 모든 해법

첫 번째만으로 두 번째가 자동 증명되지 않는다. v0.9.0의 가장 중요한 구현·자격
과제는 §5.5의 exact materialization이다.

각 field ID의 adjacency 위치를 index로 찾는 것은 상수 또는 logarithmic Range
조회로 만들 수 있지만, 전체 해법 나열 자체는 O(1)이 아니다. 시간과 출력은 방문한
graph edge 및 반환 solution 수에 비례하는 output-sensitive traversal이다.
UI에 O(1) 전체 열거라고 설명하지 않는다.

### 5.2 지원 범위

- field/graph 높이 domain: 정규화 뒤 최대 4줄
- PC 목표 줄 수: 1~4L 중 해당 profile·generation·target의 terminal과 graph
  completeness가 별도로 인증된 값. `PC4`라는 이름만으로 짧은 목표를 추론하지 않음
- 규칙 목표: SRS, SRS+, SRS-X, Jstris-180, no-kick. 다섯 profile은
  독립적으로 자격·활성화하며, 한 generation에서 일부만 사용 가능해도 자격을
  끝낸 profile은 먼저 제공할 수 있다.
- 입력: 정규화 가능한 field, hold/current/preview 또는 fixed queue/pattern
- 출력: 기존 PC full-solution typed result와 동일한 concrete solution family
- 소비 reducer: 전체 해법, coverage/probability, minimum, score-minimals, replay
- 표면: CLI, GUI(Web/Desktop), Discord

4L을 넘는 PC, target별 terminal completeness가 인증되지 않은 1~4L 요청,
인증되지 않은 field, unknown rule, 지원하지 않는 spin/setup 의미는
TB miss 또는 unsupported다. graph에 field가 없다는 사실을 일반적인
`해법 없음` 증명으로 확대하지 않는다.

### 5.3 데이터셋과 현재 알려진 자산

대상 저장소는
[muse918/tetris-4lpc-mdp-vstar-policy](https://huggingface.co/datasets/muse918/tetris-4lpc-mdp-vstar-policy)다.
전체 용량이 매우 크므로 앱이나 CI가 전체 snapshot을 다운로드하지 않는다.

2026-09-12 moving `main` 재감사에서는 위 graph/index 파일들이 dataset tree에

어긋나 있었다. README가 loader spec으로 연결한

사용한 moving revision·LFS digest를 프로그램 상수나 영구 manifest로 복사하지
않고, 매 generation discovery가 새로 해석한 뒤 §5.4 자격 절차를 통과시킨다.

같은 감사에서 moving ref를 먼저 immutable revision으로 해석한 뒤 두 helper

reader의 helper-container 경계를 뒷받침하지만, shared index와 각 graph/profile의
generation 결박이나 graph record layout을 증명하지는 않는다.

2026-09-13 소스 및 bounded Range 교차 검증에서 shared index는 `graph.bin`의
세 표본 ID와 EOF에 일치했지만 다른 네 graph에는 일치하지 않았다. SRS-X의
첫 네 레코드는 u32 LE target으로 해석할 때 정상적인 hash 순서를 보였다.
`no180 = SRS`는 사용자 지정 profile 매핑으로 채택하되, 실제 kick 동일성과
완결성 자격은 별도 검증한다. 상세 형식과 검증 한계는
[인덱스 의미 복원 기록](research/pc4-index-semantics-2026-09-13.md)에 남긴다.

### 5.4 로컬 증거 복원과 fail-closed 자격

추가 답변을 기다리지 않고 공개 소스, 제한된 실제 바이트 조회, 독립적인 로컬
차등 검증으로 다음 의미와 계약을 복원한다. upstream의 직접 답변 자체를 필수
선행 조건으로 두지 않되, v0.9.0 production 활성화 전에는 각 지원 profile에 대해
다음 항목의 재현 가능한 증거가 필요하다. 일부 표본 성공을 전체 완결성으로
승격하지 않는다.

- profile 이름과 정확한 kick/rotation/180 규칙 identity
- graph file format version, integer width, endianness와 record layout
- field canonicalization/hash/ID ordering
- per-field adjacency offset index와 hash-to-ID index
- graph, 두 index, format spec가 같은 generation임을 증명하는 binding
- layer/domain 범위와 graph completeness 한계
- 작은 source/piece/edges/terminal known-answer vectors
- license와 redistribution/direct-Range 허용 범위

한 profile의 index를 다른 profile에 대입하지 않는다. 위 정보가 없거나 모순되면
해당 profile만 `not_qualified`로 남는다. 적어도 한 profile이 전체 자격을 끝냈다면
v0.9.0 generation은 그 profile 집합으로 활성화할 수 있고, 나머지는 CLI/GUI/Discord
capability와 Setup admission에서 명시적으로 비활성화한다. 미자격 profile의 요청을
다른 graph나 기존 beta에 무음 전달하지 않으며, typed 안내와 명시 offline fallback만
제공한다. 후속 v0.9.x에서 새 profile 자격이 닫힐 때마다 같은 generation 절차로
독립 추가한다.

Clearra가 별도 HF auxiliary dataset, 대체 public index 또는 778GB mirror를 만들지
않는다. 로컬에서 생성한 임시 index를 production dependency, 릴리스 artifact,
정답 권위로 승격하지 않는다. 테스트는 synthetic fixture와 upstream KAT의 작은
Range만 사용한다.

### 5.5 graph edge에서 exact placement/replay materialization

graph edge가 보존하는 것은 source field, 현재 piece, target field transition이다.
일반적으로 edge 자체에는 다음 정보가 충분히 들어 있지 않을 수 있다.

- concrete rotation과 x/y
- 어떤 kick test가 성공했는지
- lock 전 이동/input sequence
- line-clear가 여러 realization에서 발생하는 정확한 순서
- 같은 source/target으로 접히는 서로 다른 legal placement
- Clearra canonical candidate ID와 duplicate equivalence

`Pc4SolutionMaterializer`는 selected rule의 Clearra ILC/placement generator로
source field와 piece에서 가능한 concrete placement를 열거하고, line clear 뒤
정규화된 target field가 edge target과 정확히 같은 항목을 모두 찾는다.

- 0개면 graph/profile/canonicalization 불일치이므로 `data_invalid`
- 1개면 그 concrete identity를 보존
- 여러 개면 기존 PC duplicate 계약에 따라 distinct identity를 모두 보존
- UI 편의를 위해 임의로 가장 작은 하나만 남기지 않음
- replay input sequence가 graph에서 복원되지 않으면 Clearra의 규칙별 reachability
  witness를 생성하고 그 provenance를 명시

전체 graph path는 각 edge의 concrete alternatives의 곱을 lazy하게 전개한다.
중간 state만 같다는 이유로 서로 다른 placement/replay solution을 잃지 않되,
기존 product가 같은 것으로 정의한 항목만 공통 canonical reducer에서 합친다.

upstream KAT와 Clearra offline exact solver의 작은 exhaustive corpus에서
source/target adjacency 및 materialized candidate set이 일치하기 전에는
`full solutions` capability를 공개하지 않는다.

### 5.6 독립 모듈과 SRP

온라인 TB는 기존 `CLR4TB12` 전역 installer에 네트워크 로직을 추가하지 않는다.
다음 책임을 분리한다.

| Owner | 책임 |
| --- | --- |
| `clearra-pc4-tablebase` 또는 동등한 순수 crate | manifest/schema, bounded binary parser, graph/index lookup state machine |
| `clearra-core-executor` | rule별 ILC/reachability와 exact edge materialization |
| `clearra-app` | TB request/session port, fallback 결정, cancellation, reducer 연결 |
| `clearra-cli` | native Range adapter와 명시 옵션/TTY UX |
| `clearra-gui-host` | Desktop bridge와 typed DTO |
| `apps/clearra-web` | browser Worker Range adapter, bounded cache와 progress |
| `apps/clearra-discord-bot` | interaction UX, light lookup 호출과 no-heavy-hit routing |
| release/ops | upstream discovery, qualification, signed generation manifest와 rollout |

순수 reader는 HTTP, browser API, filesystem 또는 Discord를 알지 않는다.
`Pc4LookupMachine`은 `NeedRange`, `Complete`, `Miss`, `Error`,
`Cancelled` step만 반환한다. `clearra-app`의 session owner가 generation,
request ID, stale response와 fallback을 관리한다.

기존 동기 `AppContext::run` 안에서 network fetch를 시작하지 않는다. host adapter가
typed `NeedRange`를 받아 비동기로 bytes를 공급하고, supplied bytes가
session/generation/artifact/offset/length와 정확히 일치할 때만 parser가 소비한다.

### 5.7 mutable upstream과 immutable generation manifest

제품 코드, Cargo/JS 상수, release tag 또는 계획 문서에 HF dataset commit SHA나
asset SHA256을 영구 고정하지 않는다. `main`의 새 업데이트를 매 요청마다
무검증으로 따라가지도 않는다.

두 identity를 분리한다.

- discovery identity: dataset repository와 update channel. mutable upstream을
  관찰하기 위한 설정이며 특정 revision을 코드에 박지 않는다.
- activation generation identity: 한 번 자격 심사를 통과한 resolved revision,
  profile별 artifact, byte length, format/index binding, content digest/ETag,
  KAT version과 compatibility schema를 담은 immutable signed manifest.

content digest는 그 generation의 전송 무결성을 검증하는 manifest 데이터이지
프로그램에 박힌 영구 dataset SHA가 아니다. upstream 변경은 기존 manifest를
수정하지 않고 새 `generation_id`를 만든다. 한 session은 시작한 generation에
끝까지 결박되고 중간에 `main`의 새 bytes로 바뀌지 않는다.

manifest resolver가 새 upstream revision을 발견해도 자동 활성화하지 않는다.
qualification CI가 활성화 후보인 각 profile의 format, index, KAT, differential,
Range와 성능 gate를 독립적으로 통과시킨 뒤 rollout pointer만 원자적으로
변경한다. 다섯 availability slot을 모두 기록하되, 미자격 slot은 명시
`not_qualified`이고 활성 profile의 자격을 막지 않는다. app version과 dataset
generation version은 별도다.

### 5.8 Range reader와 cache

각 lookup은 필요한 header, hash-index probe, 두 offset 및 adjacency slice만
HTTP Range로 읽는다.

- `206 Partial Content`, `Content-Range`, byte length와 manifest identity를 검증
- server가 전체 파일 `200`으로 반환하면 대형 body를 수용하지 않고 중단
- request별 최대 byte 수, session 총 byte 수와 동시 요청 수를 제한
- short read, overlapping/mismatched range, `416`, `429`, timeout을 typed error로 변환
- retry는 같은 immutable generation과 request ID의 bounded backoff만 허용
- range fragment cache는 `generation/profile/artifact/offset/length`로 key
- old generation cache를 새 generation 결과에 사용하지 않음
- GUI는 현재 요청과 결과 page에 필요한 부분만 lazy-load
- 전체 graph/policy/value layer를 background prefetch하지 않음

Web은 browser worker에서 HF로 직접 Range 요청한다. 이는 Clearra 계산 서버 호출이
아니지만 온라인 외부 데이터 접근이므로 사용자가 tablebase를 명시적으로 켠 뒤에만
시작한다. Desktop/CLI는 같은 machine의 native Range adapter를 사용한다.

### 5.9 queue, pattern, hold와 bag UX

fixed queue가 완전히 주어졌다면 bag 정보를 추가로 묻지 않는다. hold/current/preview도
명시 입력에서 정규화한다.

pattern 또는 hidden reveal 분포를 계산해야 할 때만 bag remainder가 필요하다.
provenance로 유일하게 추론할 수 없으면 다음처럼 처리한다.

- GUI: 필요한 이유와 남은 piece 선택 UI 제공
- interactive CLI: prompt 허용
- noninteractive CLI: 명시 `--bag-remaining` 없으면 typed input error
- Discord: modal로 사용자에게 piece remainder만 질문

raw qid, 내부 bag round 또는 임의의 reveal 순서를 사용자에게 요구하지 않는다.
pattern은 모든 concrete queue를 먼저 펼쳐 메모리에 담지 않고
`graph state x hold x bag multiset x preview position` DP로 합성한다.
최종 concrete solution path는 사용자가 page/export를 요구할 때 lazy하게 전개한다.

구현 체크포인트로 concrete fixed queue의 hold 상태기계는 pattern/bag DP와 분리한다.
이 층은 disabled/empty/occupied hold, current/swap/store-current 전이를 유한 budget
안에서 전수 전개하고 replay용 hold 결정을 보존한다. 동일 current/hold 교환은 하나의
semantic branch로 정규화하며, supplied queue가 끝난 뒤 보이지 않은 active piece를
가정해 held piece를 꺼내지 않는다. 이 순수 출력은 qualified fixed-queue graph
traversal의 입력일 뿐 hit나 solution 권위가 아니다.

또 다른 구현 체크포인트로 bag multiset의 1회 draw 전이는 별도 순수 상태기계로
분리한다. 이 층은 arbitrary multiplicity profile, 정확한 remainder, bag epoch를
소유하고, canonical distinct piece별 `multiplicity / denominator`와 다음 상태만
낸다. 빈 remainder에서만 profile로 refill하고 epoch를 checked increment한다.
이는 preview 관측 정책, pattern parser, hold, graph lookup 또는 제품 capability가
아니며, 실제 `graph x hold x bag x preview` DP 완성을 의미하지 않는다.

그 위의 두 번째 순수 체크포인트는 exact remainder와 명시된 hidden draw 수를
입력받는 bounded lazy reveal family다. 모든 concrete sequence를 선할당하지 않고
suffix count를 유한 memo budget 안에서 계산한 뒤 canonical piece 순서의 rank를
bounded page로 unrank한다. 각 sequence는 refill/epoch가 반영된 terminal state와
checked-u128 reduced rational 확률을 보존한다. count/rank/memo/page allocation,
cancellation, cursor-family mismatch와 산술 overflow는 typed failure로 닫는다.
이 family 역시 이후 `graph x hold x bag x preview` DP의 입력일 뿐이며 hold,
preview 관측 정책, pattern 문법 또는 graph 조회를 추론하지 않는다.

### 5.10 Setup 적용 경계

PC4 graph를 일반 Setup tablebase라고 부르지 않는다. 1~4L Setup 탐색에 적용할
때는 목표 줄 수까지 자격 manifest에 결박하고 다음 두 층을 분리한다.

1. TB가 해당 profile·generation·target에 대해 인증된 complete PC concrete
   candidate family를 공급
2. 기존 Setup engine이 target shape, spin, score, buildability 조건을 평가

해당 Setup 모드에서 TB candidate family가 기존 offline candidate universe와
완전 동등하다는 differential proof가 있을 때만 acceleration capability를 켠다.
증명이 없는 Setup objective는 기존 offline solver를 유지한다. graph miss를
Setup 불가능 증명으로 사용하지 않고, 부분 candidate를 전체라고 표시하지 않는다.

### 5.11 hit, miss, offline과 한도 처리

공통 결과 상태:

- `hit`: 인증된 domain에서 complete materialization 성공
- `miss`: 인증된 lookup에 상태 없음. 일반적 unsatisfiable 증명은 아님
- `not_qualified`: profile/manifest/index 자격 없음
- `offline` / `dataset_unavailable`
- `rate_limited`
- `snapshot_mismatch`
- `data_invalid`
- `cancelled`

fallback은 명시적이다.

- CLI는 별도 `--offline-fallback` 또는 동등한 옵션이 없으면 offline exact
  search를 시작하지 않는다.
- GUI와 Discord는 실패 이유, 예상 로컬/Cloud 비용, `오프라인으로 계속`,
  `중단` 동작을 제공한다. 안내만으로 자동 계산을 시작하지 않는다.
- fallback을 선택하면 기존 exact CLI/App use case를 새 요청으로 실행하고
  TB partial result와 섞지 않는다.
- rate limit retry와 offline fallback을 구분한다.

Discord의 TB hit는 heavy PC Cloud Run job을 실행하지 않는다. gateway/light lookup이
Range machine과 materializer를 완료하고 typed result를 기존 presenter에 전달한다.
heavy fallback은 사용자의 별도 선택과 기존 job 정책을 거친다. trace와 테스트에서
hit당 heavy Cloud Run invocation이 0임을 증명한다.

### 5.12 기존 result reducer 연결

TB 전용 결과 화면과 별도 의미를 만들지 않는다. materialized concrete candidates를
기존 canonical PC result pipeline에 공급한다.

여기서 `전체 해법`은 기존 Core가 BuildUp·도달성·coverage를 검증한 표준 PC
all-solution family를 뜻한다. raw Geometry만 반환하고 BuildUp·coverage·probability를
명시적으로 실행하지 않는 `PcTilingFamilyV1`은 같은 이름으로 우회하지 않는다.
온라인 graph 후보를 Core의 precomputed-Geometry ingress로 넣은 뒤 기존 검증 spine을
끝까지 통과시키며, raw-Geometry 전용 제품을 가속하려면 별도의 의미·동등성 계약을
먼저 추가한다.

- 전체 해법: complete candidate family
- probability/coverage: 동일 pattern universe와 denominator
- minimum: v0.8.1 first-canonical + lazy ties
- score-minimals: score-only B안, attack 비개입
- replay: materialized reachability witness와 500ms GIF
- copy/pagination/i18n: 기존 surface projection

result에는 provider가 `online-pc4-tablebase`인지 `offline-exact`인지,
rule profile, generation identity와 completeness scope를 machine-readable
provenance로 포함한다. presenter는 불필요한 내부 manifest/hash를 기본 UI에
노출하지 않지만 진단 export에는 민감하지 않은 identity를 남긴다.

### 5.13 기존 정적 베타 제거 시점

`pc4-compact-exact-v12.bin`과 `CLR4TB12` 경로는 v0.8.1 동안 유지한다.
다음 조건을 모두 충족한 v0.9.0 migration 커밋에서만 제거한다.

1. 최초 활성 profile이 하나 이상이고 각 활성 profile의 독립 자격 완료
2. 각 활성 profile의 PC full-solution materialization parity 완료
3. CLI/GUI/Discord의 profile별 capability와 hit/miss/not-qualified/fallback gate 완료
4. 새 generation rollout과 rollback 절차 검증
5. v0.8.1 artifact로 전체 application rollback 가능

제거 범위에는 static asset, CLI `include_bytes!`, App global installer,
WASM asset loader, Docker copy, old test fixture와 beta UI 문구가 포함된다.
같은 `--tablebase` 옵션 아래 old/new provider를 무음 혼용하지 않는다.
persisted beta opt-in은 새 외부 HF 접근 동의로 자동 승계하지 않고 새 opt-in을 받는다.

### 5.14 n-PC/Krylov 후속 seam

후속 PC(n-PCs) 확률과 Krylov 상태 공간은 v0.9.0/v0.9.x 공개 기능에서 제외한다.
V* recommendation도 제외한다. 이 절의 seam은 컴파일 가능한 소유권 자리일 뿐,
현재 PC/TB/Setup 경로에서 호출하거나 데이터셋을 발견·조회하는 기능이 아니다.

SRP를 지키기 위해 다음 내부 port/type 자리만 둘 수 있다.

- `PcNextProbabilityPort`
- `PcKrylovSnapshotAdapter`
- 별도 probability request/result/error namespace

이 seam은 feature-off이며 CLI command, GUI control, Discord command,
capability registry, network discovery 또는 실제 HF read에 연결하지 않는다.
synthetic no-I/O contract test만 허용한다. upstream 답변과 별도 제품 계획 없이
placeholder가 현재 TB manifest나 graph reader를 오염시키지 않게 한다.

### 5.15 v0.9.0 구현 순서

1. 새 순수 tablebase crate/module과 no-I/O synthetic parser fixture를 만든다.

4. upstream이 제공한 profile·target별 terminal, index/spec/KAT를 qualification

upstream 자격이 늦어져도 1~3과 synthetic tests는 진행할 수 있다. 4 이후의

format/integrity:

## 6. v0.9.x dataset generation 갱신

v0.9.x는 이미 자격을 통과한 제품 계약 안에서 upstream dataset generation을
갱신하기 위한 릴리스다. mutable `main`을 앱이 즉시 소비하는 채널이 아니다.

### 6.1 갱신 절차

1. discovery가 새 upstream revision을 발견
2. 별도 candidate generation manifest 생성
3. profile별 format/index/provenance와 license 재검증
4. KAT와 offline differential 재실행
5. Range byte/latency 및 full materialization A/B
6. 기존 app version과 호환성 검사
7. canary pointer에서 관찰
8. production generation pointer 원자적 promote
9. previous N generation 유지

graph bytes나 index가 같아도 manifest identity와 qualification receipt를 비교한다.
검증 없는 content-addressed cache hit를 release 권위로 사용하지 않는다.

### 6.2 버전 판정

- 데이터만 바뀌고 schema, rule 의미, candidate/result 의미가 같으면 v0.9.x patch
- parser/manifest schema가 backward-compatible하게 확장되면 영향에 따라 patch
  또는 minor를 결정
- rule semantics, completeness scope, public command/result가 바뀌면 v0.9.x
  자동 갱신으로 처리하지 않고 새 기능 릴리스 계획을 만든다.
- generation manifest는 다섯 profile의 availability를 모두 명시하되, 각 profile의
  artifact/index/qualification binding은 독립 slot이다. 이미 자격을 통과한 profile은
  그 slot의 새 generation만 promote할 수 있고, 준비되지 않은 profile은 직전의
  qualified generation을 암묵적으로 끌어오지 않은 채 명시 `not_qualified`로 남긴다.
- 서로 다른 revision이나 generation의 graph/index/qualification receipt를 한 profile
  slot 안에서 조합하지 않는다. 여러 profile이 동시에 갱신되더라도 하나의 profile
  검증 실패가 다른 독립 profile의 성공을 취소할 필요는 없지만, 실패 profile을
  성공한 profile의 자산으로 대체해서는 안 된다.

failure 시 application을 재배포하지 않고 generation pointer를 직전 qualified
manifest로 되돌릴 수 있어야 한다. parser incompatibility가 원인이면 app artifact와
manifest를 함께 atomic rollback한다.

## 7. v1.0.0 승격 조건

v1.0.0은 단순 버전 번호 변경이 아니라 다음 계약이 안정됐다는 선언이다.

- CLI-first PC/Build product contract와 GUI/Discord parity
- 1~6L initial-field exact search의 no-false-negative pruning
- minimum first-canonical/lazy-tie continuation의 schema 안정성
- 다섯 rule profile PC4 full-solution materialization
- upstream generation qualification, Range, cache, fallback과 rollback 운영
- old beta 완전 제거 및 migration 종료
- P0/P1 결함 0, 허용된 P2/P3의 owner와 후속 일정 명시
- 지원 플랫폼의 성능·memory budget과 cancellation
- release artifact 재사용, source identity와 배포 receipt
- 사용자 도움말에서 내부 로직 대신 실제 입력·결과·실패 행동 설명

n-PC/Krylov와 V* recommendation은 v1.0.0의 선행조건이 아니다. 별도 제품 계약과
데이터 자격을 얻기 전까지 비활성 future seam으로 남는다.

## 8. CI, 릴리스와 롤백

### 8.1 테스트 계층

- 변경 파일 owner의 focused unit/contract test
- 수학 filter 및 parser의 bounded exhaustive/fuzz/differential
- Core/App/CLI integration
- Web/Desktop/Discord surface contract
- canonical release acceptance
- exact artifact를 사용하는 Pages/CLI/Discord deployment smoke

작은 문서·presenter 수정에 전체 성능 suite를 실행하지 않는다. Core 알고리즘,
manifest/parser, product contract 또는 release 후보 변경 시에는 전체 gate를
배포 직전에 한 번 실행한다. 동일 exact source의 WASM/CLI/Discord core artifact는
한 producer가 만들고 downstream shard가 hash와 receipt를 검증해 재사용한다.

### 8.2 Go/No-Go

v0.8.1 No-Go:

- filter off/on result 차이 또는 unknown false negative
- minimum cardinality/canonical first set 차이
- lazy tie 누락·중복·순서 불안정
- worker 1/N 결과 차이, deadlock, UI main-thread 정지
- CLI/GUI/Discord result 의미 차이
- 기존 기능의 유의한 p95/peak-memory 회귀

v0.9.0 No-Go(활성화하려는 각 profile에 적용):

- 해당 profile의 upstream format/index/provenance 부재
- graph completeness 범위 불명
- exact placement/replay materialization 불일치
- 전체 solution을 policy 하나로 축소
- runtime이 mutable upstream을 session 중 무검증 추종
- Range 대신 전체 dataset 다운로드
- miss를 unsatisfiable로 표시
- Discord hit에서 heavy Cloud Run 실행
- old/new TB의 무음 혼용
- 미자격 profile을 다른 profile의 graph/index 또는 자격으로 실행
- 자격 profile이 하나도 없는 generation의 활성화

### 8.3 배포 순서

1. clean accepted source SHA에서 build-once artifacts 생성
2. focused와 full acceptance receipt를 source/artifact hash에 결박
3. Pages와 CLI candidate 배포 및 smoke
4. Discord light/heavy routing candidate와 Oracle path proof
5. v0.9.0이면 candidate generation manifest canary
6. 단 한 번의 publish/promote 결정
7. 모든 surface readback 후 release tag와 immutable release 게시
8. 관찰 기간 동안 P0/P1 및 provider telemetry 점검

Cloud Run candidate tag나 release tag는 promote 성공 전 최종 버전 권위가 아니다.
실패한 candidate는 lease/generation 기준으로 정리하고, 이미 동작 중인 N개
qualified version과 충돌하지 않게 한다.

### 8.4 롤백

- v0.8.1: 직전 v0.8.0 app/artifact와 명령 registry로 rollback
- v0.9.0: 직전 app artifact(v0.8.1, old beta 포함)로 전체 rollback
- v0.9.x: 우선 generation pointer만 직전 qualified manifest로 rollback
- parser/application 불일치 시 app+manifest atomic rollback
- in-flight session은 old generation을 완료하거나 typed cancellation
- 새 요청만 rollback pointer를 사용

rollback 성공은 health endpoint 하나가 아니라 CLI/Pages/Discord의 대표 명령,
Range identity, provider provenance와 no-heavy-hit routing readback으로 확인한다.

### 2026-09-13 materializer 재감사

graph의 cleared-row bottom 정규화와 고정 ILC target frame을 동일시한 오류를
발견했다. 비최하단 행 삭제 시 기존 셀의 비트 위치가 이동하므로 source가
target의 부분집합이라는 검사는 유효한 전이를 거절한다. 이 때문에 위 materializer
완료 표기를 다시 열었다. `Pc4RowFrame`의 경로별 원래 행 대응 및 exhaustive
두 단계 clear-history 테스트는 구현했지만, edge 역정규화와 concrete path의
최종 identity 연결은 아직 미완료다. 활성화 전에 반드시 완료한다.
