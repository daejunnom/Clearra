# Clearra v0.8.1 Hotfix 및 v0.9.0·v0.9.x PC4 Online Tablebase 구현·배포 계획

## 1. 문서 목적과 권위

이 문서는 이미 배포된 v0.8.0 이후의 활성 계획을 한곳에 복원한다. 범위는
v0.8.1 알고리즘·제품 안정화, v0.9.0 PC4 Online Tablebase, 후속 데이터
generation을 수용하는 v0.9.x, 그리고 v1.0.0 승격 조건이다.

`docs/v0.8.0-v0.9.0-implementation-release-plan.md`와
`docs/v0.8.0-remaining-work-plan.md`는 당시 판단과 배포 이력을 보존하는 역사
문서다. 이 문서는 그 파일을 수정하거나 과거의 미완료 판정을 현재의 완료 증거로
재사용하지 않는다. 충돌 시 다음 순서로 현재 상태를 판정한다.

1. 최종 사용자 결정과 이 문서의 제품 계약
2. 현재 Git-tracked 소스와 테스트
3. 최종 exact source SHA에 결박된 CI·artifact·배포 증거
4. 과거 계획 및 연구 기록

계획에 적힌 타입명과 파일명은 책임 경계를 설명하는 기준이다. 구현 중 이름을
바꿀 수는 있지만, Core 권위와 adapter 책임을 합치거나 비활성 기능을 우회해
공개하는 변경은 별도 설계 승인을 받아야 한다.

### 1.1 계획 복원 당시 기준선

계획 복원 당시 기준선에는 다음 기반이 존재했다. 이후 변경은 아래 현황 기록과
exact source의 검증 결과로 구분한다.

- PC Geometry는 `clearra-core-executor`의 inverse lock-clear(ILC) catalog,
  Geometry domain, APDP, component/projection 및 parallel search 경로를 사용한다.
- 최소 해법과 score-minimals의 typed product/result 경로가
  `clearra-app`에 있고 CLI, GUI host, Web, Discord가 이를 소비한다.
- 현재 `--tablebase`는
  `apps/clearra-web/static/tablebase/pc4-compact-exact-v12.bin`,
  `pc4_tablebase.rs`, `tablebase_runtime.rs`에 연결된 정적
  `CLR4TB12` 베타 자산이다.
- 현재 APDP나 v2 minimum 코드가 존재한다는 사실은 v0.8.1의 새 수학 필터,
  성능 목표 또는 전체 surface parity가 완료됐다는 뜻이 아니다.
- 현재 정적 베타가 존재한다는 사실은 muse918의 온라인 graph를 읽거나 전체
  PC 해법을 제공한다는 뜻이 아니다.

각 단계는 구현 후 새 증거로 다시 닫는다. 과거 benchmark, 한 번의 GUI 성공,
synthetic fixture 또는 특정 규칙의 성공을 다른 입력·규칙·surface의 권위로
확대하지 않는다.

### 1.2 릴리스 순서와 병렬 개발

개발은 다음 두 축을 독립 worktree/branch에서 병렬 진행할 수 있다.

- v0.8.1: 기존 exact solver의 수학 필터, minimum, parallelism, 제품 parity
- v0.9.0: feature-off PC4 graph reader, Range machine, manifest와 materializer

production mutation은 반드시 순차적이다.

1. v0.8.1 exact SHA를 acceptance하고 CLI·GUI·Discord에 배포한다.
2. 관찰 기간 동안 P0/P1 회귀가 없음을 확인한다.
3. v0.9.0 branch를 accepted v0.8.1 위로 재기준화하고 전체 gate를 다시 실행한다.
4. upstream 자격 조건이 모두 충족된 경우에만 v0.9.0 온라인 TB를 활성화한다.
5. 이후 호환 데이터 generation은 v0.9.x로 갱신한다.
6. 장기 안정성 조건이 충족되면 v1.0.0으로 승격한다.

서로 다른 branch의 소스 전체를 병합하지 않는다. 소유 모듈별 작은 커밋을 만들고,
공통 파일 충돌은 한 owner가 순서대로 통합한다. 실험·benchmark·외부 비교 코드는
local-only 또는 별도 research branch에 유지하며 release tree에 우연히 들어가지
않게 source-list gate로 막는다.

### 1.3 2026-09-13 Jstris 180 온라인 전환

사용자는 upstream Jstris 180의 전체 PC graph가 명시적으로 완료된 단계임을
확인했다. 이 선언과 Clearra reader의 형식 호환성 판정을 분리한다.

- HF의 현재 revision을 조회한 뒤 해당 작업 수명 동안만 고정한다. 고정 SHA256
  allowlist를 제품에 넣지 않는다. 다음 작업의 준비 캐시는 5분 후 재발견한다.
- 다섯 킥 프로필의 graph/field-index/offset-index를 독립적으로 확인한다.
  파일 크기, 헤더, 필드 수, record ordinal, offset 끝 경계와 작은 record 표본이
  일치하는지 자동 검사한다. 다른 graph에 canonical index를 대신 쓰지 않는다.
- 현재 upstream 완료 선언을 수용하는 공개 reader는 Jstris 180의 4L PC다.
  다른 프로필의 전용 index/형식/완료 선언이 부족하면 해당 프로필만 비활성화한다.
  graph 파일의 존재만으로 준비 완료를 선언하지 않는다.
- 이 표본 검사는 전체 graph의 수학적 재증명이 아니다. 기존 13개 미해결 전이
  관찰 기록도 삭제하지 않는다. 해당 13개는 2026-09-20 비게시 exact oracle에서
  전부 dead로 닫혔지만, 공개 graph 완료 선언과 generation 전체 materializer의
  규칙·좌표·행 제거 검증은 여전히 서로 다른 근거로 명시한다.
- Web의 TB 선택은 기존 정적 베타 파일을 읽지 않고 HF 부분 조회를 사용한다.
  CLI parser/App의 기존 후보·집계 경로에 연결하며 V*, policy, Krylov는 읽지 않는다.
- PC4 TB의 EN/KO/JA 베타 표기를 삭제한다. 별개인 미노 의존성 사전 분석의
  베타 표기는 이번 변경 대상이 아니다.
- 사용자가 제공한 회귀 기준: **빈 필드 / 4L / Jstris 180 / P7P4 / 전체 해법
  456,459개**. 이는 결과 집합의 비교 기준이며 프로그램이 이 개수를 강제로
  반환하거나 456,459개에서 탐색을 중단하는 조건이 아니다. 전체 열거가 끝나기
  전에는 같은 개수라고 판정하지 않는다. 필요 시 Wirelyre tetra-tools와 집합의
  정규화·홀드·회전·행 지우기 의미까지 대조한다.
- 4194의 실측은 준비/다운로드와 실제 온라인 탐색을 분리한다. 취소·Miss·통신
  실패·자원 한도는 완료 시간이 아니다. 자동 오프라인 fallback은 허용하지 않는다.
- 이 전환은 개발 프리뷰의 공개 연결 점검이며, CLI/Discord/셋업 전체 지원이나
  v0.9.0 릴리스 acceptance의 완료를 뜻하지 않는다.
- [실측 기록](research/pc4-online-profile-activation-2026-09-13.md): 실제 HF로
  한 피스 입력의 해법 1개를 GUI까지 반환했다. 빈 필드 P7P4는 244.8초에
  수동 취소했으므로 456,459개 일치는 미검증이다. 작은 Range의 순차 왕복
  비용 개선과 전체 집합 대조를 남은 과제로 유지한다.

### 1.4 2026-09-14 로컬 우선 TB 조회 최적화

사용자 지시에 따라 재실행/fallback 검증은 미루고, 별도 디렉터리에 프로필별 TB를
명시 저장하여 로컬 조회를 먼저 개선한 뒤 HTTP 전송을 개선한다. 작은 한 피스
입력의 성공 대신 빈 필드 / 4L / Jstris 180 / P7P4를 중심으로 비교한다.

- Jstris 180 세 파일 693,145,959B를 별도 계측 디렉터리에 한 번 저장·검증했다.
  제품 CLI/브라우저 저장소와는 별개이며 다른 프로필이나 V*/policy는 받지 않았다.
- `a22dbff`의 graph ID/hash 인덱스와 로컬 인덱스 페이징은 비게시 CI에서 통과했다.
  같은 10만 논리 조회 구간은 108.2초에서 19.7~20.2초로 줄었지만 **전체 탐색
  완료 시간이 아니다**. 4194에는 해당 CI WASM을 검증 후 게재했다.
- 큰 로컬 탐색 후반의 누적 공개 큐 재검증·재정렬을 새 delta만 처리하도록
  수정했다. 정확성 불변식, 완료 판정, 취소 및 예산은 유지한다. 이 후속 변경은
  `3ceca8b`의 App 테스트는 통과했지만 새 WASM의 120초 계측도 전체 탐색을
  끝내지 못했다. 작은 진전만 관찰했으며 a22 계측에 포함하거나 병목 해소로
  판정하지 않는다. 같은 CI에서 발견한 작은 인덱스 캐시 누락도 추가 수정했다.
- HTTP에서도 인덱스 4KiB 재사용 + graph 레코드 정확 범위를 적용한다. 기존
  16KiB 일괄 확장은 저장된 3만 조회 기록 중 8,325회에서 64MiB 한도에 걸렸고,
  새 정책은 15,026개 전송/20.96MB로 같은 3만 회를 처리했다. 이는 로컬 응답으로
  재생한 전송 정책 비교이며 실제 HTTP 시간이나 전체 456,459개 검증은 아니다.
- 대기열의 최대 32개 필드 ID를 App에서 전달하는 구현은 `7601eed`의 비게시
  CI 5개 job을 통과했다. 다만 실제 P7P4에서 모든 대기 필드를 앞서 읽는 첫
  정책은 요청 수가 증가하여 폐기했다. 현재 요청에 동봉할 수 있고 오프셋이 이미
  캐시에 있는 graph 레코드만 묶으며, 먼 필드 때문에 HTTP 요청을 추가하지 않는다.
  완료된 단일 graph 전송의 불필요한 캐시 점유와 먼 ID의 준비 연산도 제거했다.
- 같은 WASM의 10만 논리 조회 A/B에서 45,551회 → 45,220회(0.73% 감소),
  전송량 약 0.50MB 증가를 관찰했다. 전체 반환 바이트는 일치하지만 **전체 탐색
  완료나 큰 HTTP 가속 성공은 아니다**. 명시적 프로필별 전체 저장 경로는 조회
  HTTP를 0회로 유지한다. 이 후보의 JS 계약 31개와 native 보정은 `56c73ea`의
  비게시 CI 5개 job에서 통과했다(PC4 CLI 계약 25개 포함).
- 이후 로컬 GUI 파일 읽기는 지원되는 전용 워커에서 **읽기 전용 sync 핸들을
  파일당 한 번 열어 재사용**하도록 개선했다. 구형 API에 배타적 쓰기 핸들을
  요청하지 않으며 미지원 환경은 기존 Blob 경로를 유지한다. 업데이트/삭제 잠금은
  진행 중인 파일 읽기와 모든 핸들 닫기가 끝난 뒤에만 해제한다. 전체 파일을
  메모리에 추가 적재하거나 다른 킥 테이블의 자산을 빌려 쓰지 않는다.
- 같은 `7601eed` WASM과 10만 논리 조회를 유지한 새 HTTP 후보에서 현재 필요한
  graph 전송에 묶는 간격을 1KiB에서 4KiB로 넓혀 **45,220 → 44,443회**, 전송량
  **51,832,638 → 53,457,576B**를 확인했다. 무묶음 기준 45,551회보다 2.43% 적다.
  전체 순서 민감 반환 해시도 같지만, 로컬 응답 모델이며 전체 해법 완주는 아니다.
  캐시된 오프셋·이미 알려진 대기 ID만 이용하고 64KiB 단일 전송/64MiB 총량 제한을
  그대로 유지한다. 이 후속 변경은 관련 JS 46개 및 무출력 TS 타입 검사를 통과했다.
  실행 중인 4194 빌드 소유권 때문에 로컬 TS 계약 실행은 거절되었고, 서버를
  중단하거나 잠금을 우회하지 않고 해당 계약을 비게시 CI에 포함한다.
- 위 로컬 핸들/4KiB HTTP 묶음 변경 `acb27cb`는 비게시 CI
  [34774245129](https://github.com/daejunnom/Clearra/actions/runs/34774245129)의
  source/surface/PC4/native CLI job을 모두 통과했다(WASM 재빌드 job은 의도적으로
  생략). 이는 실제 브라우저 시간이나 전체 해법 수의 검증을 대신하지 않는다.
- 후속 큰 입력 점검에서는 observation 경로가 공개 큐·홀드별 근거를 전부
  생성한 뒤 Core에는 canonical 후보 합집합만 넘기는 중복을 확인했다. 이를 줄일
  `CompactPatternUnionLanguage` 입력 어댑터를 Supply 공통 계층에 추가한다.
  실제 compact 저장 구조의 구간·피스 제약을 유지하고 기존 홀드 전이를 재사용하며,
  같은 배치 접두사에서 동일한 공급 상태만 합친다. 원본 가중치·ordinal을 바꾸거나
  PC4 전체성 증명을 우회하지 않는다. **아직 graph/materializer 제품 경로를
  전환하지 않은 단계**로, 이 변경만으로 HTTP 요청 감소나 456,459개 완주를
  주장하지 않는다. 작은 입력 전수 대조와 P7P4 비전개 계약을 비게시 CI에 추가한다.
- 다른 프로필별 자격, 큰 입력의 전체 집합 실측과 release acceptance는 남아 있다.
  전송 테스트를 전체 탐색 완료나 실제 인터넷 속도 향상으로 확대하지 않는다.

소스·artifact identity, 재사용한 기록, 단계별 비용과 미완료 범위는
[로컬 우선 조회 개선 기록](research/pc4-local-first-lookup-optimization-2026-09-14.md)에 둔다.

### 1.5 2026-09-14 비동기 TB 작업 큐와 전송 배치 검토

사용자의 추가 제안에 따라 graph 연결 구현을 잠시 멈추고 당시 스케줄러와 전송을
대조했다. 이 절의 최초 관찰 시점에는 Web reader가 동시 요청을 지원해도 App/host가
한 pending 조회를 기다렸고 Windows CLI도 요청별 curl process와 HTTP/1.1을 사용했다.
후속 구현에서 이 제품 경계는 `pending_ranges()`와 persistent multi owner로 교체됐다.
현재 단일 pending 소비자는 로컬 파일 driver와 합성 test adapter뿐이며, 이를 현재
온라인 제품 병목으로 다시 분류하지 않는다.
실제 HF/CDN은 같은 HTTP/2 연결에서 두 단일 Range의 동시 응답을 확인했다.
HTTP/3는 광고만 확인했으며 실제 GUI/QUIC 협상이나 검색 성능의 증명은 아니다.

후보는 CPU ready queue, 응답 대기 continuation, 공유 bounded I/O broker의 분리다.
무제한 요청 대신 중복/인접 범위 결합, byte credit, 독립 응답별 재개와 tail 우선순위를
두며 입력·행 지우기·프로필·세대 및 전체성 계약은 유지한다. 먼저 local-first에서
정확성을 확인하고 온라인 전송으로 연결한다. `.safetensors` 전환은 선행 조건이
아니며 native mmap은 별도 A/B다. 기존 Jstris graph를 그대로 두는 64-record 블록
주소표는 실제 offset 기준 header 제외 949,112B로 표현 가능하다는 초기 상한을 얻었고,
후속 real-demand trace에서는 16-record 블록이 요청 수와 bytes의 균형이 더 좋았다.
다른 프로필의 재사용률과 WAN 검증 전에는 제품 정책으로 채택하지 않는다.

후속 native 후보는 최대 16개 known graph Range를 4KiB gap/64KiB span으로 묶고 한
`curl --parallel` owner에서 물리 전송 4개를 진행하며, 먼저 끝난 응답부터 exact
lookup/request ID로 admission한다. ready CPU는 전송과 겹쳐 진행하고 request/byte
credit은 I/O 전에 한 번에 예약한다. 이는 요청마다 curl을 기다리던 직렬 경로보다
제안 정책에 가깝지만, 실행 중인 유한 batch에 새 요청을 추가하지 못하므로 최종
host-lifetime libcurl multi/pool을 대신하지 않는다. graph/index 혼합 요청과 마지막
느린 transfer tail도 남은 A/B 대상으로 둔다.

HTTP/2·3은 강제 제품 옵션이 아니라 runtime capability다. 현재 Windows 개발 curl은
HTTP/2·3을 지원하지 않아 HTTP/1.1 병렬 연결만 검증 가능하다. Discord accepted
Bookworm 후보에는 curl/CA 설치와 build-time HTTP2 feature 검사를 추가했다. 실제
accepted image build와 HF 협상 receipt가 통과해야 활성 증거가 된다. HTTP/3는 별도
QUIC build와 유의미한 tail 이득이 확인되기 전에는 활성화하지 않는다. 제품 우선순위는
bounded persistent HTTP/2 multi, HTTP/1.1 fallback 순이다.

native qualification은 header, sampled index address, sampled graph record의 3개 의존
단계로만 나누고 단계 내부 Range는 같은 persistent multi에서 함께 제출한다. 단일 공개 HF
표본에서 scalar `87c2cdd`의 20 transfer/4.77초가 batch `cb65fe6`의 15 transfer/1.89초로
줄었고, 양쪽 모두 qualification 뒤 graph Range가 새 연결 0/HTTP2로 기존 연결을 재사용했다.
이는 handshake 중복과 초기 직렬 RTT 완화의 증거이지 full-search tail 완료 판정은 아니다.

Web은 TB opt-in 시 온라인 준비를 WASM worker 준비와 겹치고, 토글을 꺼도 terminal worker
dispose/fail-close 전에는 generation 준비를 폐기하지 않는다. cached online generation을
30초 이상 뒤 다시 켤 때는 실제 `graph*.bin` 경로의 exact 1바이트/1요청 Range를
`Request.cache=no-store`로 검색보다 먼저 실행한다. 작은 index의 HTTP cache hit를 graph CDN
handshake 완료로 오인하지 않으면서도 요청/전송 예산은 1회/1바이트로 유지한다. 브라우저가
소유한 socket을 영구 보장한다고 주장하거나 TB off 동안 timer heartbeat를 보내지 않는다.
다른 검색이 실행 중인 순간의 off→on 전이도 상위 controller가 transport-only 메시지를 즉시
보내 handshake를 시작한다. active WASM table 해제와 전체 worker 재설정은 terminal 뒤로
미루므로 선행 준비가 현재 검색의 안정성을 침범하지 않는다. 최초 generation discovery 전에도
opt-in을 허용하고 loading 이후 exact target 자격이 없을 때만 실행을 막아, 자격을 알아야
handshake를 시작할 수 있었던 UI 순환을 제거한다.
native의 TCP keepalive는 dead-peer probe로 유지하되 TCP Fast Open은 TLS session cache를
비활성화하는 libcurl 제약과 이 workload의 연결 재사용 우선순위 때문에 기본 off다.
추가 Windows/Schannel live 표본은 qualification 15 transfer에서 HTTP/2 0,
재사용 0, 누적 새 연결 22를 기록했고 후속 graph도 새 연결 1개를
열어 엄격 live 계약이 실패했다. 이 반례로 인해 Linux/Bookworm의 HTTP/2
성공 receipt를 Windows 제품 증거로 일반화하지 않으며, native persistent pool은
계속 opt-in으로 둔다. Windows 대형 탐색은 명시 전체 다운로드 로컬 TB가
우선이며, 실 HTTP/2/full-search tail A/B 전에는 HTTPS를 성능 동등 경로로
판정하지 않는다.

upstream 저장 형식은 `.safetensors`로 바꾸지 않는다. named dense tensor metadata는
가변 길이 Hydra graph record의 주소를 대체하지 못해 GOFF/sidecar가 계속 필요하다.
대신 resolved revision과 세 artifact identity에 결박된 qualified metadata cache 및
`graph block offsets v1` sidecar를 사용한다. `mmap`은 명시 다운로드 로컬 경로의
positional-read A/B 후보일 뿐 HTTP 최적화가 아니며, cold/warm 전체 wall time과 RSS
이득이 입증되기 전에는 기본값으로 켜지 않는다.

현재 정책, HTTP 실확인, 큐의 적체/완료 조건, 메타데이터 캐시와 upstream 보조 파일
후보는 [비동기 전송·파일 배치 검토](research/pc4-async-transport-and-layout-review-2026-09-14.md)에
기록한다. 이는 검토안 추가이며 4194, 배포, 프로필 활성화 또는 완료 판정을 바꾸지 않는다.

### 1.6 비동기 큐 연결 전 compact graph 생산자 구현

검토 이후 graph와 실제 compact 공급 상태를 합성하는 후보 생산자를 추가한다.
키는 `정규 부분 배치 집합 + 현재 graph 필드 + 원본 행 대응`으로 고정하며,
같은 깊이의 같은 키에 도달한 공급 상태만 합친다. HTTP가 필요한 작업은 필드별
대기 목록으로 보내고 다른 준비된 작업을 계속한다. 다음 깊이를 실행하기 전에는
모든 유입 상태를 합치는 장벽을 유지하며, 향후 장벽 제거에는 delta/fixpoint 증명이
필요하다. 완료 전 후보 제공이나 확률·리플레이 근거의 대체는 허용하지 않는다.

이 단계의 생산자는 제품 dispatcher에서 선택하지 않았다. 기존 생산자와의 60개
입력/홀드/프로필 대조, 6종 제품 집계, 행 지우기·분기 합류·서로 다른 응답 순서와
취소/불완전 결과 차단 계약을 비게시 CI에 추가한다. 작은 입력이 명시 배열로 저장되는
실제 경계를 유지하고, 대조 시험의 compact 입력은 공개 길이를 고정한 숨은 suffix로
만든다. 로컬 정적 검증과 새 Rust 실행 결과를 구분해 기록한다.

현재 남은 구현은 retained-byte 한도, 협력적 최종 정리, 큰 전체 집합 A/B와 Setup
결합이다. 제품 host의 다중 pending broker는 후속 persistent HTTP/2 작업으로 닫혔다.
내부 작업 큐 구현만으로 HTTP/GUI 병목이
해결됐다고 판정하지 않으며 기존 4194와 배포 상태를 유지한다. 상세 구현·검증 범위는
[로컬 우선 조회 개선 기록](research/pc4-local-first-lookup-optimization-2026-09-14.md)에 둔다.

후속 CI에서 새 입력 생성기의 `[IO]P5` 문법 오류를 확인해 `[IO]1P5`로 교정했다.
제품 문법은 바꾸지 않으며 60개 대조는 재실행 성공 전까지 미검증으로 남긴다.
다른 새 계약 4개 및 기존 계약은 통과했다. 후속 구현에서는 후보 수집·제자리 정렬·
digest를 작업 단위로 나누고 최종 버퍼가 동시에 존재하는 용량을 검사한다.
이는 최종 정리 버퍼만의 한도이며 전체 탐색 메모리 권위는 아니다. 이 변경의 실행
검증, 전체 retained-byte 처리, 큰 입력과 다중 pending 연결은 여전히 남아 있다.
이미 기록한 성능 A/B는 `--benchmarks` 명시 시에만 반복하며 일반 회귀와 정확성
대조 테스트는 유지한다. 이 단계에서는 4194와 제품 dispatcher를 전환하지 않았다.

### 1.7 2026-09-19 독립 조회 세션과 비동기 host 연결

`b23cb5ef8e04092d93c4ccb9e0436f6bd11fa28d`의

독립적으로 유지하며 어느 한도든 초과하면 잘린 결과가 아닌 명시 실패다. 이 후보의

### 1.8 2026-09-19 TB 큐·프로토콜 재비교

현재 커밋의 compact Web 경로는 8개 독립 lookup과 HTTP 기본 4개, 먼저 완료된 응답의
admission을 지원하지만 TB CPU 계산은 단일 WASM runner다. legacy/fixed-queue 및
CLI의 요청별 curl/동기 drive까지 비동기화됐다고 보지 않는다. 작업 큐 제안은 신규
확장 credit과 기존 응답 처리·작업 완료를 분리하는 방향으로 강화한다. `4840a32`에서
resident/source-target pin/CLOCK cache/admission revision을 구현했고 비게시 CI 다섯
job이 통과했다. 누적 cache-size 제한을 단순 증대하지 않고 100,000 lookup을 실제로
넘겼지만, 큰 입력 완료를 선언하지 않는다.

공개 HF/CDN의 같은 h2 연결에서 두 1B Range가 병렬 완료됨을 새로 확인했다.
이번에는 h3 광고를 관측하지 못했으며 실제 QUIC/GUI 협상은 미확인이다. 1.5절의
9월 14일 광고 관측은 과거 증거로 유지한다. CLI curl의 HTTP2/3 미지원도 재확인했다.
이는 전송 능력 확인이며 검색 성능 또는 4194/배포 반영의 증거가 아니다.

GOFF header의 세대별 검증 witness와 작은 블록 주소표를 별도 A/B 후보로 유지한다.
`.safetensors` 전환은 필수가 아니며 native mmap은 기존 binary의 read-only 수명
계약 아래 비교한다. 프로필별 파일과 전체 해법 의미는 바꾸지 않는다. 세부 경계와
새 통신 수치는 [전송·파일 배치 재비교 9절](research/pc4-async-transport-and-layout-review-2026-09-14.md#9-2026-09-19-재비교-검증-소스-작성-중-후보-실제-전송을-분리)에 기록했다.
새 로컬 대형 probe는 92.720초에 1,000,000 논리 조회(물리 390,678회,
273,225,460B) 한도로 취소됐다. 계산 28.701초, local I/O 25.993초,
host/WASM bridge 35.717초였고 FHID/GOFF/graph 논리 조회가 2/666,666/333,332로
`offset -> graph` 의존과 bridge 호출 감소가 다음 우선순위임을 확인했다. 이번
비교로 전체 게이트/프로필 자격/456,459개 전체성의 미완료 항목을 닫지 않는다.

`e8b6bfe`에서는 같은 generation/profile/artifact/field-count에 결박된 GOFF-header
witness를 구현해 compact field-ID lookup의 반복 header 논리 왕복을 제거했다. opaque
graph는 기존 FHID 검증을 유지한다. exact-source 비게시 CI `35439887487`의 다섯 job이
모두 통과했고, 동일 333,332 graph-demand local probe는 92.720초/1,000,000 logical read에서
72.993초/666,667 logical read로 줄었다. 물리 읽기와 bytes는 사실상 같고 bridge가
35.717초에서 25.932초로 줄었으므로 이는 논리 App/ABI 비용 개선이지 전체 검색이나 WAN
완료 증거가 아니다. 30,000 real-demand trace의 profile별 sparse
block-directory 모델에서는 Jstris 16-record 후보가 3,796,448B sidecar,
11,319 modeled requests/12,606,042B로 기존 채택 정책의 14,998회/21,016,558B보다
유리했다. 같은 sidecar를 실제 로컬 adapter 방식으로 읽은 결과도 sidecar
1,638회/6,707,616B와 graph 9,681회/5,898,426B로 모델과 정확히 일치했고, 9,999개
Hydra record가 기존 GOFF exact 범위와 byte 및 aggregate SHA-256까지 동일했다. 이는
read-only local adapter-format 증거이지 제품/WAN/전체 완료 증거가 아니다. 다른
프로필별 최대 block이 64KiB 이내이고 WAN에서 실제 tail이 줄어드는지 확인한 뒤에만
upstream 보조 파일을 요청한다.
HF 정적 경로의 multipart Range는 bounded probe에서 416이므로 여러 단일 h2 Range와
공유 bounded broker를 유지한다. `.safetensors`는 의존 왕복을 제거하지 않아 전환하지
않고, native mmap은 기존 binary의 immutable lease 아래 별도 A/B로 남긴다.

온라인 Tail 후보는 worker별 HTTP client가 아니라 shared broker의 bounded-fair 선택으로
구현한다. exact graph는 이미 점유한 resident 계산을 풀기 때문에 오래된 index FIFO보다
우선하되, 최대 3회 뒤 index 한 번을 강제한다. 기본 물리 요청 4개·논리 slot 16개·byte와
request 예산은 유지한다. focused range-reader 24개와 Web host 12개 계약은 통과했으며,
exact-source 비게시 CI `35440710495`의 다섯 job도 모두 통과했다. 실제 WAN/대형 전체
탐색 A/B 전에는 완료로 판정하지 않는다.
CLI/Discord 기본 경로는 최대 16개 graph demand를 유한 `curl --parallel` wave로 묶고
첫 완료 exact-ID를 admission하지만, wave 실행 중 새 handle을 추가하거나 다음 wave와
연결을 공유하지 못한다. `native-pc4-libcurl` opt-in 후보는 ready CPU drain -> 최대 16개
논리 queue -> 네 active easy handle -> 완료 slot 즉시 재충전 -> 첫 완료 exact-ID admission을
한 온라인 실행 수명의 multi owner 안에서 구현한다. 기존 index page/frontier cache는 유지하며,
mixed graph/index 3:1 통합과 full-search A/B 전에는 기본 feature로 승격하지 않는다. 서로
다른 CPU thread의 요청별 client를 늘리는 방식은 shared h2 stream/cache/취소 owner를
만들지 못하므로 채택하지 않는다. exact-source 비게시 CI `35446511211`에서 source/PC4/
native CLI/surface와 Ubuntu·Windows 후보 compile/link 및 두 owner unit이 모두 통과했다.
후보 빌드는 각각 1분 35초/4분 49초였으므로 특히 Windows 비용도 승격 A/B에 포함한다.

후속 실제 local-reader A/B에서는 sparse sidecar가 100,000 lookup의 파일 bytes를
51,329,915B에서 K=8 10,145,153B, K=16 19,551,146B로 줄였지만 검색 벽시계는
16.440초에서 각각 16.667초와 16.828초로 느려졌다. 30,000 lookup에서 보였던 K=8의
작은 이득은 큰 표본에서 재현되지 않았다. 따라서 명시 다운로드 제품에는 sidecar를
생성·활성화하지 않고 기존 exact graph 읽기를 유지한다. 실험용 adapter/benchmark만
남겨 WAN 후보와 같은 bytes를 재현한다. 온라인 K=16은 RTT가 지배적인 별도 가설이므로
source GOFF/graph identity, K, field count, target encoding, max span, completion과 sidecar
identity를 묶은 upstream manifest+보조 파일이 제공된 뒤 실제 HTTP A/B로 판정한다.
`.safetensors` 전환과 native mmap은 이 선행 조건이 아니다.

## 2. 공통 제품 원칙과 SRP

### 2.1 CLI-first 권위

제품 범위는 CLI, GUI(Web/Desktop), Discord다. 제품 의미의 권위는 다음 한 방향
흐름으로 고정한다.

`surface input -> canonical CLI/domain request -> App use case -> Core exact engine
-> typed result -> surface presenter`

- CLI/domain parser가 공개 옵션의 정규형과 기본값을 소유한다.
- `clearra-app`이 use case, cancellation, continuation, minimum/tie reducer와
  product result 계약을 소유한다.
- `clearra-core-executor`가 ILC Geometry, BuildUp/reachability, exact candidate,
  pruning proof와 worker-neutral 계산을 소유한다.
- GUI와 Discord는 명령 알고리즘을 복제하지 않는다. 입력 수집, 진행 표시,
  pagination, 복사·렌더링과 locale 표현만 소유한다.
- Web worker, native HTTP, Oracle/light lookup은 같은 typed port의 실행 adapter다.
- presenter는 내부 bitfield, CTK1, raw field ID, worker/session/cache key를 사용자
  설명에 노출하지 않는다.

surface별 편의 기능이 필요하면 Core 결과를 다른 의미로 다시 계산하지 않고
동일한 typed result의 projection을 추가한다. Discord의 명령 재설계와
`/help` 계약도 이 경계를 유지한다.

### 2.2 결과와 identity

- candidate identity는 규칙, 정규화된 초기 field, 목표 줄 수, piece/hold/queue
  provenance, concrete placement와 ILC realization을 포함한다.
- 정렬과 tie-break는 stable canonical candidate ID를 사용한다.
- 점수 동률에는 attack을 섞지 않는다. attack은 별도 표시 값이며 동등성,
  자격, 최소 집합 membership 또는 정렬 권위가 아니다.
- GUI/CLI의 명시적 tie 경로는 continuation으로 다음 집합을 조회한다.
  Discord는 가장 작은 canonical identity를 우선한 하나로 고정한다.
- 한 화면에 100개씩 lazy render할 수 있지만, 복사는 현재 선택한 해법 집합
  전체를 복사한다. 렌더링 page slice를 복사 의미로 사용하지 않는다.
- CTK3 변환과 GIF/이미지 생성은 결과 선택 이후 presenter에서만 실행한다.
  Geometry, minimum proof 또는 probability 계산 중 CTK3를 만들지 않는다.

### 2.3 상태와 실패

모든 장기 실행은 `preparing -> running -> terminal`로 수렴한다.
`complete`, `empty`, `cancelled`, `unsupported`, `resource_limit`,
`unavailable`, `data_invalid`를 구분하고, 하나의 실패에서 범용 오류 세 개를
중복 표시하지 않는다. 제품 hard timeout은 두지 않는다. 시간 제한은 명시된
test fixture, Discord 응답/Cloud Run 수명, 사용자가 설정한 예산에만 둔다.

## 4. v0.8.1 알고리즘·제품 안정화

### 4.1 범위와 완료 의미

v0.8.1의 목표는 기존 exact 의미를 유지하면서 다음 비용을 줄이는 것이다.

- ILC Geometry에서 불가능한 branch를 더 일찍 제거
- minimum의 첫 정확한 canonical 집합을 빨리 반환
- worker 준비·분할·steal·종료 tail 개선
- PC와 Build probability가 같은 reducer와 진행 계약 사용
- CLI, GUI, Discord 결과·pagination·copy·i18n parity 보장

수학 필터는 모두 필요조건 기반의 negative filter다. 필터가 통과했다고 해법을
증명하지 않으며, 실패했을 때만 해당 branch를 제거한다. 하나라도 false negative가
나오면 해당 필터는 기본 off로 되돌린다.

### 4.2 10-wide, 1~6L, 초기 field의 면적 조건

목표 너비는 10으로 고정하고 목표 줄 수 `l`은 1부터 6까지 모두 허용한다.
초기 field가 있을 수 있으므로 1/3/5L를 opening-PC 규칙으로 일괄 거부하지 않는다.

같은 scenario compiler와 line-clear normalization을 통과한 초기 점유 셀 집합을
`B`, 그 셀 수를 `b = |B|`, 앞으로 놓을 tetromino 수를 `m`, 목표 직사각형을
`R_l = {0..9} x {0..l-1}`로 둔다. 필요한 첫 조건은 다음과 같다.

`b + 4m = 10l`

따라서 빈 field의 홀수 줄 PC가 불가능하다는 사실과, 적절한 초기 field가 있는
1/3/5L scenario가 가능하다는 사실을 동시에 표현한다. `B`는 raw 입력 mask가
아니라 규칙에 맞게 정규화된 target frame의 점유 셀이어야 한다. target 밖 셀,
이미 지워졌어야 할 완성 줄, 높이 변환 오류는 parity 이전에 typed invalid input으로
처리한다.

면적 조건과 함께 다음 값도 cheap preflight로 계산한다.

- 남은 셀 수와 남은 piece 수
- 각 열의 정확한 수요
- 각 row/connected component의 4-cell 분해 가능성에 대한 안전한 하한·상한
- hold와 queue가 허용하는 piece multiplicity domain

### 4.3 수직 패리티

셀 집합 `S`에 대해 다음 signed column 합을 정의한다.

`V(S) = sum((x,y) in S) (-1)^x`

10-wide 완성 직사각형은 짝수·홀수 열이 각각 다섯 개이므로
`V(R_l) = 0`이다. 따라서 모든 완성 해법은 정확히 다음을 만족한다.

`V(B) + sum_j V(P_j) = 0`

면적 조건 때문에 `b`는 짝수이고 `V(B)/2`가 정수다. 이를 modulo 2로
내리면 다음 vertical parity가 된다.

`V(B)/2 + n_L + n_J + n_T_vertical = 0 (mod 2)`

여기서 `n_T_vertical`은 T의 세로 orientation, 즉 일렬인 세 칸에서 벗어난
한 칸이 좌우에 있는 orientation의 개수다. 빈 초기 field에서는 사용자가 제시한
`L/J 개수 + 세로 T 개수는 짝수` 조건으로 환원된다. 초기 field가 있으면
`V(B)/2`가 보정항이므로 단순 짝수 규칙을 그대로 적용하면 안 된다.

구현은 piece 이름만 세는 전역 shortcut보다 실제 Geometry row의
`V(P)` signature를 사용한다. 이는 kick table이나 같은 occupancy로 접히는
realization과 무관하게 셀 수준 필요조건을 보존하고, residual search에서도
남은 target과 남은 piece domain을 직접 비교할 수 있게 한다.

### 4.4 4색 패리티

셀 집합 `S`에 대해 열 번호의 modulo 4 합을 정의한다.

`M4(S) = sum((x,y) in S) x (mod 4)`

한 행에서 `0+1+...+9 = 45 = 1 (mod 4)`이므로 완성 직사각형은
`M4(R_l) = l (mod 4)`이다. 모든 완성 해법의 필요조건은 다음과 같다.

`M4(B) + sum_j M4(P_j) = l (mod 4)`

tetromino를 가로로 한 칸 평행이동하면 네 셀의 합이 4 증가하므로
`M4(P)`는 가로 위치와 무관하다. 실제 placement orientation별 residue를
catalog compile 시 한 번 계산한다.

- T/L/J는 돌출 셀이 오른쪽이면 `+1`, 왼쪽이면 `-1`인 orientation
  residue를 가진다.
- 세로 S/Z와 가로 I/O 계열에는 `2` residue가 나타날 수 있다.
- 나머지는 `0` 또는 shape/orientation에 맞는 실제 계산값을 사용한다.

위 설명은 사람을 위한 분류일 뿐, 제품 코드는 도형 이름별 상수를 권위로 삼지
않고 각 row의 네 좌표에서 residue를 계산한다. rotation convention이나
kick profile이 바뀌어도 occupancy signature가 같은 한 결과가 유지된다.

현재 `parity-report.v1`의 `four_color_counts`는 `(x mod 2, y mod 2)` 네 색을
세는 정적 문서 관찰값이다. 이 값은 여기서 정의한 열 방향 `M4 = sum(x) mod 4`와
이름만 비슷할 뿐 같은 invariant가 아니며 pruning 권위도 없다. 구현과 진단 필드는
내부적으로 `column_mod_four`처럼 두 의미를 구별하는 이름을 사용하고, 기존 정적
리포트를 새 PC feasibility 증거로 승격하지 않는다.

residual node에서는 이미 사용한 placement를 다시 합산하지 않는다. 남은 target
셀 `E'`의 `M4(E')`와 남은 piece별 가능한 residue bitset을 작은 modulo-4
convolution으로 비교한다. 가능한 합이 없을 때만 prune한다.

### 4.5 수직 패리티와 4색 패리티의 포함 관계

수직 패리티를 4색 패리티와 독립적인 두 번째 고비용 필터로 중복 실행하지 않는다.
짝수 크기 셀 집합 `S`에 대해

`V(S)/2 = |S|/2 + M4(S) (mod 2)`

이고, 각 tetromino는 `|P|/2 = 2 = 0 (mod 2)`다. 면적 조건
`b + 4m = 10l`까지 함께 쓰면 vertical parity는 4색 조건의 modulo-2
projection이다.

따라서 구현 순서는 다음과 같다.

1. 면적과 입력 정규화
2. residual 셀 한 번의 순회로 column signature, checker 값과 `M4`를 함께 계산
3. 하나의 modulo-4 domain을 합성해 target residue를 검사하고, vertical/modulo-2는
   그 domain의 파생 view 또는 무비용 조기 판정으로만 사용
4. 필요할 때만 더 강한 APDP·exact-column·component 분석

같은 정보를 별도 cache와 digest로 두 번 유지하지 않는다. 하나의 additive
signature owner가 `mod 2`, `mod 4` view를 제공한다.

### 4.6 APDP, checkerboard와의 관계

4색 패리티는 고정된 `x mod 4` additive invariant다. 전통적인 checkerboard
parity는 `(x+y) mod 2`를 사용하므로 서로 같지 않다. 4색 패리티를
checkerboard의 별칭으로 구현하지 않는다.

APDP는 placement/partial shape가 가질 수 있는 여러 additive 상태의 reachable
domain을 동적으로 합성하는 더 일반적인 틀이다. 적절한 weight와 state를 넣으면
vertical, 4색, checkerboard 또는 그 joint domain을 표현할 수 있지만, 현재 APDP가
자동으로 그 모두를 계산한다고 가정하지 않는다. 다음을 증명한 뒤 통합한다.

- APDP state가 사용하는 정확한 좌표계와 line-clear frame
- piece/partial-shape transition의 보존식
- `M4` 단독 및 `M4 x checkerboard` joint domain의 over-approximation 방향
- 기존 APDP와 새 fixed residue filter의 중복 비용

cheap fixed residue가 APDP보다 먼저 충분한 branch를 제거하면 그대로 분리한다.
APDP에 합쳤을 때 cache locality와 node당 비용이 개선되는 경우에만 단일 state로
통합한다.

### 4.7 ILC, line-clear, row 선택

패리티는 줄 지우기 순서를 직접 시뮬레이션하지 않아도 target frame의 완성
직사각형을 기준으로 성립한다. 다만 placement row는 반드시 ILC가 만든
inverse-clear realization을 target frame에 투영한 실제 셀을 사용한다.

- ILC catalog 이전에 raw board만 보고 concrete placement를 제거하지 않는다.
- ILC compile 뒤 Geometry row에 column, `V`, `M4`, checkerboard/APDP
  signature를 붙인다.
- 6L에서도 목표 row를 2/4L로 고정하지 않고 `l=1..6`의 실제 target을 쓴다.
- 4색 residue는 같은 orientation의 세로 위치를 구분하지 못한다. row 선택
  전체를 대체하지 않고 orientation/family domain을 먼저 줄이는 역할만 한다.
- exact cover, BuildUp, reachability와 terminal clear 검증이 최종 권위를 가진다.

### 4.8 legal-board 후보

legal-board는 규칙별 도달 가능한 board/placement domain을 미리 요약한 negative
filter 후보로 유지한다. SRS, SRS+, SRS-X, Jstris-180, no-kick의 kick table이
다르므로 하나의 index를 공유하지 않는다.

- generator 입력에 rule profile, kick-table identity, rotation convention,
  board height/width, spin/180 정책을 포함한다.
- kick table이 바뀌면 해당 index를 재생성하고 identity를 바꾼다.
- closed-world 생성 완전성과 no-false-negative KAT가 없으면 제품 filter로
  사용하지 않는다.
- 외부 구현은 알고리즘 아이디어와 공개 수학만 참고한다. 라이선스가 불명확한
  코드·생성 자산은 복사하거나 vendoring하지 않는다.
- first-use 대형 generation을 GUI나 Discord 요청 안에서 실행하지 않는다.
- 범위가 불완전하면 `unknown`으로 통과시키고 `illegal`로 prune하지 않는다.

legal-board는 ILC를 대체하지 않는다. A/B에서 compile/memory 비용을 포함한 p95
이득이 확인되고 exact result parity가 유지될 때만 규칙별로 opt-in한다.

v0.8.1에서는 제품 활성화를 명시적으로 보류한다. 2026-09-07의 독립 local-only
경계 실험은 generation key와 실패 폐쇄 계약을 검증했지만, 다섯 rule profile별
완전한 4L index generation·closed-domain 증명·재배포 가능한 자산 라이선스를
제공하지 않았다. 특히 arbitrary initial field는 empty-origin index의 부재만으로
불가능 판정을 내릴 수 없다. 따라서 이번 버전은 기존 cheap invariant와 ILC를
유지하고, 모든 미자격/누락/메모리 초과를 `unknown`으로 통과시킨다. 새로 독립
작성한 Clearra index와 규칙별 no-false-negative KAT가 마련되기 전에는 이 A/B를
반복하거나 제품 flag를 만들지 않는다.

### 4.9 minimum: 첫 정확한 canonical 집합과 lazy tie

최소 해법은 candidate가 덮는 queue/pattern universe의 exact set-cover 문제다.
v0.8.1의 공개 완료 단위는 모든 동률 집합이 아니라 다음 둘이다.

1. 최소 cardinality가 더 작을 수 없다는 정확한 증명
2. 그 cardinality에서 original canonical candidate ID 순으로 가장 앞선 집합 하나

첫 결과 전에 전체 동률 개수나 모든 portfolio를 세지 않는다. 내부 dense row ID,
worker partition 순서 또는 solver의 첫 feasible 해를 canonical 결과로 쓰지 않는다.
정규화된 original candidate identity에 대한 lexicographic refinement를 수행한다.

후속 동률 집합은 다음 continuation 계약으로 lazy하게 찾는다.

- accepted source/problem/candidate-family identity
- 증명된 최소 cardinality
- 직전 canonical portfolio와 exclusion frontier
- tie 정책과 정렬 schema version
- generation, cancellation 및 memory budget

다음 페이지는 직전 집합 이하를 제외하고 정확한 다음 canonical 집합을 찾는다.
미확정 tie 총수를 `N개`로 표시하지 않고 `추가 결과 확인 가능` 상태로 둔다.
GUI와 명시적 CLI 경로만 페이지를 넘기며 Discord는 첫 canonical 집합 하나로
고정한다.

Qnia/OR-Tools CP-SAT, HiGHS와 SAT/ILP의 branch ordering, presolve, dominance,
warm-start 아이디어는 동일한 normalized incidence matrix에서 local-only A/B한다.
외부 solver의 `Fast` 또는 첫 feasible 집합을 exact canonical 결과로 간주하지
않는다. 도입 후보는 다음처럼 분리한다.

- 알고리즘: dominance, forced row/column, lower bound, component decomposition,
  branch-and-bound, incumbent seeding, lexicographic proof
- 구현: bitset layout, allocation, memo, work queue, serialization
- 병렬화: partition grain, steal, shared incumbent, proof frontier merge

각 축을 따로 on/off 계측해 미세 최적화와 알고리즘 개선을 혼동하지 않는다.

### 4.10 parallelism과 tail

worker 수는 host 제어 thread를 포함하는 표시 숫자와 실제 계산 worker를 구분한다.
`사용 가능한 논리 프로세서 N`에 대해 기본 정책은 플랫폼별로 결정하되 다음
불변식을 지킨다.

- browser main thread는 UI, cancellation, message pump를 막는 긴 계산에 참여하지 않는다.
- 별도 coordinator worker는 관리 중에도 계산 worker의 준비를 직렬로 기다리지 않는다.
- 격리된 `모든 논리 프로세서 사용` 옵션은 계산 worker N 또는 host가 허용한
  별도 coordinator+N 구성을 명시하며, 몰래 N-1로 낮추지 않는다.
- Discord/Cloud Run처럼 UI thread를 남길 필요가 없는 격리 환경은 CPU quota와
  event loop를 해치지 않는 범위에서 N worker를 허용한다.
- 작은 탐색을 piece 수만으로 1 worker에 고정하지 않는다. 추정 작업량,
  branching, objective와 measured dispatch cost를 함께 사용한다.
- 큰 partition 하나가 남을 때 worker가 줄어드는 tail은 work stealing 또는
  재분할 가능한 frontier로 완화한다.
- 너무 작은 task의 steal storm, 공유 incumbent contention, clone/transfer 비용은
  최소 grain과 bounded mailbox로 막는다.

active worker 표시는 실제 계산 중인 수와 admitted maximum을 `active/max`로
고정 폭 영역에 보여 준다. 단계 전환 때 이전 단계 worker 수가 남지 않으며,
숫자 폭 변화로 경과 시간이 이동하거나 깜빡이지 않는다. 이 UI는 성능 증거가
아니므로 trace의 admitted, ready, active, stolen, completed, idle reason과 대조한다.

### 4.11 결과 집계와 surface parity

PC와 Build probability는 적용 가능한 공통 result reducer를 공유한다.

- 전체 해법
- Complete Replay Paths
- Minimum Solutions
- field별 score와 전체 score
- Field Average Score
- score-optimal minimum set
- tiling/build probability
- spin/search-specific 집계

`Field Average Score`는 최고 점수 최소 집합의 다른 이름이 아니다. 각 field의
점수와 전체 평균/집계를 보존한다. 최고 점수 최소 해법 집합은
`score-minimals`의 별도 typed contract다.

전체 replay는 첫 frame PNG가 아니라 전체 placement/clear 경로를 frame당 500ms의
GIF로 렌더링한다. 너무 많은 replay를 한 응답에 materialize하지 않고 canonical
grouping, lazy page와 명시적 export를 사용한다. 패턴 전체 replay와 고정 queue
replay의 입력 계약을 섞지 않는다.

GUI는 기존 간편 surface 수준을 유지한다. 결과 옵션이 실제 App request에 연결되지
않은 채 화면에만 존재하는 상태를 금지한다. locale별 label, 빈 field, 준비·취소,
복사, 페이지 전환을 같은 typed result로 테스트한다.

2026-09-13 통합 소스의 집중 확인에서는 JS 74개, TypeScript 계약 3개 및 실제
CLI 라우팅 테스트 6개가 통과했다. 전체 집합 복사, lazy minimum continuation,
Build 집계, 500ms replay 및 3개 locale 계약을 포함한다. 이는 native-C process,
브라우저 실제 탐색, 배포 Discord까지 포함한 전체 parity 완료와 구분한다.
재현 절차와 초기 의존성 누락의 해결은
[surface 검증 기록](research/v081-surface-verification-2026-09-13.md)에 남긴다.

### 4.13 v0.8.1 정확성·성능 gate

정확성 gate:

- `l=1..6`, 빈/비어 있지 않은 초기 field, hold on/off, fixed queue/pattern을 포함한다.
- 모든 지원 kick profile에서 filter off/on의 normalized candidate family,
  coverage, minimum cardinality와 canonical first set이 같다.
- 작은 target은 가능한 board/piece multiset을 exhaustive하게 열거한다.

- vertical, M4, checkerboard, APDP를 각각 단독/조합 on/off해 false negative를 찾는다.
- same occupancy의 여러 legal placement/replay identity가 의도치 않게 합쳐지지 않는다.
- lazy tie의 앞 두 페이지를 eager reference와 비교하고 취소·resume·stale cursor를
  검증한다.
- 1/2/N-1/N worker의 최종 결과와 canonical 순서가 같다.

성능 gate는 표본 수뿐 아니라 표본 종류를 확보한다.

- 줄 수 1~6
- 초기 field의 밀도, hole, component, column-demand 형태
- piece 수와 queue/pattern branching
- 전체 해법, minimum, score-minimals, replay, Build probability
- SRS, SRS+, SRS-X, Jstris-180, no-kick
- desktop/mobile-class core 수와 1/2/N-1/N worker
- cold compile, warm catalog, cold/warm WASM

대표 회귀 입력 `ctk3_w0kCQBjwwAMPPAD37g / P7 / 4L /
Jstris-180`의 알려진 minimum cardinality 25는 사후 assertion으로만 쓴다.
25를 solver hint나 종료 조건으로 주입하지 않는다. median 하나가 아니라 phase별
wall time, p95, visited nodes, pruned nodes, bytes transferred, worker tail,
peak memory를 기록한다.

기능 정확성이 통과해도 느려진 후보는 기본 off로 둘 수 있다. 반대로 빠른 한 번의
측정만으로 승격하지 않는다. 성능 threshold는 동일 장치·동일 artifact의 ABBA와
confidence interval로 판단하고, release gate 자체는 불안정한 절대 시간 하나에
의존하지 않는다.

## 5. v0.9.0 PC4 Online Tablebase

### 5.1 핵심 의미 교정

v0.9.0은 V* optimal recommendation 제품이 아니다. muse918의
`tetris-4lpc-mdp-vstar-policy`에서 policy/value layer는 ZXCL-PC가 최선의
한 action을 고르는 데 사용할 수 있지만, 그 사실이 graph에 최적 해법 하나만
있다는 뜻은 아니다.

graph는 모델 domain의 `source field + piece`에 대한 모든 outgoing field
transition edge를 제공한다. v0.9.0은 policy 하나를 따르지 않고 모든 outgoing
edge를 순회해 인증된 1~4L PC terminal에 도달하는 전체 graph-level solution
family를 구한다.
V*, policy recommendation, optimal action UI·CLI·Discord 명령은 범위에서 제외하고
관련 value/policy 자산을 제품 경로에서 읽지 않는다.

v0.9.0의 검색 권위로 허용하는 데이터는 다음 둘뿐이다.

1. profile·generation·target별 완결성이 인증된 all-outgoing `graph.bin` 계열
2. 그 graph 또는 Clearra offline exact PC 탐색을 끝까지 실행해 만든, 동일한
   완결성 manifest에 결박된 전체 PC 해법 집합

두 번째 형태도 한 최선 수나 policy cache가 아니라 complete candidate family다.
V*, value, policy, Krylov state는 candidate 생성·prune·정렬·tie-break·확률·Setup
판정 어느 단계에도 참여하지 않는다. dormant future seam의 타입이 저장소에
존재하더라도 v0.9.0 Cargo/product dependency graph, capability registry, command,
network discovery와 runtime I/O에서 도달할 수 없어야 한다.

다만 다음 둘을 구분한다.

- graph-level completeness: 주어진 모델 domain과 queue/hold 조건에서 모든 outgoing
  state transition path
- Clearra product completeness: concrete rotation, x/y, kick/ILC realization,
  replay와 기존 duplicate semantics를 보존한 모든 해법

첫 번째만으로 두 번째가 자동 증명되지 않는다. v0.9.0의 가장 중요한 구현·자격
과제는 §5.5의 exact materialization이다.

각 field ID의 adjacency 위치를 index로 찾는 것은 상수 또는 logarithmic Range
조회로 만들 수 있지만, 전체 해법 나열 자체는 O(1)이 아니다. 시간과 출력은 방문한
graph edge 및 반환 solution 수에 비례하는 output-sensitive traversal이다.
UI에 O(1) 전체 열거라고 설명하지 않는다.

### 5.2 지원 범위

- field/graph 높이 domain: 정규화 뒤 최대 4줄
- PC 목표 줄 수: 1~4L 중 해당 profile·generation·target의 terminal과 graph
  completeness가 별도로 인증된 값. `PC4`라는 이름만으로 짧은 목표를 추론하지 않음
- 규칙 목표: SRS, SRS+, SRS-X, Jstris-180, no-kick. 다섯 profile은
  독립적으로 자격·활성화하며, 한 generation에서 일부만 사용 가능해도 자격을
  끝낸 profile은 먼저 제공할 수 있다.
- 입력: 정규화 가능한 field, hold/current/preview 또는 fixed queue/pattern
- 출력: 기존 PC full-solution typed result와 동일한 concrete solution family
- 소비 reducer: 전체 해법, coverage/probability, minimum, score-minimals, replay
- 표면: CLI, GUI(Web/Desktop), Discord

4L을 넘는 PC, target별 terminal completeness가 인증되지 않은 1~4L 요청,
인증되지 않은 field, unknown rule, 지원하지 않는 spin/setup 의미는
TB miss 또는 unsupported다. graph에 field가 없다는 사실을 일반적인
`해법 없음` 증명으로 확대하지 않는다.

### 5.3 데이터셋과 현재 알려진 자산

대상 저장소는
[muse918/tetris-4lpc-mdp-vstar-policy](https://huggingface.co/datasets/muse918/tetris-4lpc-mdp-vstar-policy)다.
전체 용량이 매우 크므로 앱이나 CI가 전체 snapshot을 다운로드하지 않는다.

현재 알려진 graph 후보에는 `graph.bin`, `graph_no180.bin`,
`graph_nokick.bin`, `graph_srsplus.bin`, `graph_srsx.bin`과 shared
`graph_offsets.u32.bin`, `field_hash_to_id.v1.bin`이 있다. 파일 이름만 보고
다섯 rule profile의 의미, field ordering 또는 index 호환성을 추측하지 않는다.

특히 관찰된 graph target encoding이 동일하지 않을 수 있고 SRS-X 후보는 다른
width를 사용할 가능성이 있다. shared offset/hash index가 어느 graph generation과
field order에 결박됐는지 upstream provenance가 없으면 재사용하지 않는다.

`field_hash_to_id`의 hash는 암호학적 hash가 아니라 복원 가능한 10×4 점유
비트맵이고, 이 인덱스의 역할은 비트맵에서 graph node ID를 찾는 것이다.
관측 generation의 항목 수는 15,185,706개이며, 817,740개의 layer-0 V* 상태와
혼동하지 않는다. `graph_offsets`는 각 node의 가변 길이 graph 레코드에 대한
바이트 시작 주소 N+1개(마지막은 EOF)다. ID i의 레코드는
`graph[offsets[i]..offsets[i+1]]`이고, 피스별 모든 다음 node를 읽는다.
graph의 edge 자체가 배치 좌표나 완성 해법 하나는 아니므로 기존 materializer와
전체 경로 순회가 필요하다. 이 의미 복원에 V*·policy·Krylov 조회는 사용하지 않는다.

2026-09-12 moving `main` 재감사에서는 위 graph/index 파일들이 dataset tree에
존재했지만 README의 `graph.bin, not included here` 설명과 실제 tree가 서로
어긋나 있었다. README가 loader spec으로 연결한
[muse918/zxcl-pc-jstris-tbp](https://github.com/muse918/zxcl-pc-jstris-tbp)의
`docs/DATA.md`도 해당 시점의 전체 repository tree에는 존재하지 않았고, 그
저장소의 `src/graph.rs`는 README상 실제 bot이 사용하지 않는 stub이다. 따라서
파일 존재나 링크 문구를 record-layout 자격 증거로 승격하지 않는다. 이 관찰에
사용한 moving revision·LFS digest를 프로그램 상수나 영구 manifest로 복사하지
않고, 매 generation discovery가 새로 해석한 뒤 §5.4 자격 절차를 통과시킨다.

같은 감사에서 moving ref를 먼저 immutable revision으로 해석한 뒤 두 helper
index의 0~15 byte만 Range 조회했을 때 `206 Partial Content`, 정확한 전체 길이,
`FHIDIDX1`/`GOFFIDX1`, version 1과 같은 field count를 확인했다. 이는 현재 순수
reader의 helper-container 경계를 뒷받침하지만, shared index와 각 graph/profile의
generation 결박이나 graph record layout을 증명하지는 않는다.

2026-09-13 소스 및 bounded Range 교차 검증에서 shared index는 `graph.bin`의
세 표본 ID와 EOF에 일치했지만 다른 네 graph에는 일치하지 않았다. SRS-X의
첫 네 레코드는 u32 LE target으로 해석할 때 정상적인 hash 순서를 보였다.
`no180 = SRS`는 사용자 지정 profile 매핑으로 채택하되, 실제 kick 동일성과
완결성 자격은 별도 검증한다. 상세 형식과 검증 한계는
[인덱스 의미 복원 기록](research/pc4-index-semantics-2026-09-13.md)에 남긴다.

### 5.4 로컬 증거 복원과 fail-closed 자격

추가 답변을 기다리지 않고 공개 소스, 제한된 실제 바이트 조회, 독립적인 로컬
차등 검증으로 다음 의미와 계약을 복원한다. upstream의 직접 답변 자체를 필수
선행 조건으로 두지 않되, v0.9.0 production 활성화 전에는 각 지원 profile에 대해
다음 항목의 재현 가능한 증거가 필요하다. 일부 표본 성공을 전체 완결성으로
승격하지 않는다.

- profile 이름과 정확한 kick/rotation/180 규칙 identity
- graph file format version, integer width, endianness와 record layout
- field canonicalization/hash/ID ordering
- per-field adjacency offset index와 hash-to-ID index
- graph, 두 index, format spec가 같은 generation임을 증명하는 binding
- layer/domain 범위와 graph completeness 한계
- 작은 source/piece/edges/terminal known-answer vectors
- license와 redistribution/direct-Range 허용 범위

한 profile의 index를 다른 profile에 대입하지 않는다. 위 정보가 없거나 모순되면
해당 profile만 `not_qualified`로 남는다. 적어도 한 profile이 전체 자격을 끝냈다면
v0.9.0 generation은 그 profile 집합으로 활성화할 수 있고, 나머지는 CLI/GUI/Discord
capability와 Setup admission에서 명시적으로 비활성화한다. 미자격 profile의 요청을
다른 graph나 기존 beta에 무음 전달하지 않으며, typed 안내와 명시 offline fallback만
제공한다. 후속 v0.9.x에서 새 profile 자격이 닫힐 때마다 같은 generation 절차로
독립 추가한다.

Clearra가 별도 HF auxiliary dataset, 대체 public index 또는 778GB mirror를 만들지
않는다. 로컬에서 생성한 임시 index를 production dependency, 릴리스 artifact,
정답 권위로 승격하지 않는다. 테스트는 synthetic fixture와 upstream KAT의 작은
Range만 사용한다.

### 5.5 graph edge에서 exact placement/replay materialization

graph edge가 보존하는 것은 source field, 현재 piece, target field transition이다.
일반적으로 edge 자체에는 다음 정보가 충분히 들어 있지 않을 수 있다.

- concrete rotation과 x/y
- 어떤 kick test가 성공했는지
- lock 전 이동/input sequence
- line-clear가 여러 realization에서 발생하는 정확한 순서
- 같은 source/target으로 접히는 서로 다른 legal placement
- Clearra canonical candidate ID와 duplicate equivalence

`Pc4SolutionMaterializer`는 selected rule의 Clearra ILC/placement generator로
source field와 piece에서 가능한 concrete placement를 열거하고, line clear 뒤
정규화된 target field가 edge target과 정확히 같은 항목을 모두 찾는다.

- 0개면 graph/profile/canonicalization 불일치이므로 `data_invalid`
- 1개면 그 concrete identity를 보존
- 여러 개면 기존 PC duplicate 계약에 따라 distinct identity를 모두 보존
- UI 편의를 위해 임의로 가장 작은 하나만 남기지 않음
- replay input sequence가 graph에서 복원되지 않으면 Clearra의 규칙별 reachability
  witness를 생성하고 그 provenance를 명시

전체 graph path는 각 edge의 concrete alternatives의 곱을 lazy하게 전개한다.
중간 state만 같다는 이유로 서로 다른 placement/replay solution을 잃지 않되,
기존 product가 같은 것으로 정의한 항목만 공통 canonical reducer에서 합친다.

upstream KAT와 Clearra offline exact solver의 작은 exhaustive corpus에서
source/target adjacency 및 materialized candidate set이 일치하기 전에는
`full solutions` capability를 공개하지 않는다.

### 5.6 독립 모듈과 SRP

온라인 TB는 v0.8.1의 정적 베타 전역 installer에 네트워크 로직을 추가하지 않는다.
다음 책임을 분리한다.

| Owner | 책임 |
| --- | --- |
| `clearra-pc4-tablebase` 또는 동등한 순수 crate | manifest/schema, bounded binary parser, graph/index lookup state machine |
| `clearra-core-executor` | rule별 ILC/reachability와 exact edge materialization |
| `clearra-app` | TB request/session port, fallback 결정, cancellation, reducer 연결 |
| `clearra-cli` | native Range/local-file adapter와 프로필별 명시 다운로드·관리 UX |
| `clearra-gui-host` | Desktop bridge와 typed DTO |
| `apps/clearra-web` | browser Worker Range/local-file adapter, 프로필별 OPFS 수명, bounded cache와 progress |
| `apps/clearra-discord-bot` | interaction UX, light lookup 호출과 no-heavy-hit routing |
| release/ops | upstream discovery, qualification, signed generation manifest와 rollout |

순수 reader는 HTTP, browser API, filesystem 또는 Discord를 알지 않는다.
`Pc4LookupMachine`은 `NeedRange`, `Complete`, `Miss`, `Error`,
`Cancelled` step만 반환한다. `clearra-app`의 session owner가 generation,
request ID, stale response와 fallback을 관리한다.

기존 동기 `AppContext::run` 안에서 network fetch를 시작하지 않는다. host adapter가
typed `NeedRange`를 받아 비동기로 bytes를 공급하고, supplied bytes가
session/generation/artifact/offset/length와 정확히 일치할 때만 parser가 소비한다.

### 5.7 mutable upstream과 immutable generation manifest

제품 코드, Cargo/JS 상수, release tag 또는 계획 문서에 HF dataset commit SHA나
asset SHA256을 영구 고정하지 않는다. `main`의 새 업데이트를 매 요청마다
무검증으로 따라가지도 않는다.

두 identity를 분리한다.

- discovery identity: dataset repository와 update channel. mutable upstream을
  관찰하기 위한 설정이며 특정 revision을 코드에 박지 않는다.
- activation generation identity: 한 번 자격 심사를 통과한 resolved revision,
  profile별 artifact, byte length, format/index binding, content digest/ETag,
  KAT version과 compatibility schema를 담은 immutable signed manifest.

content digest는 그 generation의 전송 무결성을 검증하는 manifest 데이터이지
프로그램에 박힌 영구 dataset SHA가 아니다. upstream 변경은 기존 manifest를
수정하지 않고 새 `generation_id`를 만든다. 한 session은 시작한 generation에
끝까지 결박되고 중간에 `main`의 새 bytes로 바뀌지 않는다.

manifest resolver가 새 upstream revision을 발견해도 자동 활성화하지 않는다.
qualification CI가 활성화 후보인 각 profile의 format, index, KAT, differential,
Range와 성능 gate를 독립적으로 통과시킨 뒤 rollout pointer만 원자적으로
변경한다. 다섯 availability slot을 모두 기록하되, 미자격 slot은 명시
`not_qualified`이고 활성 profile의 자격을 막지 않는다. app version과 dataset
generation version은 별도다.

### 5.8 Range reader와 cache

기본 온라인 lookup은 필요한 header, hash-index probe, 두 offset 및 adjacency
slice만 HTTP Range로 읽는다. 사용자 명시 전체 다운로드는 아래 5.8.1의 독립
경로이며 일반 Range 요청의 `200` 응답 허용이나 자동 prefetch를 뜻하지 않는다.

- `206 Partial Content`, `Content-Range`, byte length와 manifest identity를 검증
- server가 전체 파일 `200`으로 반환하면 대형 body를 수용하지 않고 중단
- request별 최대 byte 수, session 총 byte 수와 동시 요청 수를 제한
- short read, overlapping/mismatched range, `416`, `429`, timeout을 typed error로 변환
- retry는 같은 immutable generation과 request ID의 bounded backoff만 허용
- range fragment cache는 `generation/profile/artifact/offset/length`로 key
- host 전송 계층은 현재 읽기 요청이 닿는 16KiB 창만 가져와 재사용할 수 있다.
  같은 창의 동시 요청은 하나로 합치며, 소비자에게는 요청한 정확한 바이트만
  반환한다. 작은 파일은 정확한 Range를 유지하고 전체 파일로 확장하지 않는다.
  동시 HTTP는 4개, 캐시는 8MiB/2,048항목, 작업당 총 전송 예약은 64MiB로
  제한한다. 창을 미리 순회하거나 관련 없는 graph 전체를 가져오지 않는다.
- old generation cache를 새 generation 결과에 사용하지 않음
- 이미 알고 있는 복수 byte demand는 같은 artifact/identity 안에서만 합친다.
  최대 512 demand, 한 전송 64KiB, 사이 간격 기본 1KiB/상한 4KiB를 유지하며
  원래 순서와 정확한 slice를 반환한다. 자격 확인은 headers -> index 표본 ->
  records의 의존 단계별로 묶는다. 아직 모르는 graph frontier를 미리 순회하지 않는다.
- ordinal field ID 및 Hydra source-hash prefix가 자격 확인된 경우, by-ID 조회는
  GOFF와 graph의 big-endian 40-bit source hash를 사용해 중복 FHID 읽기를 생략한다.
  미자격/opaque graph는 기존 경로를 유지하고 짧은 record는 typed format error다.
- GUI는 현재 요청과 결과 page에 필요한 부분만 lazy-load
- 전체 graph/policy/value layer를 background prefetch하지 않음

Web은 browser worker에서 HF로 직접 Range 요청한다. 이는 Clearra 계산 서버 호출이
아니지만 온라인 외부 데이터 접근이므로 사용자가 tablebase를 명시적으로 켠 뒤에만
시작한다. Desktop/CLI는 같은 machine의 native Range adapter를 사용한다.

### 5.8.1 프로필별 명시 전체 다운로드와 로컬 조회

사용자 선택으로 필요한 graph와 두 index의 전체 파일을 로컬에 저장할 수 있다.
이는 약 778GB 전체 dataset이나 V*/policy/Krylov 다운로드가 아니다. 2026-09-13
관찰에서 Jstris 180은 graph 510,917,451B + FHID 121,485,664B + GOFF
60,742,844B = **693,145,959B(약 661MiB)**다. 이 숫자는 관찰값이며 제품 상수는
아니다. 실행 때 resolved revision의 길이와 digest를 읽는다.

- CLI `tablebase <check|download|status|remove> --profile PROFILE`에서 profile을
  필수로 받는다. `srs`, `srs-plus`, `srs-x`, `jstris-180`, `no-kick`을 구분한다.
- GUI는 접힌 다운로드 영역에서 다섯 프로필을 개별 표시한다. 선택한 프로필의
  저장 상태·용량 확인·명시 다운로드·취소·삭제를 제공한다. 다른 프로필로 바꾸면
  이전 용량 확인과 다운로드 대상을 초기화한다. 미자격 항목도 숨기지 않는다.
- 현재 reader로 확인된 Jstris 180만 활성화한다. 다른 프로필은 별도 graph와
  전용 index/형식/완료 근거가 갖춰진 후 별도로 활성화하며 Jstris index를 빌려
  쓰지 않는다. 모든 프로필을 한꺼번에 내려받는 기본 동작은 없다.
- 실제 다운로드 직전 사용자에게 총 byte 수를 보인다. `check`나 옵션을 펴는
  것만으로 전체 파일을 받지 않는다. 세 파일의 전체 GET은 명시 경로만 수행하고,
  읽기/쓰기/증분 SHA-256은 stream으로 처리해 693MB 배열을 만들지 않는다.
- hash는 generation별 전송 무결성 값이다. 새 upstream을 수용할 수 있도록
  코드에 영구 SHA256을 고정하지 않는다. 모든 파일의 크기와 digest가 맞기 전에는
  새 저장본을 활성화하지 않는다. 실패·취소는 기존 저장본을 유지한다.
- 저장 공간은 프로필별 active 1개 + 업데이트 중 staging 1개다. 성공 후 기존
  generation을 정리한다. 게시 후 정리만 실패하면 새 저장 성공/정리 대기를 별도
  표시하며 이전 데이터가 유지됐다고 잘못 안내하지 않는다. 다음 관리 작업이
  해당 프로필의 남은 임시 generation만 다시 정리한다.
- GUI는 origin-private OPFS를 사용한다. Pages/4194 및 다른 브라우저와 공유하지
  않으며 브라우저 quota에 따른 오류·삭제를 지원한다. 전용 Worker가 hash/I/O를
  맡고 다른 탭의 탐색 lease가 있으면 업데이트·삭제를 거부한다. lock 해제 완료를
  확인한 뒤 작업을 반환한다. CLI는 OS file lock과 프로필별 저장 경로를 사용한다.
- 다운로드한 데이터 조회는 기존 App/Core의 같은 machine과 reducer를 사용한다.
  파일 offset read/Blob slice는 별도 `verified-local-file` admission으로 넣고
  HTTP 206을 가장하지 않는다. revision/profile/artifact/range/budget 검증은 같다.
  로컬 조회 bytes와 HTTP bytes/요청 수를 관측에서 분리한다.
- 저장된 TB 사용은 `offline-exact` fallback이 아니다. 파일이 없거나 프로필이
  맞지 않을 때 다른 규칙 데이터나 offline solver로 조용히 대체하지 않는다.
- v0.9 통합 브랜치 CLI 기본 feature는 새 로컬 host를 사용한다. native HTTP
  Range, Desktop 저장 UI 및 Discord adapter 완료는 별도 잔여 gate다. 프로필별
  다운로드 관리 구현만으로 v0.9.0 전체 릴리스 완료를 선언하지 않는다.

구현 및 소유 모듈/검증 근거는
[명시 다운로드와 Discord 배치 검토](research/pc4-explicit-download-and-host-placement-2026-09-13.md)에 둔다.

### 5.9 queue, pattern, hold와 bag UX

네이티브 CLI의 후속 연결에서는 명시 `--tablebase` 요청에 대해 같은 프로필의
설치 파일을 우선하고, 설치 데이터가 없는 경우에만 해당 immutable HF generation의
부분 조회를 사용한다. 로컬 데이터 손상/사용 중/다른 프로필을 온라인 또는 오프라인
우회 조건으로 쓰지 않는다. 파일과 HTTP는 같은 형식 검사·App 실행기를 공유한다.
세부 소유자와 검증 범위는 [네이티브 연결 기록](research/pc4-explicit-download-and-host-placement-2026-09-13.md#native-online-continuation-implementation-checkpoint)에 남긴다.
이는 전체 CLI/Web/Desktop/Discord parity 또는 release gate 완료가 아니다.

fixed queue가 완전히 주어졌다면 bag 정보를 추가로 묻지 않는다. hold/current/preview도
명시 입력에서 정규화한다.

원본 pattern 식만으로 유한 큐 집합과 분포가 완전히 정의되면 추가 bag 정보를
묻지 않는다. 그 밖의 hidden reveal 분포에 bag remainder가 필요하고,
provenance로 유일하게 추론할 수 없으면 다음처럼 처리한다.

- GUI: 필요한 이유와 남은 piece 선택 UI 제공
- interactive CLI: prompt 허용
- noninteractive CLI: 명시 `--bag-remaining` 없으면 typed input error
- Discord: modal로 사용자에게 piece remainder만 질문

raw qid, 내부 bag round 또는 임의의 reveal 순서를 사용자에게 요구하지 않는다.
pattern은 모든 concrete queue를 먼저 펼쳐 메모리에 담지 않고
`graph state x hold x bag multiset x preview position` DP로 합성한다.
최종 concrete solution path는 사용자가 page/export를 요구할 때 lazy하게 전개한다.

구현 체크포인트로 concrete fixed queue의 hold 상태기계는 pattern/bag DP와 분리한다.

안에서 전수 전개하고 replay용 hold 결정을 보존한다. 동일 current/hold 교환은 하나의
semantic branch로 정규화하며, supplied queue가 끝난 뒤 보이지 않은 active piece를
가정해 held piece를 꺼내지 않는다. 이 순수 출력은 qualified fixed-queue graph
traversal의 입력일 뿐 hit나 solution 권위가 아니다.

또 다른 구현 체크포인트로 bag multiset의 1회 draw 전이는 별도 순수 상태기계로
분리한다. 이 층은 arbitrary multiplicity profile, 정확한 remainder, bag epoch를
소유하고, canonical distinct piece별 `multiplicity / denominator`와 다음 상태만
낸다. 빈 remainder에서만 profile로 refill하고 epoch를 checked increment한다.
이는 preview 관측 정책, pattern parser, hold, graph lookup 또는 제품 capability가
아니며, 실제 `graph x hold x bag x preview` DP 완성을 의미하지 않는다.

그 위의 두 번째 순수 체크포인트는 exact remainder와 명시된 hidden draw 수를
입력받는 bounded lazy reveal family다. 모든 concrete sequence를 선할당하지 않고
suffix count를 유한 memo budget 안에서 계산한 뒤 canonical piece 순서의 rank를
bounded page로 unrank한다. 각 sequence는 refill/epoch가 반영된 terminal state와
checked-u128 reduced rational 확률을 보존한다. count/rank/memo/page allocation,
cancellation, cursor-family mismatch와 산술 overflow는 typed failure로 닫는다.
이 family 역시 이후 `graph x hold x bag x preview` DP의 입력일 뿐이며 hold,
preview 관측 정책, pattern 문법 또는 graph 조회를 추론하지 않는다.

### 5.10 Setup 적용 경계

PC4 graph를 일반 Setup tablebase라고 부르지 않는다. 1~4L Setup 탐색에 적용할
때는 목표 줄 수까지 자격 manifest에 결박하고 다음 두 층을 분리한다.

1. TB가 해당 profile·generation·target에 대해 인증된 complete PC concrete
   candidate family를 공급
2. 기존 Setup engine이 target shape, spin, score, buildability 조건을 평가

해당 Setup 모드에서 TB candidate family가 기존 offline candidate universe와
완전 동등하다는 differential proof가 있을 때만 acceleration capability를 켠다.
증명이 없는 Setup objective는 기존 offline solver를 유지한다. graph miss를
Setup 불가능 증명으로 사용하지 않고, 부분 candidate를 전체라고 표시하지 않는다.

구현 기반은 다음과 같이 좁혀 둔다.

- App admission은 request/profile/초기 필드/4L target/objective/exact generation과
  `SetupSearch` 자격을 묶은 differential proof 없이는 complete family를 Core로 넘기지
  않는다. proof를 일반 product caller가 임의로 생성할 수 없게 한다.
- Core ingress는 candidate canonical 순서, 초기 필드, 깊이, piece multiset, target cell과
  active ILC catalog membership을 재검증한다. 최초 geometry root family만 후보로 seed하고
  후속 residual은 기존 exact compiler가 담당한다. 기존 Setup의 shape·spin·score·BuildUp·
  probability evaluator는 교체하지 않는다.
- candidate-injected graph는 일반 Setup cache에 저장하지 않는다. 같은 query 문자열이라도
  generation/proof가 다른 결과와 섞이지 않게 하기 위함이다.
- 현재 Setup engine의 실제 지원 경계인 empty 10x4/4L만 실행 ingress에 열어 둔다. 1~3L
  manifest 타입 지원이나 향후 non-empty scenario를 이 구현이 지원한다고 확대 해석하지
  않는다.

profile별 실제 `SetupSearch` completeness 자격과 offline differential proof가 아직 없으므로
위 경로는 제품 capability를 켜지 않는 fail-closed 기반이다. 첫 활성화 전에는 다음 A/B를
통과해야 한다.

1. 동일 query/profile/kick/generation/worker/memory/time budget에서 양쪽이 완료되면 exact
   result digest, candidate/coverage count와 오류 분류가 같아야 한다.
2. wall time, first result, geometry/residual nodes, peak RSS를 구간별로 기록한다.
3. offline이 정해진 자원 안에 완료되지 않지만 자격된 TB complete family와 기존 Setup
   evaluator가 완료하면 `feasibility dominance`로만 기록한다. 무한 배속이나 수치 speedup을
   만들지 않는다.
4. 기존 IOTS 29.1초/35.68초와 broad fixture 1,519.58초 기록은 TB on/off 동일 입력이
   아니므로 baseline 참고값일 뿐 A/B 증거로 재사용하지 않는다.

Setup 성능 receipt에는 exact source SHA, query digest, profile, immutable generation,
worker/CPU/memory/time budget, 양쪽 terminal state, result digest, candidate/coverage count,
first-result/wall/nodes/peak RSS가 모두 있어야 한다. 기존 기록에는 이 동일 입력 쌍이 없으므로
현재 수치 A/B는 `없음`으로 유지한다. 향후 offline이 고정 예산에서 typed resource-limit 또는
timeout으로 끝나고 자격된 TB 경로가 exact 완료한 최초 순간부터만 feasibility dominance를
기록한다.

2026-09-20 현재 generation capability는 `pc_search_target_lines`와
`setup_search_target_lines`를 별도 필드로 운반한다. upstream 선언과 bounded Range
표본은 reader-ready 자격만 만든다. 13개 omitted transition은 비게시 exact oracle에서
dead 13/live 0/unknown 0으로 닫혔지만, generation-bound exact outgoing-edge,
known-answer, offline parity receipt가 아직 없으므로 현재 Jstris 세대의 두 target 목록은
모두 비어 있다. 해당 exact receipt가 들어오면 PC Search 4L만 독립적으로 열 수 있고,
SetupSearch는 별도의 differential receipt 전까지 계속 비어 있다. GUI는 사용자의 opt-in으로
generation discovery와 handshake를 먼저 시작할 수 있지만, loading이 끝난 뒤 exact
profile/4L Setup capability가 없으면 실행을 막고 unavailable을 표시한다. CLI는
`setup_pc_acceleration_not_qualified`로 명시 실패하고, WASM도 명시 요청에 snapshot이 없으면
`pc4_online_generation_unavailable`로 닫혀 오프라인 Setup으로 하강하지 않는다. 이 경계는 새 세대가 독립
SetupSearch 자격을 갖추면 같은 필드를 통해 열 수 있지만, PC Search 자격만으로는 열리지
않는다.

같은 입력 A/B용 `clearra.pc4.setup-ab-receipt.v1` 검증기도 추가했다. 양쪽 completed arm의
result digest와 candidate/coverage count가 일치할 때만 exact parity/activation evidence로
분류한다. offline timeout 또는 resource-limit과 TB complete의 조합은 feasibility
dominance로만 분류하며 제품 활성화 권한이 없다. online transport는 compute 전 prewarm을,
local transport는 HTTP 수치 0을 각각 강제한다. 실제 profile별 Setup proof와 A/B는 여전히
미완료다.

### 5.11 hit, miss, offline과 한도 처리

공통 결과 상태:

- `hit`: 인증된 domain에서 complete materialization 성공
- `miss`: 인증된 lookup에 상태 없음. 일반적 unsatisfiable 증명은 아님
- `not_qualified`: profile/manifest/index 자격 없음
- `offline` / `dataset_unavailable`
- `rate_limited`
- `snapshot_mismatch`
- `data_invalid`
- `cancelled`

fallback은 명시적이다.

- CLI는 별도 `--offline-fallback` 또는 동등한 옵션이 없으면 offline exact
  search를 시작하지 않는다.
- GUI와 Discord는 실패 이유, 예상 로컬/Cloud 비용, `오프라인으로 계속`,
  `중단` 동작을 제공한다. 안내만으로 자동 계산을 시작하지 않는다.
- fallback을 선택하면 기존 exact CLI/App use case를 새 요청으로 실행하고
  TB partial result와 섞지 않는다.
- rate limit retry와 offline fallback을 구분한다.

Discord의 TB hit는 heavy PC Cloud Run job을 실행하지 않는다. gateway/light lookup이
Range machine과 materializer를 완료하고 typed result를 기존 presenter에 전달한다.
heavy fallback은 사용자의 별도 선택과 기존 job 정책을 거친다. trace와 테스트에서
hit당 heavy Cloud Run invocation이 0임을 증명한다.

#### 5.11.1 Discord graph 파일의 배치와 Oracle 보호 조건

Oracle 영구 저장소에 선택한 프로필 파일을 놓고, Gateway와 격리된 제한적 파일
조회 프로세스가 필요한 slice를 공급하는 방안을 우선 검증한다. graph는 header 없는
flat adjacency이므로 전체 hash map을 RAM에 만들지 않고 FHID 이진 탐색/GOFF
직접 seek/graph byte read로 조회할 수 있다. 조회가 작다는 것과 P7P4 전체 해법
열거·물리적 배치 복원·최소 집합 선택이 작다는 것은 다른 명제다.

- Gateway event loop에서 동기 graph traversal을 돌리지 않는다. 조회 프로세스의
  메모리/CPU/동시 요청/큐/byte budget과 I/O 우선순위를 별도로 제한한다.
- 캐시 cold/warm, 취소, 다운로드/교체와 요청 동시성, 디스크 부족에서 Gateway
  heartbeat 지연·명령 응답 p95/p99·RSS/CPU/IO를 기준선과 대조한다. 비간섭
  증거가 없으면 Oracle full-family 계산을 활성화하지 않는다.
- 작은 단일 node hit를 complete-family hit로 표기하지 않는다. 자원 한도는
  typed 한도 상태로 반환하며 사용자 선택 없이 heavy Cloud Run fallback하지 않는다.
- Cloud Run의 **읽기 전용 image data layer**에도 기술적으로 탑재할 수 있다.
  승인된 CLI 바이너리를 그대로 소비하고 프로필별 데이터 manifest/digest를
  별도 입력으로 포장한다. 데이터만 바뀌는 업데이트에 Rust 재빌드를 추가하지 않는다.
- Cloud Run 시작 때 writable filesystem으로 전체 파일을 받는 방식은 피한다.
  해당 파일시스템은 인스턴스 메모리를 소비하고 비영속적이므로 cold-start와 OOM
  비용이 생긴다. image layer도 실제 cold-start/RSS 비용을 확인하기 전에는
  성능 무손실로 판정하지 않는다.

이번 변경에서는 Oracle/Cloud Run 파일 설치·이미지 변경·트래픽 전환을 수행하지
않는다. 파일 배치 가능성은 확인하되 실제 서버 자원과 비간섭 실측은 다음 운영
검증이며, 기존 no-heavy-hit 계약과 순차 배포 권위는 유지한다.

### 5.12 기존 result reducer 연결

TB 전용 결과 화면과 별도 의미를 만들지 않는다. materialized concrete candidates를
기존 canonical PC result pipeline에 공급한다.

여기서 `전체 해법`은 기존 Core가 BuildUp·도달성·coverage를 검증한 표준 PC
all-solution family를 뜻한다. raw Geometry만 반환하고 BuildUp·coverage·probability를
명시적으로 실행하지 않는 `PcTilingFamilyV1`은 같은 이름으로 우회하지 않는다.
온라인 graph 후보를 Core의 precomputed-Geometry ingress로 넣은 뒤 기존 검증 spine을
끝까지 통과시키며, raw-Geometry 전용 제품을 가속하려면 별도의 의미·동등성 계약을
먼저 추가한다.

- 전체 해법: complete candidate family
- probability/coverage: 동일 pattern universe와 denominator
- minimum: v0.8.1 first-canonical + lazy ties
- score-minimals: score-only B안, attack 비개입
- replay: materialized reachability witness와 500ms GIF
- copy/pagination/i18n: 기존 surface projection

result에는 provider가 `online-pc4-tablebase`인지 `offline-exact`인지,
rule profile, generation identity와 completeness scope를 machine-readable
provenance로 포함한다. presenter는 불필요한 내부 manifest/hash를 기본 UI에
노출하지 않지만 진단 export에는 민감하지 않은 identity를 남긴다.

### 5.13 기존 정적 베타 제거 시점

`pc4-compact-exact-v12.bin`과 `CLR4TB12` 경로는 v0.8.1 동안 유지한다.
다음 조건을 모두 충족한 v0.9.0 migration 커밋에서만 제거한다.

1. 최초 활성 profile이 하나 이상이고 각 활성 profile의 독립 자격 완료
2. 각 활성 profile의 PC full-solution materialization parity 완료
3. CLI/GUI/Discord의 profile별 capability와 hit/miss/not-qualified/fallback gate 완료
4. 새 generation rollout과 rollback 절차 검증
5. v0.8.1 artifact로 전체 application rollback 가능

제거 범위에는 static asset, CLI `include_bytes!`, App global installer,
WASM asset loader, Docker copy, old test fixture와 beta UI 문구가 포함된다.
같은 `--tablebase` 옵션 아래 old/new provider를 무음 혼용하지 않는다.
persisted beta opt-in은 새 외부 HF 접근 동의로 자동 승계하지 않고 새 opt-in을 받는다.

v0.9 개발 브랜치에는 이 제거를 미리 적용한다. migration marker가 켜진 소스는
정적 자산, 전역 registry, CLI embed, Core exact-dead 가지치기, App session,
WASM ABI와 Discord image copy를 모두 거부한다. 이는 **소스 migration 완료**일 뿐
곧바로 배포 가능하다는 뜻은 아니다. 위 1~5 조건과 활성 generation 자격이 닫히지
않으면 v0.9 release gate는 계속 차단하며, 배포된 v0.8.1의 정적 베타 상태를
개발 브랜치 안에서 대체 권위로 다시 살리지 않는다.

### 5.14 n-PC/Krylov 후속 seam

후속 PC(n-PCs) 확률과 Krylov 상태 공간은 v0.9.0/v0.9.x 공개 기능에서 제외한다.
V* recommendation도 제외한다. 이 절의 seam은 컴파일 가능한 소유권 자리일 뿐,
현재 PC/TB/Setup 경로에서 호출하거나 데이터셋을 발견·조회하는 기능이 아니다.

SRP를 지키기 위해 다음 내부 port/type 자리만 둘 수 있다.

- `PcNextProbabilityPort`
- `PcKrylovSnapshotAdapter`
- 별도 probability request/result/error namespace

이 seam은 feature-off이며 CLI command, GUI control, Discord command,
capability registry, network discovery 또는 실제 HF read에 연결하지 않는다.
synthetic no-I/O contract test만 허용한다. upstream 답변과 별도 제품 계획 없이
placeholder가 현재 TB manifest나 graph reader를 오염시키지 않게 한다.

### 5.15 v0.9.0 구현 순서

1. 새 순수 tablebase crate/module과 no-I/O synthetic parser fixture를 만든다.
2. rule profile, format, artifact와 generation manifest typed schema를 정의한다.
3. resumable Range state machine, cancellation과 stale reply fence를 구현한다.
4. upstream이 제공한 profile·target별 terminal, index/spec/KAT를 qualification
   fixture로 연결한다.
5. graph all-outgoing-edge traversal을 fixed queue부터 구현한다.
6. exact placement/replay materializer와 offline differential을 통과한다.
7. hold와 pattern/bag DP를 추가하고 output을 lazy page한다.
8. 기존 PC reducer에 provider-neutral candidate stream으로 연결한다.
9. native CLI, browser worker, Desktop, Discord light adapter를 순서대로 연결한다.
10. miss/offline/rate-limit/fallback과 no-heavy-Cloud-Run-on-hit를 검증한다.
11. 자격 조건이 모두 닫힌 뒤 old beta 제거 migration을 수행한다.
12. 최종 exact SHA와 generation manifest로 전체 release gate를 실행한다.

upstream 자격이 늦어져도 1~3과 synthetic tests는 진행할 수 있다. 4 이후의
production activation과 completeness 주장은 대기한다.

### 5.16 v0.9.0 검증 gate

format/integrity:

- magic/version/endianness/width/overflow/short read fuzz
- U24/U32 등 profile별 실제 encoding KAT
- hash-to-ID와 offset index의 generation binding
- Range 206/200/416/429/timeout/stale generation
- 한 요청이나 CI가 전체 dataset을 받지 않는 byte-budget assertion

정확성:

- upstream known source/piece/edge vectors
- 활성화하는 각 profile의 small exhaustive source-field adjacency
- fixed queue/hold의 graph path와 offline exact candidate family 비교
- 같은 edge로 접히는 multiple placements와 replay identity 비교
- pattern/bag denominator와 coverage 비교
- full solutions, minimum, score-minimals, replay reducer parity
- graph miss가 false unsatisfiable로 표시되지 않는지 확인

surface/operation:

- CLI noninteractive fallback 금지와 explicit fallback
- GUI opt-in 전 network request 0, current page lazy Range
- Desktop와 Web의 normalized result parity
- Discord hit의 heavy Cloud Run invocation 0
- Discord miss/failure의 안내·중단·명시 fallback
- locale별 도움말에 V* 추천 또는 n-PC 확률이 노출되지 않음
- generation 전환 중 기존 session이 자기 manifest로 완료
- rollback pointer와 previous application artifact 복구

성능:

- cold header/index lookup, warm fragment lookup, traversal, materialization,
  reducer, render를 분리
- Range request 수/bytes, cache hit, visited states/edges와 output 수 기록
- offline exact 대비 hit latency 및 memory 비교
- 4L 전체 해법이 큰 경우 first page와 full export 시간을 분리

모든 gate는 provider source, app exact SHA, generation ID와 rule profile을 함께
기록한다.

## 6. v0.9.x dataset generation 갱신

v0.9.x는 이미 자격을 통과한 제품 계약 안에서 upstream dataset generation을
갱신하기 위한 릴리스다. mutable `main`을 앱이 즉시 소비하는 채널이 아니다.

### 6.1 갱신 절차

1. discovery가 새 upstream revision을 발견
2. 별도 candidate generation manifest 생성
3. profile별 format/index/provenance와 license 재검증
4. KAT와 offline differential 재실행
5. Range byte/latency 및 full materialization A/B
6. 기존 app version과 호환성 검사
7. canary pointer에서 관찰
8. production generation pointer 원자적 promote
9. previous N generation 유지

graph bytes나 index가 같아도 manifest identity와 qualification receipt를 비교한다.
검증 없는 content-addressed cache hit를 release 권위로 사용하지 않는다.

### 6.2 버전 판정

- 데이터만 바뀌고 schema, rule 의미, candidate/result 의미가 같으면 v0.9.x patch
- parser/manifest schema가 backward-compatible하게 확장되면 영향에 따라 patch
  또는 minor를 결정
- rule semantics, completeness scope, public command/result가 바뀌면 v0.9.x
  자동 갱신으로 처리하지 않고 새 기능 릴리스 계획을 만든다.
- generation manifest는 다섯 profile의 availability를 모두 명시하되, 각 profile의
  artifact/index/qualification binding은 독립 slot이다. 이미 자격을 통과한 profile은
  그 slot의 새 generation만 promote할 수 있고, 준비되지 않은 profile은 직전의
  qualified generation을 암묵적으로 끌어오지 않은 채 명시 `not_qualified`로 남긴다.
- 서로 다른 revision이나 generation의 graph/index/qualification receipt를 한 profile
  slot 안에서 조합하지 않는다. 여러 profile이 동시에 갱신되더라도 하나의 profile
  검증 실패가 다른 독립 profile의 성공을 취소할 필요는 없지만, 실패 profile을
  성공한 profile의 자산으로 대체해서는 안 된다.

failure 시 application을 재배포하지 않고 generation pointer를 직전 qualified
manifest로 되돌릴 수 있어야 한다. parser incompatibility가 원인이면 app artifact와
manifest를 함께 atomic rollback한다.

v1.0.0은 단순 버전 번호 변경이 아니라 다음 계약이 안정됐다는 선언이다.

## 8. CI, 릴리스와 롤백

### 8.1 테스트 계층

- 변경 파일 owner의 focused unit/contract test
- 수학 filter 및 parser의 bounded exhaustive/fuzz/differential
- Core/App/CLI integration
- Web/Desktop/Discord surface contract
- canonical release acceptance
- exact artifact를 사용하는 Pages/CLI/Discord deployment smoke

작은 문서·presenter 수정에 전체 성능 suite를 실행하지 않는다. Core 알고리즘,
manifest/parser, product contract 또는 release 후보 변경 시에는 전체 gate를
배포 직전에 한 번 실행한다. 동일 exact source의 WASM/CLI/Discord core artifact는
한 producer가 만들고 downstream shard가 hash와 receipt를 검증해 재사용한다.

### 8.2 Go/No-Go

v0.8.1 No-Go:

- filter off/on result 차이 또는 unknown false negative
- minimum cardinality/canonical first set 차이
- lazy tie 누락·중복·순서 불안정
- worker 1/N 결과 차이, deadlock, UI main-thread 정지
- CLI/GUI/Discord result 의미 차이
- 기존 기능의 유의한 p95/peak-memory 회귀

v0.9.0 No-Go(활성화하려는 각 profile에 적용):

- 해당 profile의 upstream format/index/provenance 부재
- graph completeness 범위 불명
- exact placement/replay materialization 불일치
- 전체 solution을 policy 하나로 축소
- runtime이 mutable upstream을 session 중 무검증 추종
- Range 대신 전체 dataset 다운로드
- miss를 unsatisfiable로 표시
- Discord hit에서 heavy Cloud Run 실행
- old/new TB의 무음 혼용
- 미자격 profile을 다른 profile의 graph/index 또는 자격으로 실행
- 자격 profile이 하나도 없는 generation의 활성화

### 8.3 배포 순서

1. clean accepted source SHA에서 build-once artifacts 생성
2. focused와 full acceptance receipt를 source/artifact hash에 결박
3. Pages와 CLI candidate 배포 및 smoke
4. Discord light/heavy routing candidate와 Oracle path proof
5. v0.9.0이면 candidate generation manifest canary
6. 단 한 번의 publish/promote 결정
7. 모든 surface readback 후 release tag와 immutable release 게시
8. 관찰 기간 동안 P0/P1 및 provider telemetry 점검

Cloud Run candidate tag나 release tag는 promote 성공 전 최종 버전 권위가 아니다.
실패한 candidate는 lease/generation 기준으로 정리하고, 이미 동작 중인 N개
qualified version과 충돌하지 않게 한다.

### 8.4 롤백

- v0.8.1: 직전 v0.8.0 app/artifact와 명령 registry로 rollback
- v0.9.0: 직전 app artifact(v0.8.1, old beta 포함)로 전체 rollback
- v0.9.x: 우선 generation pointer만 직전 qualified manifest로 rollback
- parser/application 불일치 시 app+manifest atomic rollback
- in-flight session은 old generation을 완료하거나 typed cancellation
- 새 요청만 rollback pointer를 사용

rollback 성공은 health endpoint 하나가 아니라 CLI/Pages/Discord의 대표 명령,
Range identity, provider provenance와 no-heavy-hit routing readback으로 확인한다.

중간 역방향 집합이 path domain보다 과도하게 커지는 경우에는 동등한 더 작은
증명으로 전환할 수 있다. 전체 indexed adjacency parity, 모든 indexed node의
root-reachable/terminal-co-reachable 판정, 그리고 모든 outside-index 경계
successor에 대한 layer DAG memoized dead proof를 같은 generation에 결박한다.
실제 root-to-terminal 경로가 index를 처음 벗어나는 edge는 반드시 이 경계 집합에
포함되므로, 경계 전체가 dead이고 indexed node에 extra가 없으면 domain 동등성이
성립한다. 이 방식도 전 shard exact cover와 별도 offline product-family parity를
요구하며, 표본 또는 기존 13개 negative oracle로 대체하지 않는다.

compact key 실행은 이전 cliff를 넘었지만 후속 nested-frontier admission에서
`268,435,592 > 268,435,456`, 즉 136B 초과로 다시 fail-closed했다. 당시 ready
작업은 63개뿐인데 캐시 응답이 한 field의 waiter를 전부 깨운 이력 때문에 deque가
128칸을 유지했다. wake-up은 이제 64-task resident window의 빈 슬롯만 옮기고
나머지는 이미 회계된 waiting owner에 둔다. 실행 폭과 해법은 그대로 유지하면서
사용하지 않는 doubled backing capacity만 금지하며, 후속 full-family parity 실행을
최종 판정으로 삼는다.

정적 베타 migration은 v0.9 marker와 함께 asset, Core compiler/registry, App/CLI
session, WASM ABI, browser runtime hook, Discord Docker copy를 제거했다. 집중 권위
validator와 Rust all-feature compile, Web toggle 수명 및 deployment-impact 검사가
통과했다. 활성 signed generation과 제품 release gate가 없으므로 배포 완료 표기는
아니다.

### v0.9.x 및 v1.0.0

- [ ] 새 generation마다 전체 qualification과 canary
- [x] previous N generation fail-operational registry/rollback 상태기계

- [x] n-PC/Krylov seam이 비활성·무 I/O 상태

모든 checkbox는 코드, 테스트, exact artifact 또는 production readback 중 해당
권위의 증거로 닫는다. 계획 문구, synthetic 성공, benchmark 한 번 또는 다른
규칙의 결과만으로 완료 처리하지 않는다.

위 `[x]` 가운데 `구현`, `경계`, `상태기계`, `local-only`로 한정한 항목은 현재
소스와 집중 테스트가 닫혔다는 뜻이다. 실제 HF profile 자격, signed generation,
제품 surface 활성화, 최종 exact-SHA acceptance·배포 권위를 대신하지 않는다.

bytes, KAT, Clearra materializer differential과 signed generation manifest로
자격을 심사한다.

### 2026-09-13 materializer 재감사

graph의 cleared-row bottom 정규화와 고정 ILC target frame을 동일시한 오류를
발견했다. 비최하단 행 삭제 시 기존 셀의 비트 위치가 이동하므로 source가
target의 부분집합이라는 검사는 유효한 전이를 거절한다. 이 때문에 위 materializer
완료 표기를 당시 다시 열었다. `Pc4RowFrame`의 경로별 원래 행 대응과 edge 역정규화,
공통 concrete path의 최종 identity 변환까지 연결했다. core 4개, TB 156개 및
App PC4 60개 테스트가 통과했다. 실제 upstream edge와 제품
reducer의 여러 삭제 이력 차등 검증 및 exact-oracle 후속 검증까지 끝낸 뒤
구현 완료 표기를 다시 닫았다. profile 전체 자격은 별도로 계속 열어 둔다.
상세: [행 좌표 회귀 기록](research/pc4-row-normalization-regression-2026-09-13.md).

실제 HF 비어 있지 않은 5개 상태의 전이 194개까지 forward lock/역복원 결과를
대조했다. 지우기 전이 11개와 비단조 좌표 전이 4개가 포함된다. 그래프 밖의
물리적 배치 170개 중 157개는 독립 negative completion 증거를 얻었지만,
13개는 당시 완전성 판정이 미해결이었다. 상태 5만 개의 검증 예산 소진은 실패
증명이 아니므로 canonical profile도 계속 미자격 상태로 두었다. 후속 exact oracle은
13개를 모두 dead로 닫았지만, 좁은 materializer 회귀 테스트와 generation 전체 profile
qualification을 같은 성공으로 취급하지 않는다.
상세: [비어 있지 않은 필드 차등 검증](research/pc4-hf-nonempty-differential-2026-09-13.md).

App의 public 입력 factory부터 Range 조회·여러 단계의 materializer·최종 reducer와
리플레이까지 연결하는 1~4L 합성 회귀 4개를 추가했다. 각 테스트는 다섯 typed
profile을 순회하며 윗줄 선삭제, graph ID와 탐색 순서의 불일치, 한 경로씩의
paging, 원래 필드 mask와 실제 replay 좌표의 분리를 확인한다. 로컬 core 7개는
통과했지만 TB 실행 파일과 compile-only App 확인의 build script가 Windows
애플리케이션 제어 정책으로 차단됐다. 새 App 테스트의 실행 성공은 아직 주장하지
않으며 비게시 Linux CI로 검증한다. 실제 HF의 profile·1~4L 완전성 자격과 위
13개 전이의 생존 가능성은 후속 비게시 exact oracle로 닫혔다. generation 전체
completeness와 나머지 profile/target 자격은 계속 열어 둔다.
상세: [App 다중 삭제 경로 계약](research/pc4-app-multi-clear-contracts-2026-09-13.md).
