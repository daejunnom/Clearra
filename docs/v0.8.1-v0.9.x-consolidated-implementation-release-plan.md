### 1.0 2026-09-27 실행 우선순위: v0.8.1 우선

사용자 지시에 따라 PC4 Tablebase의 v0.9.0 계산·I/O·병렬화 업그레이드는
일시 중단한다. 이미 작성된 코드와 증거 및 아래 v0.9.0/v0.9.x 미완료 대장은
보존하되 이번 v0.8.1 구현·검증 또는 배포 완료 범위에 합치지 않는다.

이번 작업은 다음 세 경계로 분리한다.

1. qualified legal-board와 조건부 도달성의 실제 호출 위치·중복 계산을 줄이는
   성능 개선. 자산 의미와 지원 domain은 변경하지 않는다.
2. worker별 할당의 소유권 추적: 변경 가능한 memo/frontier/언어 ID는 독립
   유지하고, immutable 요청 자료와 결과 병합의 불필요한 복사를 별도 평가한다.
   이전 compact-memo 후보는 성능 비회귀 증명 전까지 기본값으로 승격하지 않는다.
3. 나머지 v0.8.1 제품 lifecycle·surface/reducer parity·통합·검증·배포 경계.

다섯 profile의 이미 자격을 마친 자료를 변경 없이 다시 생성·전수 자격 검증하지
않는다. 변경된 계산·조회 경계의 집중 차분과 실제 성능·메모리 gate는 별도로
남긴다. WSL의 추가 사용·재구성, Windows 정책 우회 또는 실행 차단 표본을
완료 시간으로 해석하는 경로는 이번 작업에 포함하지 않는다.

이번 구조 수정·worker 소유권 판정·집중 검증과 남은 gate는
[`v081-accelerator-worker-product-closure-2026-09-27.md`](research/v081-accelerator-worker-product-closure-2026-09-27.md)에
별도로 기록한다. native ABBA와 실제 surface 검증 결과 전에는 성능·배포 상태를 닫지 않는다.

최신 main `7d7fc390b2f65d52ebf8362dff65dcbfcb6d481b` 위의 v0.8.1 선별 통합,
최신 제품 계약 보존 및 새 소스 검증/비게시 CI 범위는
[`v081-selective-integration-2026-09-27.md`](research/v081-selective-integration-2026-09-27.md)에
분리 기록한다. 원본의 v0.9.0 구현 이력과 과거 benchmark 권위는 이 통합으로 닫지 않는다.

### 1.0.1 후속 기능 완성 단계: native 도달성 owner

이번 단계에서는 벤치마크를 다음 단계로 미루고 소스·집중 검증을 진행한다.
native branch worker의 immutable reachability template·sky-entry를 요청별
공유 owner로 이동하고 representative 재검증도 같은 owner를 사용한다.
board-dependent cache와 scratch, worker/epoch-local union memo는 별도 유지한다.
프로필·크기 불일치 시 기존 정확 private 경로로 돌아간다. 결과와 새 메모리 영수증
계약 및 좁은 검증은 [native 도달성 owner 기록](research/v081-native-reachability-request-owner-2026-09-27.md)에
남긴다. 기존 스냅샷을 삭제하거나 과거 ABBA를 새 변경의 검증으로 승격하지 않는다.

이는 native 소유권 경계의 `Implemented`/집중 `Locally validated`이며 Web의
모든 verifier 공유, 실제 peak, 전체 surface/reducer parity 또는 release 완료가 아니다.
기존 다섯 profile 자료는 재생성하지 않고 v0.9.0의 미완료 항목도 보존한다.

### 1.0.2 후속 기능 완성 단계: Web 단일 relation owner와 bounded peer

조건부 pack의 전체 자료는 root WASM 한 곳에만 설치한다. 모든 Geometry verifier는
같은 qualified owner에서 파생된 작은 context seed와 크기가 제한된 레코드 캐시를
사용한다. cache miss는 기준 정확 탐색으로 즉시 돌아가며, 누적한 최대 64개 질의를
host yield 사이에 일괄 전송한다. 요청 도중 HTTP, 동기 대기, 전체 pack 복제 또는
교차 출처 격리를 위한 페이지 새로고침을 추가하지 않는다.

generation/rule/profile/서명 statement/전체 payload/proof identity와 세션을 고정한다.
초기 미설치는 fail-open, 적용 후 invalid reply는 현 결과와 기존 partial을 무효화한다.
캐시와 전송 버퍼를 함께 사전 예산에 넣고, 예산 부족으로 요청 worker 수를 낮추지
않는다. 각 peer의 optional 가속만 끄고 기준 정확 경로를 유지한다.

이 경계의 구현·집중 검증과 실제 WASM/surface 검증의 미완료 상태는
[Web relation peer 기록](research/v081-web-relation-peer-owner-2026-09-28.md)에 분리한다.
native/TypeScript 계약 통과를 실제 5-profile 브라우저 검증, OS peak, 성능 gate 또는
배포 완료로 확대하지 않는다. 아래 과거의 `첫 verifier 전체 pack` 기록은 당시 증거로
보존하되 현재 실행 구조는 이 절로 대체한다. 벤치마크와 v0.9.0 업그레이드는 계속 동결한다.

### 1.0.4 후속 기능 완성 단계: 실제 서명 pack의 peer/solver 합성

실제 다섯 qualified 조건부 pack을 재생성 없이 읽어 root owner와 bounded peer를
동일한 BuildUp 도달성 workspace에 연결한다. cold miss의 즉시 exact fallback,
warm reply 이후 Boolean/전체 lock-family 합성, 삭제 행 문맥 및 사후 손상 상태를
독립 primitive 탐색과 대조하는 집중 테스트를 추가했다.

실제 pack smoke에서 peer seed가 유효한 삭제 행 의존 마스크를 `InvalidWire`로
거절하는 회귀를 확인·수정했다. 점유 가능 범위는 surviving physical rows지만,
의존 셀 범위는 원래 target-sized collision frame의 known-empty cells도 포함한다.
둘을 구분하며 점유의 범위·generation·checksum·profile 검증은 완화하지 않는다.
자산 바이트와 서명 catalog는 변경하지 않았다.

[서명 pack 합성 검증 기록](research/v081-signed-pack-peer-composition-2026-09-28.md)에
560개 작은 profile/context/board 사례의 좁은 증거와 감독·lint 미완료 경계를 남긴다.
비게시 CI도 이미 컴파일한 Core 테스트를 재사용해 같은 immutable 자료를 읽는다.
이는 자료 재자격, 실제 여러 WASM realm의 browser smoke, 제품 전체 candidate/reducer
parity, active-session peak 또는 release 완료가 아니다. 벤치마크와 v0.9.0은 동결한다.

### 1.0.5 후속 기능 완성 단계: 실제 App reducer·확률·replay 동등성

이전 소스 `108a4387`의 비게시 CI 네 작업 성공을 확인했다. 그 증거와 새 검증을
분리하여, 작은 production App/Core 요청을 가속기 네 가지 on/off 조합으로 실행한다.
1~6L 최소 해법, score-minimals, Build 커버 확률, PC chance 및 줄 삭제를 포함한
전체 replay witness의 semantic candidate/coverage/canonical/probability 결과를 대조한다.
synthetic Core 결과나 local-search-ab 전역 정책으로 제품 실행을 대체하지 않는다.

자산 없는 exact fallback 40개 실행과 실제 SRS+ signed legal-board/relation pair를
설치한 40개 실행이 각각 집중 테스트로 통과했다. 최소 해법의 request policy가 실제
Core session snapshot까지 도달하고, 실행 전후 generation identity가 유지되며,
remove 뒤 active identity가 사라지는 것도 확인한다. 기존 qualified 자료를 재사용한다.

[실제 App 결과 검증 기록](research/v081-real-app-accelerator-result-parity-2026-09-28.md)에
작은 입력·서명 admission·감독 경고와 좁은 완료 권위를 남긴다. 비게시 CI는 동일
product-policy integration target을 재사용해 일반/signed smoke를 실행한다. 이것은
전체 profile/worker/초기 필드의 candidate universe, lazy tie·copy/page, 실제 세 surface
readback, relation hit/prune 효과, peak·성능 또는 release 완료가 아니다. 해당 경계들은
계속 Open이며 벤치마크와 v0.9.0은 동결한다.

### 1.0.6 후속 기능 완성 단계: 실제 lazy 최소 집합의 UI·복사 경계

기준 소스 `e4eef736`의 비게시 CI 네 작업 성공을 확인했다. 다음 단계는 실제
공통 command ingress와 production WASM runtime/App/Core에서 나온 작은 PC·Build
최소 집합을 browser JSON과 기존 UI validator/exporter까지 연결하는 기능 검증이다.
빈 2L `IIOOO`의 네 동률 집합은 canonical 첫 집합만 먼저 응답하고 후속 집합을

재조회도 최초 페이지와 복사 payload를 그대로 복원한다. Build의 두 필수 member는
대표 해법 하나로 줄이지 않고 현재 선택 집합 전체로 복사한다.

두 입력을 가속기 네 on/off 조합으로 실행한 실제 8개 요청의 key·순서·복사 의미가
동일했다. Rust가 생성한 managed 자료를 지정한 UI 소비자도 skip 없이 통과했다.
자산 미설치의 exact fallback 기능 검증이며 실제 100-member solver 집합,
여러 WASM realm, 가속 hit/prune 또는 병렬 성능 증거가 아니다.

[실제 페이지·UI 복사 검증 기록](research/v081-real-portfolio-ui-wire-parity-2026-09-28.md)에
입력, 감독의 정상 테스트 영수증/컴파일 drain 경고 및 좁은 검증 범위를 남긴다.
비게시 CI는 exact source/run/attempt의 JSON 파일 하나를 producer에서 별도 UI
consumer로 전달하고 Rust 재컴파일이나 기존 독립 surfaces job의 대기를 추가하지 않는다.
기존 adaptive State-major 기본값은 유지한다. 전체 surface/worker parity, signed
asset의 실제 browser 실행, strict lint, peak·성능 및 release는 계속 Open이며
벤치마크와 v0.9.0 업그레이드는 동결한다.

### 1.0.7 후속 기능 완성 단계: 실제 WASM owner·bounded peer realm

기준 Rust source `83cb5fdb`의 비게시 CI 다섯 작업 성공을 확인했다. 일반 제품
WASM의 compile-source snapshot·바이트 해시·실제 응답 runtime identity를 검증하고
owner 하나와 독립 linear memory의 실제 Node peer 두 개에서 기존 다섯 signed
relation pack을 사용했다. full pack은 owner 하나에만 설치하고 peer에는 bounded
seed/query/reply를 전달했다. 작은 기존 6미노 P7 입력의 47개 정상 요청과 2개
취소에서 전체 identity 순서·집합 digest·coverage·해법별 확률이 일치했다.

각 profile에서 실제 query/reply가 발생했으며 cold exact fallback, import 뒤
재실행, 제거 뒤 재실행을 대조했다. 취소는 실제 제품 controller와 같은
cancel→drain으로 scope 해제를 확인했다. 각 realm은 1-worker solver 요청이므로
이 기능 증거를 11-worker 성능, relation hit rate 또는 실제 공유 peak로 해석하지
않는다. Node realm은 실제 browser의 worker entrypoint/pool/broker/OPFS 검증을
대신하지 않는다. browser 연결 도구의 초기 kernel asset 오류로 그 경계는 Open이다.

[실제 WASM realm 검증 기록](research/v081-real-wasm-owner-peer-smoke-2026-09-28.md)에
다섯 profile 관측값과 정상 기능 테스트 영수증을 남긴다. WASM 컴파일·staging은
완료했지만 넓은 관리기 snapshot의 테스트 입력이 빌드 중 변경되어 cache seed
봉인이 거절된 실패 영수증도 따로 보존한다. source guard를 완화하거나 그 파일을
캐시·릴리스 권위로 사용하지 않는다. 새 비게시 CI의 독립 `wasm-realms` job은
변경 없는 checkout에서 일반 WASM을 한 번 빌드해 같은 검증을 실행한다.
벤치마크, 자산 재생성·전수 재자격, v0.9.0 업그레이드와 main 배포는 계속 제외한다.

### 1.0.8 후속 기능 완성 단계: 실제 legal synopsis와 native compute-data

기준 소스 `12f8587e`의 비게시 CI 여섯 작업 모두 성공을 확인했다. 변경 없는
ordinary WASM과 다섯 signed legal-board에서 full-owner 하나 및 독립 memory의
두 실제 peer를 연결했다. peer는 256KiB 이하 negative-only synopsis만 받는다.
eligible empty 4L와 out-of-scope 2L·초기 필드 1L/4L에서 전체 identity·coverage·
확률 parity를 확인하고, 잘못된 profile·손상 admission 거절과 제거·취소 뒤
정확 경로 복귀도 대조했다. legal 검사만 97개 정상 탐색·2개 취소·20개 기대된

현재 checked-in legal-board와 조건부 도달성 catalog는 각각 다섯 profile의
서명 자격 상태다. 자료 전용 fail-closed gate는 두 catalog의 모든 슬롯과
서명 metadata의 제품별·profile별 상한을 통과했다. 그러나 실제 active-session
peak, 성능 채택, CLI·Web·Desktop·Discord 제품 readback 및 앱 exact-SHA
acceptance는 남아 있으므로 v0.8.1 앱 릴리스는 여전히 **No-Go**다.
과거 `BoardConditionedReachability` pack은 `spawn-to-lock` sparse record로,
계획의 실제 entry→first-exit 국소 관계가 아니었다. 현재 제품 parser와
composer는 `CLLR0002` 실제 entry→first-exit 경계로 교체됐으며 게이트는
`ActualEntryToFirstExit` 의미 계약을 확인한다. 그러나 이 검사는 실제
자산의 완전성 증명이 아니다. 다섯 legal-board는 별도 F/R/L source chain과
서명된 실제 파일을 검증해 자격을 얻었고, 최종 앱 SHA·세 surface
acceptance는 추가로 필요하다. 문자열 또는 enum 값 변경만으로 완료
처리해서는 안 된다.
새 `CLLR0002` 로컬 후보는 pack 단독 파싱에서 멈추지 않고 catalog의
schema, profile/rule, generation, 전체 pack digest, query·감사 레코드
수를 함께 읽는 상태 경계를 갖췄다. SRS+의 실제 221바이트 pack과
962바이트 catalog를 CLI가 함께 재조회해 `structurally_valid_unqualified`,
`qualified=false`, `installed=false`로 출력했다. 한 파일만 있거나 서로
다른 generation이면 활성화가 아니라 불완전/무효 후보로 남는다. 원본
query 집합의 digest는 source 파일 없이 재계산할 수 없고, 구조 검증은
전역 진입 pose의 도달성·profile 전체 완전성·제품 성능을 증명하지 않는다.
`CLLR0002`의 로드 후 context 인덱스는 같은 레코드/entry pose를 복제하던
`BTreeMap` 대신 정렬된 레코드 범위로 변경했다. loader의 canonical 순서,
충돌 조건 거부와 context별 hit/miss의 집중 테스트는 통과했고, 알려진 Rust
allocation의 논리적 resident bytes를 별도로 보고한다. allocator·프로세스
overhead를 포함한 128MiB active-session peak와 실제 속도 채택은 아직
실측하지 않았다. 새 CLI 실행 파일은 이 환경의 Windows 앱 제어 정책
`os error 4551`로 두 번 차단돼 변경 후 실제 CLI process 재조회는 미완이다.
라이브러리 집중 테스트는 별도 통과했으며 정책 우회나 무제한 재시도는 하지 않는다.

삭제하지 않았다. 2026-09-23 추가 재고에서 별도 과거 작업트리의

정책 로드에서 그 목록 외 추가를 거절한다. 특히 새 entry/first-exit 생성기와

staging 실패 시 임시 archive를 정리한다. 셸/manifest 계약 테스트 17개와
SHA `13f02eb7`의 비게시 CI에서 Rust manager 빌드·workspace 타입 검사·

storage audit까지 통과했지만, 등록된 WSL 확인은 `Clearra-Build` 배포판 부재로
실패했다. 실제 WSL 생성·archive 전달은 아직 검증되지 않았다.
이 source 경계와 선택 질의 후보는 release provenance나 완전 domain 자격이
아니다. 실제 생성 전에는 archive 입력과 정확한 생성 SHA를 다시 확인한다.
이 작업트리의 `AGENTS.md`는 Rust `tools/clearra-manage`를 활성 관리기로
정하므로, 존재하지 않는 역사적 Python 관리기를 대체 실행하거나 raw WSL로
관리기를 우회하지 않는다.

`F_k` 생성기의 층 파일 읽기는 원본 파일 전체 바이트와 파싱된 `u64` 상태 벡터를
동시에 보유하던 경계에서 순차 해시·검증·파싱으로 변경했다. 이 변경은 해당
중복 버퍼를 없앤다. 또한 전방 생성의 worker별 전체 `BTreeSet`을 1,024개
source 상태 단위로 제한하고, input·filter digest에 결박된 임시 run을 재개·병합해
최종 집합을 정확히 중복 제거하도록 변경했다. 다만 큰 `F_k` 자체와 중간
disk peak, 32-run 병합 시 한 그룹의 일시적 벡터 문제를 해결했다는 뜻은
아니다. Wirelyre의 정방향 그래프는
isolated-cell 및 split 조건을 사용하지만, Clearra는 중간 행 삭제가 가능한
물리 보드·원행 codec을 사용한다. 동일 prune의 안전성이 증명되기 전에는
특히 음성 판정에 이를 이식하지 않는다. 전방 spill의 기능 검증과 실제 다섯
profile 생성·공간 계측은 계속 `Open`이다.

전방·후방 pair run을 최대 32개씩 줄이는 병합 단계가 결과 전체를 `Vec`에
올린 뒤 파일로 다시 쓰던 경계는 입력 reader와 1 MiB writer만 유지하는
스트리밍 병합으로 바꿨다. 출력 count·digest는 파일 헤더에 뒤늦게 기록하고,
완전 기록·동기화 뒤 기존 파일을 덮어쓰지 않는 동일 디렉터리 게시를 한다.
중복 pair, 정렬 및 digest round-trip 테스트를 소스에 추가했다. 이어서 최종
전방 병합도 정렬된 필드를 domain 파일에 바로 쓰도록 변경하고, count를 확정한
후 헤더와 전체 파일 digest를 완성하는 경계를 추가했다. 기존 직접 작성 파일과
바이트 단위 동등성, 재개, 잘못 정렬된 결과의 게시 거부 테스트를 소스에
추가했다. 제품 생성에서 쓰는 필터 없는 전방 `F_k → F_(k+1)` 단계는 입력
파일을 먼저 전수 검증해 digest를 고정하고, 두 번째 순차 읽기에서 bounded
source chunk를 생성한 뒤 digest를 다시 대조한다. 따라서 이 단계는 입력과
출력 `F_k`의 전체 상태 벡터를 동시에 또는 각각 적재하지 않는다. 후방 `R_k`
생성과 `L_k` 역추적의 최종 검증 결과도 bounded checkpoint에서 domain
writer로 바로 전달해 전체 출력 벡터를 제거했다. 직접 작성 파일과의 바이트
동등성 테스트를 소스에 추가했으나 실행하지 못했다. 역사적 필터 적용 전방
단계와 `L_k` 역추적의 목표 층은 아직 전체 입력 벡터를 적재한다. `L_k`의
`F_k` membership은 검증된 정렬 파일의 순차 커서로 바꾸고, 전역 pair-run
병합 후 한 번의 exact 교집합에서 판정한다. 입력 전체의 재검증 digest가
일치해야만 결과를 게시한다. 이 초기 버전은 `F_k`에서 탈락할 원시
predecessor도 pair run에 먼저 기록해 중간 디스크 피크를 키울 수 있었다.
후술한 Bloom 후보는 이 지점만 줄이며 exact 커서 검증을 제거하지 않는다.
생성기 전체의 메모리·공간 한도 해결로 판정하지 않는다.
후보 bundle 게시 때에도 각 `L_k`의 complete `F_k`/`R_k` 부분집합 검사는
두 파일의 정렬 커서로 수행한다. 인코더는 같은 불변 포맷을 유지하면서
`L_0…L_10`을 층별 검증 방문자로 받아 전체 층 벡터의 동시 보유를 제거했다.
기존 인코더와의 바이트 단위 동등성 테스트는 소스에 추가했지만 실행 전이다.
압축 결과 자체는 최대 64 MiB 메모리에 보유하며, `Arc` 변환·parser index까지
포함한 생성 시 순간 peak와 active-session 공유 128 MiB는 실측 전이다.
Rust 실행·실제 프로필 검증 전이므로 자격 상태는
계속 `Open`이다. 집중 테스트의 Windows 최초 실행과 한 번의 수동 재시도는
모두 `generic-array` build script가 애플리케이션 제어 정책 `os error 4551`로
차단돼 테스트 본문까지 도달하지 못했다. 자동 반복이나 WSL 우회는 하지 않았다.

후보 생성은 양방향 정확 교집합으로 변경했다. 초기 후보는 6피스 층에서
만나도록 했으나, 실제 SRS+의 `F_4`가 13,299,035개임을 확인한 뒤
무제한 정방향 frontier를 한 층 줄이는 **5피스 meet 후보**로 바꿨다.
즉 완전한 `F_0…F_5`, 완전한 `R_10…R_6`을 독립 생성하고,
`L_5 = F_5 ∩ Pre(R_6)`을 exact ILC로 계산한다. 아래층은
`L_k = F_k ∩ Pre(L_{k+1})`, 위층은 `L_{k+1} = Post(L_k) ∩ R_{k+1}`로
만든다. 후자는 `F_{k+1}` 전체 생성이 아니다. 두 등식은 `F`·`R`의
전이 정의에서 귀납적으로 따르며, 행 삭제를 포함한 같은 exact edge 관계를
양방향에서 사용해야만 성립한다. 후보 bundle 게시 직전에는 각 `L_k`의
source·filter 파일 digest가 이 전방·후방 점화식의 이웃 층과 정확히 이어지는지
검사한다. 기존 `forward-reachable-layer-07…10`은
역사적 중간물로 남겨도 새 bundle 체인에는 쓰지 않는다. 초기 6피스 meet
후보의 소스와 국소 관계 차분은 SHA `c292fcc8`의 비게시 CI에서 컴파일·집중
테스트를 통과했고, 그 바이너리로 SRS+ `F_0…F_5`까지 생성했다. 이후
5피스 meet 소스로 `R_6`와 `L_5`까지 진행했으나 최종 bundle과 다섯
프로필 자격은 아직 검증 전이다. 어느 쪽도 `Qualified`가 아니다.
후속 SHA `df42e7a1`의 비게시 Windows·Linux 관리 게이트는 통과했고,
그 정확한 Windows 후보 생성기를 로컬에 확보했다. SRS+ 단일 프로필의
중간 층은 `F_5` 151,891,476개(층 파일 약 1.13 GiB), `R_7`
2,022,317개, `R_6` 52,918,372개(약 0.39 GiB)까지 생성·재읽기
검증했다. `R_6` 생성은 약 1억 5,429만 서로 다른 기하 후보를 exact ILC로
확인해야 했고, 중간 작업 공간은 약 9 GiB까지 증가했다. 이는 생성기 진행
증거일 뿐 다섯 프로필 또는 크기·성능 자격의 완료가 아니다.
다음 `F_5 ∩ Pre(R_6)`은 원래 모든 원시 predecessor를 pair run에 먼저
기록했다. 이를 완전 검증한 `F_5` 파일에서 구성하는 최대 128 MiB의
no-false-negative Bloom semi-join 후보로 줄이고, 최종 승인 여부는 여전히
정렬된 `F_5` 커서와 exact ILC에 맡기도록 소스를 변경했다. 이전 spill과
섞이지 않도록 체크포인트 identity도 바꿨다.
Bloom이 거르는 `L_5` 전용 pair-run 청크는 512개에서 4,096개 target으로
늘렸다. 이 변경은 일반 역방향 층의 청크 크기를 바꾸지 않고 체크포인트
파일 수를 줄인다. SHA `077560db`의 비게시 Windows·Linux 관리 게이트와
Bloom no-false-negative·청크 경계 exact 차분 테스트가 통과했다. 그 exact
Windows 생성기로 SRS+ `L_5` 6,830,860개를 생성하고 재읽기 검증했다.
이 층에서 34,558,011개의 `F_5` 생존 후보 쌍을 exact ILC로 확인했고,

`L_6` 4,796,285개, `L_7` 754,994개, `L_8` 19,412개,

역방향 source 검증은 종전의 전체 목표 열거·정렬·벡터 변환 대신
충돌 없는 기하학적 배치에서 입력 층으로 이어질 수 있는 잠금 위치를 먼저
모은다. 이 집합이 비면 BFS를 생략하고, 비어 있지 않으면 같은 exact

기존 reachability 경계가 보존되는지 집중 테스트를 통과했다. 다만
기하학적 목표 전부에 대한 추가 차분 테스트의 로컬 실행은 Windows
애플리케이션 제어가 새 테스트 실행 파일을 두 번 차단했다. 대신 exact SHA
`d064841a2e7ac24cf2106b667f23809e313b5ba6`의 브랜치 전용 비게시 CI
run `35837283321`에서 해당 차분, 막힌 지붕의 음성 판정, Hydra hash
교차 검사와 기존 reachability 테스트가 모두 통과했다. 이 CI는 source
contract 증거이지 실제 전체 자산 자격이나 release acceptance가 아니다. 당시
SRS 생성 프로세스는 변경 전 실행 파일로 진행했으므로 이 수정은
완료한 층을 덮어쓰지 않고 다음 재개·프로필 생성에만 적용한다. 자산
완전성이나 성능 자격을 이 소스 테스트만으로 부여하지 않는다.
입력 역방향 목표 층에 대한 소형 Bloom admission을 검증 배치 전체에서
재사용하도록 소스를 추가했다. 필터가 음성인 기하학적 목표는 sorted-domain
이진 검색을 건너뛰되, 양성은 반드시 원래의 exact 이진 검색으로 확인한다.
허위 음성은 허용하지 않으며 속도 이득은 후속 동일 바이너리 A/B 전까지
주장하지 않는다. 이전 SRS 실행 파일에는 이 수정이 적용되지 않는다.
source SHA `c1c57cc676cf9930b38154ff032278855c9c4d3f`의 비게시
accelerator CI run `35839641030`과 management CI run `35839641002`는
모두 성공했다. 이 성공은 target admission과 국소 relation의 source

새 bundle에서 누락 identity의 실제 graph 경로 모든 상태가

음성 필터의 양성은 자격 증명이 아니라 단순 통과이며, false positive는
prune 기회만 놓칠 뿐 결과 집합을 바꾸지 않아야 한다.
그 후보는 완전 검증된 bundle payload를 로드할 때 layer별 64비트
block Bloom을 만들고, BuildUp의 음성 판정에서는 단일 word만 조회한다.
정확한 membership을 요구하는 진단·자격 API는 기존 압축 bundle
lookup을 유지한다. Bloom 거짓 양성을 강제로 만들어도 정확 API가
`VerifiedAbsent`를 반환하는 테스트와 삽입 키 전체의 no-false-negative
bounded 테스트가 통과했다. 이것은 구현·집중 검증 상태이며 실제
P7P4 시간·메모리·동일 identity KAT 전에는 성능 자격을 부여하지 않는다.

별도의 SHA `e216c8eb` 11-worker baseline-only 계측은 약 82초에서
메모리 압박으로 중단됐다. 이는 완료 시간이 아니며 외삽하지 않는다.
종료 시 process-tree peak는 약 6.78 GB, host 물리 여유는 약 500 MB였고

142.17초 기록은 다른 Chrome/WSL 환경과 과거 SHA라 현재 11-worker
결과로 취급하지 않는다. 선별한 4/7/11-worker 동일 binary 단일 탐색,
실제 CPU 사용량, 단계별 시간과 memory receipt를 기록하되 압박 표본은
censored로 남긴다. 두 최종 후보 bundle은 이미 각각 약 25 MB로 로컬에
저장돼 있어 검색 지연을 곧바로 자료 저장 불능으로 해석하지 않는다.
같은 `e216c8eb` 바이너리의 7-worker baseline-only 실측은 142.708초,
456,923개와 기준 해시 `cts1:98ebe8726537b29f`였고 요청한 7워커가
모두 활성으로 보고됐다. 이는 7-worker의 현 호스트 단일 완료 표본이며
과거 11-worker 약 2분 기록과 동등 조건 비교나 속도 채택 증거가 아니다.
층별 임의 유한 그래프 1,000개에서 양방향 점화식과 전체 `F∩R`의 집합 일치를
확인한 것은 수학적 계약의 보조 검사에 불과하며, 실제 kick/ILC 차분 테스트나
다섯 profile 자격 증거를 대신하지 않는다.

조건부 도달성의 현 pack은 전체 board와 profile sky seed에 대한 sparse Boolean
spawn-to-lock cache이며, 계획의 임의 진입 pose·국소 입출구 macro·witness 관계를
대신하지 않는다. 독립 primitive BFS는 다섯 profile의 ordered kick을 원시 shape
충돌로 해석하여 작은 보드의 장애물 0~2개 조합 및 10폭 1~6높이 표본과 최적화
탐색을 비교하도록 추가했다. local-only 후보 생성기는 입력 query set의 모든
레코드를 이 기준 탐색과 다시 대조하고 불일치 시 게시 전에 실패한다. Windows
수동 재시도에서 두 bounded 차분 테스트와 생성기의 다섯 profile 선택 레코드
대조 테스트가 통과했다. 그러나 query set 밖의 완전성은 증명하지 못했으므로 이 코드나 기존
생성기 결과를 실제 pack의 `Qualified` 증거로 승격하지 않는다.
후보 생성기의 query 파일은 읽기 전에 실제 일반 파일·크기 한도를 확인하고,
기존 출력이 link 또는 다른 내용이면 거절한다. 후보 pack/catalog 게시에는
기존 파일을 덮어쓰지 않는 동일 디렉터리 hard-link 게시를 사용한다. 이는
local-only 파일 수명 보강이지 국소 relation 구현이나 signed release 게시의
증거가 아니다.

국소 relation의 다음 차분 검증을 위해 독립 primitive BFS에 실제 진입 pose
집합을 명시하는 경로를 추가했다. 잘못되거나 충돌하는 진입 pose는 빈 도달
집합으로 조용히 바꾸지 않고 질의 오류로 돌려보낸다. 최적화된 템플릿 BFS에도
동일 시작 pose를 사용하는 테스트 경로를 두고 다섯 profile·일곱 미노를
대조하도록 했다. 이 경로는 전체 물리 보드의 정확 탐색일 뿐 창 밖 우회가
불가능하다는 증명이 아니다. 이후 동일 최적화 탐색을 `derive_exact_conditioned_entry_lock_anchors`라는
공개된 전체 보드 primitive로 승격했다. 빈·유효하지 않은 entry 집합은 완결 음성 판정이
아닌 `None`으로 돌려주고, 다중 entry 집합의 독립 BFS 대조 테스트를 추가했다.
`derive_exact_conditioned_local_relation`에는 전체 물리 보드의 충돌·first-success
결정을 사용하되 탐색을 pose 창으로 제한하고, 최초 창 밖 상태를 모두 출구로 기록하는
entry→exit/lock 원시 관계도 추가했다. 창 밖 우회 후 재진입은 출구를 기존 전체 보드
탐색에 합성해야 보존되므로 출구가 남은 국소 음성 결과만으로 전역 불가능을 선언하지 않는다.
독립 BFS와 국소 lock + 출구 후속 lock의 합이 일치하는 다섯 profile 테스트를 추가했다.
현재 원시 관계에는 창 안의 모든 유효 source pose, translation/grounding target 및
first-success의 **모든 선행 킥 후보**가 읽는 셀을 보수적으로 합친 의존 마스크도
추가했다. 동일 규칙·창·진입 집합에서 마스크상의 점유가 같을 때만 in-process
재사용을 허용하고, 마스크 밖 단일 셀 변이에서 결과가 같은지 대조하는 테스트를
추가했다. 이는 충분조건인 보수적 서명이며 작은 pack이나 높은 적중률의 증거는 아니다.
또한 원시 shape 셀·ordered kick을 직접 해석하는 독립 국소 BFS를 별도 모듈로
구현하여, 단순한 최종 lock 합집합뿐 아니라 창의 **첫 출구 집합 자체**를
다섯 profile·일곱 미노·상단 장애물 표본에서 비교하도록 했다. 생성기에 연결할
qualification oracle의 소스 후보이지, 아직 실행된 차분 증거는 아니다.
별도 `LocalRelationCandidateIndex`는 profile·미노·좌표창·진입 집합을 묶어
in-process 후보 관계를 조회하며, 같은 질의에 겹치는 점유 조건이 서로 다른
lock/exit를 반환하면 설치 전에 거절한다. 이 인덱스 자체는 충돌 검출용
비권위 후보이며, 당시에는 제품 registry 또는 BuildUp hit 경로가 아니었다.
별도 `CLLR0002` 후보 바이너리에는
profile별 규칙 fingerprint, payload·generation digest, 정렬된 가변 길이 관계와
16MiB 파일 상한을 묶고, 파서는 길이·중복·충돌을 거절한다. BuildUp의
고정 목표 높이와 삭제된 원래 행 mask를 `LocalRelationRowFrame`으로 분리해
같은 compact physical board라도 다른 원행 대응이면 후보를 재사용하지
않는다. 기존 4L `OriginalRowFrame`의 자격을 1~6L로 암묵 전파하지 않는다. 구형 sparse
spawn-to-lock `CLBR0001`과 parser/namespace를 혼용하지 않는다. 다섯 profile의
라운드트립·손상·세대 불일치 테스트와 `qualification-reference` 전용
레코드 감사 코드를 추가했다. 감사 코드는 raw shape·ordered kick으로 모든
창 내부 source 및 이동/킥 후보의 충돌 의존 셀을 독립 재구성하고, 저장된
source-board lock·첫 exit를 원시 BFS와 대조한다. 이는 저장된 후보 레코드의
오류를 검출하는 단계이며, 모든 가능한 창·진입·보드의 완전성 또는 전역
BuildUp 합성의 정확성을 증명하지 않는다. 현재 소스에서
`conditioned_local` 11개와 독립 `reachability::reference_tests` 10개 Rust
집중 테스트를 실행해 모두 통과했다. 서명된 product authority, 실제 압축
크기·메모리 측정과 제품 설치는 이 시점에는 `Open`이었다.
국소 관계를 dependency mask가 같은 다른 board에 재사용할 때 출구 후속
탐색을 저장된 원본이 아닌 실제 질의 board에서 수행하도록 수정하고,
독립 primitive BFS와 다시 대조했다. exact SHA `fba6b209`의 비게시
accelerator CI `35847950029`와 management CI `35847950020`이
통과했다. 이는 후보 소스의 재사용 정확성 증거이지 제품 pack 자격이 아니다.
local-only 후보 생성기의 파일 경로도 작은 SRS+ 질의로 실행했다. 독립
레코드 감사, `candidate_unqualified` 표시, 동일 입력 재실행의 byte identity,
다른 내용의 immutable 출력 덮어쓰기 거절을 검증했다. 이 검증은 프로필
전체 query domain의 완전성이나 실제 제품 pack 자격을 대신하지 않는다.
CLI의 기존 `reachability-pack generate`는 구형 sparse spawn-to-lock 후보로
유지하고, 새 entry/first-exit 포맷은 명시적

두 후보의 상태·삭제 경로도 별도 파일명으로 표시한다. CLI와 qualifier의
집중 테스트 및 SRS+ 한 질의의 221바이트 실제 생성·재조회에서 새 후보는
`structurally_valid_unqualified`, 제품 catalog는 `not_qualified`, 설치는
`false`였다. 이 CLI 연결은 작은 개발용 후보 수명주기일 뿐, 서명 자산
설치나 BuildUp 가속 활성화가 아니다.
재사용 가능한
결정 DAG, 16MiB 이하의 소형 조건부 relation pack, 임의 entry의 제품
가속 활성화와 witness/스핀 증거는 여전히 `Open`이다.
2026-09-24에는 선택 레코드의 정확성과 선언된 보드 조건의 완전 커버를
분리하는 bounded symbolic 판정기를 추가했다. 고정된 실제 entry pose의
점유 셀과 삭제로 존재하지 않는 물리 행은 영으로 고정한 뒤, 각 레코드의
`board & dependency_mask == dependency_occupancy` 조건들이 선언된
단일 context/domain을 전부 덮는지 비트별 분기로 증명한다. 불완전하면
반례 보드를, 증명 예산을 소진하면 `Inconclusive`를 반환한다. 독립 primitive
레코드 감사는 pack당 한 번만 실행한다. 별도 `prove` 명령은 이 결과를
immutable `bounded_context_coverage_only` 보고서로 남기며 서명 또는
profile 전체 자격으로 승격하지 않는다. 8비트 전수 진리표와 소형 실제
레코드의 집중 테스트가 통과했지만, 다섯 profile의 유용한 완전 domain,
16MiB pack, 성능 gate 및 제품 배포는 계속 `Open`이다.
이후 자산을 읽지 않는 구조 계측으로 현재 BuildUp의 full-sky 창

benchmark나 기존 profile 해법 차분의 재검증이 아니다. 이 과거 계측은
sky 창에 한정되고, 새 전체 높이·상단 절반 창의 pack 크기나
도메인 커버율을 입증하지 않는다. 최악 문맥의 모든
점유를 압축 없이 1:1 평면 레코드로 전개하면 `2^30`개가 되어 16MiB 한도에
맞지 않는다. 같은 결과를 공유하는 점유가 얼마나 되는지는 아직 검증되지
않았다. 따라서 broad-domain 제품 pack은 창/entry의 분해 또는 공유
decision DAG로 조건을 압축해야 하며, 좁은 단일 문맥의 커버 보고서만으로
다섯 profile 자격을 선언하지 않는다.

후속 소스 변경에서는 위의 **모든 정적 pose** 30비트 상한을 그대로 각
레코드의 조건으로 쓰지 않고, 실제로 도달한 pose에서 출발하는 이동·접지·
순서 있는 모든 킥 후보의 충돌 셀만 합친다. 이 집합 밖의 보드 변화는
도달 집합의 어느 상태에서도 나가는 간선을 바꾸지 못하고, 미도달 상태가
새로 도달하려면 먼저 그 간선 중 하나가 바뀌어야 하므로 관계 결과가
동일하다는 귀납적 충분조건이다. 독립 원시 shape·킥 감사도 같은 도달 집합을
별도로 계산해 저장 마스크를 대조한다. No-kick T와 180 킥을 쓰는 SRS-X J의
선별된 1L 조건에서 정적 마스크보다 엄격히 작은 조건이 실제로 나왔고,
그 조건에 맞는 10비트 보드 전체의 lock·첫 출구가 동일한 집중 테스트가
통과했다. 이는 `Implemented`/`Locally validated`인 조건 축소 증거일 뿐,
4L의 조건 DAG 크기, 다섯 profile 완결성, 16MiB pack·128MiB 세션 한도,
성능 채택 또는 서명 자격을 증명하지 않는다.
작은 선언 도메인을 자동으로 덮는 local-only 후보 함수도 추가했다. 기존
레코드의 독립 감사와 symbolic coverage proof가 돌려준 실제 반례 보드에서
새 관계를 만들고, record/증명 예산 안에서 완전 커버가 나올 때까지 반복한다.
No-kick T의 1L 한 문맥에서는 생성된 pack이 10비트 보드 전체를 덮고,
각 보드의 직접 탐색 결과와 일치했다. 반례가 남으면 한도를 넘겨도 성공으로
처리하지 않는다. proof 분기 빈도의 65,536레코드 `u16` overflow도 제거했다.
기존 명시 `generate-local-candidate --queries` 파일 경로는 이제
`cover-set.v1` 선언 도메인도 받아 반례 기반 후보를 immutable pack/catalog로
출력한다. 원본 query-set 경로와 별도의 schema·증거 범위를 catalog에 남기되
어느 쪽도 서명이나 제품 자격을 부여하지 않는다. 반례마다 이전 전체
레코드를 인코딩·로드·재감사하던 경로는 새 레코드 한 개의 독립 감사와
누적 감사 집합의 symbolic proof로 바꿨다. 최종 직렬화된 pack은 다시
전체 감사하고 같은 선언 도메인의 커버를 재증명한다. 누적 감사와 최종
pack의 증명이 일치하며 거짓 dependency는 거절하는 집중 테스트를 통과했다.
여러 선언 도메인의 레코드를 합친 파일 생산 경로도 최종 pack을 독립 감사한 뒤
각 도메인의 커버를 다시 증명해야 게시한다. 이 마지막 경계의 Windows 테스트
실행은 애플리케이션 제어 정책 차단으로 미완료이며 branch CI 확인 대상이다.
다섯 profile의 넓은 도메인 자격, 실제 생성 비용·pack 크기·제품 효용은
계속 `Open`이다.
후보 catalog의 구조 검사만으로는 출처 없는 커버 주장을 증명하지 못하므로,
원본 `cover-set.v1` bytes와 source/canonical identity를 pack·catalog에
다시 결박하고 선언된 각 도메인의 symbolic proof를 재실행하는 별도
local-only 검증 함수를 두었다. 단일 레코드 pack에 완전 커버라고 적은
위조 후보는 구조 검사를 통과해도 이 경계에서 반례로 거절된다. 이 증거도
선언된 작은 도메인에 한정되며 profile 자격으로 승격하지 않는다.
겹치는 cover 도메인이 동일한 source board·의존 조건·lock·출구 관계를
반복 생성하면 이제 후보 병합 단계에서 **완전히 같은** 레코드만 하나로
합친다. 같은 canonical key에 결과나 원본 증거가 다른 레코드가 있으면
계속 거절한다. 한 레코드가 여러 도메인을 덮을 수 있으므로 구조 검사의
`query_count ≤ record_count` 가정을 제거하고 도메인 상한 64를 적용했다.
원본 source-bound 검증은 병합 후에도 선언된 모든 도메인의 symbolic
coverage를 각각 재증명한다. 겹치는 두 도메인·한 레코드 회귀와 충돌
레코드 거절 테스트를 통과했으며, 이는 pack 크기 개선을 위한 후보
계약이지 다섯 profile의 완전 자격·16MiB·성능 gate의 증거는 아니다.
`solver-cover-set.v1`은 수동 진입 pose와 창 대신 profile·높이·미노·원행
frame·창 종류·점유 조건을 받아, 실제 BuildUp template의 canonical sky
진입 집합과 제품 조회 창을 동일 소스에서 도출한다. 이를 후보 생성과 원본
선언 재증명 양쪽에 결박했다. no-kick T의 1L 고정 한 보드에서 생성한
관계는 제품의 실제 조회 문맥에 hit했고 독립 증명을 통과했다. 이 작은
고정 보드 fixture와 다섯 profile의 4L J 문맥 identity 집중 테스트는
광범위한 profile 커버, 16MiB 한도 또는 성능 채택의 증거가 아니다.

2026-09-23 후속 구현에서는 1~6L 삭제 행/물리 필드/bottom-prefix/replay의
공통 `CompactedRowFrame` codec으로 LB-001의 분리 산식을 합쳤다. 모든 삭제 행
mask의 round-trip과 기존 legal-board 집중 테스트를 통과했으나 실제 다섯
profile exhaustive parity는 계속 `Open`이다. 별도 서명 authority wrapper와
profile별 immutable owner를 `CLLR0002`에 연결하고, Native CLI와 WASM의
제품 admission이 구형 `CLBR0001` 대신 전체 파일 digest·규칙·generation·
record count를 검증하도록 변경했다. BuildUp은 실제 삭제 행 frame이 전달된
Boolean 요청에서만 profile sky-entry의 실제 도달 pose를 사용한다.
전체 높이의 닫힌 창을 먼저, 상단 절반과 기존 sky 창을 순서대로 조회하며,
모든 첫 출구는 질의 board에서 정확히 합성한다. 출구 후속 탐색은
BuildUp worker에 이미 컴파일된 template과 scratch를 재사용하고, 닫힌
전체 높이 hit에는 후속 탐색이 없다. Jstris 180의 닫힌 창, SRS-X의
상단 절반 창과 no-kick의 출구 있는 sky 창을 독립 exact 결과와
비교했으나 제품 성능은 아직 미측정이다.
2026-09-24의 자료 완결 작업은 다섯 profile 각각에 대해 제품이 실제 조회하는
56개의 `sky` Boolean 문맥을 선언했다. 1~6L·일곱 미노, 2L에서의 추가 두 원행
삭제 frame, 각 문맥의 하단 여덟 물리 셀 전체 점유 조합이 이 **닫힌 지원 영역**이다.
사용자는 이번 자료 완성 목표를 이 계획상 닫힌 지원 영역의 완결로 확인했다.
다른 보드·진입 pose·witness/spin/finesse/CountAll까지 완전하다는 뜻은 아니다.
기존 반례 기반 생성기의 단일 문맥·총합 proof 예산을 분리했고, 소스 전체에
누락·중복·축소 문맥이 없는지 별도 제품 후보 검증기로 확인한다. 다섯 profile
후보는 모두 56개 문맥을 독립 원시 탐색 및 symbolic coverage로 재검증했다.
SRS 7,449레코드/4,184,234바이트, SRS+ 7,449/4,183,658,
SRS-X 7,833/4,407,722, Jstris 180 7,449/4,184,234,
no-kick 2,222/785,942이다. 전체 encoded 합계는 80MiB 이하다.
실제 BuildUp frame의 1·2·4·6L 대표 요청도 이 로컬 pack으로 hit하고 기존
정확 탐색과 결과가 일치했다. 이 단계까지는 `Locally validated`인 **source-bound
candidate** 증거였다.
이후 같은 다섯 로컬 후보를 실제 BuildUp 조회에 연결해, 각 profile에서
1~6L·일곱 미노와 2L의 세 원행 frame을 합한 **56개 선언 문맥 전부**에 대해
빈 물리 보드 조회가 pack에 적중하고 기존 exact 판정과 일치함을 확인했다.
각 문맥의 하단 여덟 셀 256개 점유 조건도 제품 pack 인덱스에서 전부 hit하여
다섯 profile 합계 71,680개 조회가 빠짐없이 완료됐다. 이는 인덱스 적중의
로컬 증거이며, 각 hit의 국소 관계 정확성과 선언 domain의 완전성은 위의
별도 독립 primitive 감사·source-bound symbolic proof가 증명한다.
서명 전용 도구는 다섯 source-bound proof를 재확인하고 나서만 catalog를
작성하며, 개인키를 파일·로그에 남기지 않도록 설계했다. 성능/ABBA는 이번
자료 완결 목표 밖에 남긴다.
legal-board 서명 전에 관리 실행기에 1~4096바이트의 비대화식 stdin만
자식에게 전달하는 경계를 추가했다. 해당 bytes는 인자·receipt·디버그
출력에 기록하지 않고 전달 뒤 버퍼를 지운다. 무해한 입력의 전달 성공과
상한 초과의 자식 실행 전 거절을 확인했으며, 실제 서명 키·서명 catalog는
다섯 F/R/L 체인이 모두 통과하기 전에는 생성하지 않는다.

같은 날 후속 자료 게이트에서 전용 Ed25519 키의 공개 부분을 checked-in
accelerator keyring에 추가하고 개인 부분은 `CLEARRA_ACCELERATOR_SIGNING_SEED_V1`
GitHub Secret으로만 등록했다. `63deb2d0984059506b64e3c40a12f3b7bb34aa4d`의
source와 다섯 pack의 source-bound 증명을 서명 직전에 모두 다시 대조했다.
불변 데이터 후보 릴리스
[`conditioned-data-v081-20260924-rc1`](https://github.com/daejunnom/Clearra/releases/tag/conditioned-data-v081-20260924-rc1)
에는 다섯 개의 별도 `CLLR0002` pack만 게시했다. GitHub의 readback은
해당 tag가 위 source SHA에 결박되고, 다섯 asset의 길이·SHA-256이 catalog와
일치하며, 릴리스가 immutable prerelease임을 확인했다. 이 tag는 앱 v0.8.1
릴리스가 아니며 자동 배포를 트리거하는 `v*` tag도 아니다.

실제 공개 URL에서 다섯 profile을 각각 CLI의 명시 다운로드 경로로 받아
서명·digest·parser·제품 자격을 통과해 `ready`로 설치했다. 별도 프로세스의
다섯 재활성화도 성공했고, BuildUp의 1·2·4·6L 대표 frame 조회가 실제 pack
hit와 기준 결과 일치를 보였다. 따라서 다섯 pack은 **정확히 위에 선언된
56문맥·하단 8셀 Boolean 영역에서만** `Qualified`다. 전체 1~6L 보드와
임의 진입 pose, witness/spin/finesse/CountAll은 여전히 지원 영역 밖이다.
profile별 공유 상주 상한은 가장 큰 SRS-X도 9,918,130바이트이며 pack의
encoded 합계는 17,745,790바이트다. 제품 앱의 배포·Web/Discord readback,
legal-board와 결합한 실제 peak, 분산 worker의 효과 및 성능 채택은 여전히
`Open`; 이 데이터 자격을 v0.8.1 전체 `Released`로 승격하지 않는다.

서명되지 않은 개발용 pack, 문맥 miss,
범위 밖 요청은 기존 정확 탐색으로 돌아간다. 이 seam의 집중 테스트는
hit와 행 frame mismatch fallback을 확인했다. 현재 다섯 catalog slot은
자격이 있지만 임의의 내부 진입 pose를 자동으로 증명하는 경로, 전체 보드
domain 자격, 독립적인 실제 메모리 peak, Web/Discord 배포 및 성능 채택은
`Open`이다.
벤치마크는 사용자 지시에 따라 다음 단계로 미뤘다.
조건부 pack의 선언된 지원 영역을 채우는 **자료 완성**과 앱 릴리스 자격은
별개다. Web의 Release 직링크는 최종 바이너리 응답에 CORS 허용 헤더가 없어
브라우저 다운로드가 실패하므로, accepted Pages build가 qualified catalog의
길이·SHA-256을 검증한 동일 바이트를 짧은 같은-origin 경로에 포함하도록
수정했다. 4194 개발 서버는 사용자가 명시 다운로드를 누른 요청에만 같은
검증을 수행해 응답한다. 브라우저 worker는 다시 digest·WASM admission을
확인한다. 실제 Release 다섯 pack의 전송 검증과 실험 build의 정적 stage
재읽기는 모두 일치했고, SHA `5c1e8d22`의 비게시 후보 CI
`35915191357`은 Web 계약 포함 전체 성공했다. 이 결과는 Pages 배포 후
브라우저 readback을 대신하지 않는다.
같은 호스트의 전체 Web 빌드는 제품 build-owner 잠금으로 제품 슬롯에
진입하지 못했고, 별도 실험 슬롯의 Windows WASM 컴파일은
`wasm-bindgen`의 `rustversion` 의존성 오류로 중단됐다. 관리형 WSL
시도도 호스트 compiler guard/manager 경계에서 중단돼 WASM·Pages 전체
산출물 완료 증거는 없다. 이 실패를 pack의 길이·hash 또는 source-bound
완전성 실패로 해석하지 않으며, 릴리스 전 빌드 환경과 실제 Web readback을
별도로 닫는다.

Web 수명주기는 소스에 내장된 서명 catalog를 WASM에서 검증한 뒤에만 자산 URL과
용량을 제시한다. 사용자가 명시 다운로드를 누르기 전에는 원격 asset을 읽지 않고,
다운로드 후에는 digest와 제품 parser를 통과한 바이트만 별도 OPFS pointer에
게시한다. 검색 root WASM owner는 legal-board를 재검증해 설치하고, 조건부
relation은 서명 payload를 검증한 뒤 실행 형태에 따라 직렬 root 또는 단일
분산 verifier에 설치한다. 다른 profile의 이전 슬롯을 제거한 후 시작한다.
동일 서명 legal-board 세대가 계속 설치되어 있으면 OPFS pointer와 파일 길이를
재확인하되 그 큰 payload를 매 검색마다 WASM으로 다시 복사하지 않는다.
조건부 relation의 분산 handoff는 job마다 읽기·검증·한 verifier로 transfer하며,
명시 삭제·교체·profile 변경 시 이전 WASM slot을 제거한다.
검색 root의 요청별 자산 선택은 `--rule`/비활성 옵션을 찾는 정규식 대신
공통 Rust 명령 파서의 typed profile과 `exact_accelerator_policy`를 읽는다.
따라서 기본 rule을 생략한 유효 요청도 동일한 선택을 받는다. 파서 실패는
이전 slot을 비우고 원래 명령 오류를 반환하며, 지원하지 않는 custom rule은
이전 slot을 비운 뒤 기준 정확 경로로 간다.
이 경계의 Rust 집중 테스트와 Web worker 타입·계약 테스트는 로컬 통과했지만,
실제 qualified 자산을 이용한 분산 실행 검증은 별도 `Open`이다.
손상된 로컬 pointer나 payload는 서명된 다운로드 계획을 가리지 않고
`InvalidAsset`으로 표시해 재다운로드·삭제를 허용한다. 이 복구는 모의 OPFS 계약
검증 상태이며 실제 브라우저와 qualified Release asset의 smoke를 대신하지 않는다.
조건부 relation은 직렬 탐색이면 root WASM이, 분산 탐색이면 첫 verifier 하나만
전체 서명 pack을 설치한다. root는 분산 handoff 전에 payload를 검증만 하고
소유하지 않는다. 다른 verifier는 기존 정확 경로를 사용하므로 전체 pack을
worker별로 복제하지 않는다. signed complete legal-board가 있는 경우에는 root가
음성 전용 요약을 만들고 admitted verifier 수와 signed resident 상한에 맞춰 전송한다.
이것은 `single-owner` 소스 경계이며 모든 verifier의 조건부 relation hit 또는
실제 자산에서의 active-session peak 증명이 아니다. 둘 다 `Open`이다.
비게시 WASM smoke에서 실제 공개 no-kick pack의 길이·SHA-256은 맞았으나 첫
설치는 `accelerator_session_in_use`로 거절됐다. ABI의 일반 worker-start 충돌
검사가 설치 함수 자신이 소비하는 `transfer_input`까지 실행 중 owner로
간주한 결함이다. 설치·음성 synopsis 수신의 guard를 실제 외부 compute owner만
보도록 좁히고 native ABI 회귀 테스트를 통과했다. 수정 SHA `7380db5d`의
집중 CI `35927889164`는 네 job 모두 성공했고, 동일 SHA의 비게시 WASM
smoke `35927899902`는 공개 no-kick pack의 서명 catalog 조회·download
digest·WASM 설치·제거를 모두 통과했다. 이는 한 profile의 브라우저용 ABI
경계 증거이지 실제 Web 분산 검색, 다섯 profile의 브라우저 admission 또는
Pages 배포 readback의 증거는 아니다.
후속 SHA `50f6a04a`의 비게시 WASM smoke
[`35930194641`](https://github.com/daejunnom/Clearra/actions/runs/35930194641)는
공개 불변 자산 다섯 개를 각각 내려받아 catalog 크기·SHA-256·WASM 설치와
제거를 통과했고, no-kick 설치 상태에서 짧은 PC 제품 job도 완료했다.
다섯 프로필의 WASM 자산 수용 범위는 넓어졌지만 실제 Web 분산 실행,
모든 문맥의 제품 hit, Pages/Discord readback의 증거로 확대하지 않는다.
완전 legal-board의 단일 소유자에서 파생 가능한 음성 전용 Bloom synopsis는
임의의 더 작은 power-of-two word budget으로 접어도 저장된 모든 key의 bit를
보존한다. 이 안전성·크기 하한·서명 세대 결박을 Core 집중 테스트로 확인했다.
요약의 wire는 profile·rule·generation·signed catalog identity와 손상 검사에
묶인다. 동일 앱 job의 신뢰된 root→worker 전송만을 권위로 삼으며, wire의
checksum을 독립 서명이나 외부 입력에 대한 음성 증명으로 취급하지 않는다.
worker 설치·교체·취소의 Web 계약은 통과했지만 당시 legal-board
catalog가 미자격이어서 실제 분산 음성 조회의 증거는 아니었다.
현재 signed catalog로도 이 실제 Web 분산 실행 검증은 `Open`이다.
두 제품 registry의 설치 전 128 MiB 검사도 선택 profile만이 아니라 모든
resident profile의 크기를 합산하도록 소스를 보완했다. 다만 Windows 애플리케이션
제어로 이 Rust 경계의 실행 검증은 아직 못 했고, 실제 자산의 decode·install 중
순간 peak 및 worker별 복제량도 별도 실측이 필요하다.
Web의 host snapshot은 기기 메모리가 미확인일 때 WASM 단일 transfer를 32 MiB로,
0.5 GiB 기기에서는 16 MiB로 제한한다. legal-board 자산 상한 64 MiB보다
작으므로 큰 qualified bundle은 설치 상태여도 검색 root에서 활성화되지 않고
정확 fallback으로 돌아갈 수 있다. 다운로드 화면에는 root worker와 같은 host
snapshot의 transfer 한도를 보여 주고, 초과한 qualified 자산이 저장되더라도
탐색에 적용되지 않는다는 안내를 추가했다. 용량을 임의로 상향하지 않으며, 실제
다섯 bundle 크기를 확인한 뒤 저메모리/미확인 기기의 chunked admission 또는
명시적 비활성 상태 UX를 확정한다. 이 호환성은 v0.8.1 surface gate에서 `Open`이다.
Desktop GUI의 파일 기반 관리는 이 Web 변경만으로 완료되지 않는다. 이후
Desktop에는 별도 Tauri native 관리 패널과 CLI 공통 저장소 호출이
연결됐지만, 서명된 실제 자산이 없어 설치·취소·탐색 효과를 제품에서 검증하지
못했다. 첫 Tauri Rust 타입 검사에서는 Windows UMCI가 생성된 build script를
차단했으나 수동 재시도에서는 빌드가 진행돼 비동기 `Send`/borrow 오류를 수정하고
`cargo check --locked --offline`을 통과했다.
후속 Desktop 장기 실행 프로세스에서는 새 job을 시작하기 전에 이전 job의
실행 종료를 확인하고, 선택하지 않은 profile과 명시 비활성 제품의 resident
slot을 먼저 제거하도록 했다. 제거 중 session lease가 남아 있으면 다른
profile을 추가 설치하거나 새 job을 시작하지 않는다. CLI·GUI host의 로컬
Rust 타입 검사는 통과했다. Tauri 전체 타입 검사는 이번 Windows 실행에서
서드파티 `selectors` build script가 응용 프로그램 제어 정책에 두 번 차단돼
미확인이다. 이는 qualified 자산의 Desktop 실사용 smoke나 실제 peak 증거를
대신하지 않는다.

Discord의 accepted Cloud Run job-service 이미지에는 별도 v0.8.1 데이터 계층
연결을 추가했다. 이미 승인된 CLI가 빌드 단계에서 catalog 열 슬롯을 모두
`qualified`로 확인한 뒤에만 두 제품의 다섯 profile을 다운로드하고, 설치
generation·catalog·payload 길이를 재조회한다. 디렉터리는 root 소유의
읽기 전용 상태로 고정하고 `USER node` 전환 후 다시 읽어 확인한다. v0.8.0
이미지는 자산 없이 기존 실행을 유지하지만 v0.8.1 이상에서 한 슬롯이라도
미자격이면 이미지 구성이 실패한다. 이는 Gateway 무적재와 서명 자산의
compute-side 배치 **소스 계약**이다. 두 catalog가 모두 qualified가 된 뒤에도
실제 Cloud Run 이미지를 완성했다는 증거는 아니다. 전체 자산의 게시 순서,
이미지 빌드·실행 smoke, 요청별 한 profile만 상주하는 peak 검증은
여전히 `Open`이다.

pnpm injected `@clearra/ui`에서 형제 `ctk3/src` 상대 import를 찾지 못하던
Desktop Vite 빌드 문제는 Web/Desktop 공통으로 `@clearra/ui`의 선언된 export를
원본 workspace source에 결박하여 해결했다. 공개 export 전체의 해석 계약과
managed Desktop 실험용 Vite build를 통과했으나 Tauri 제품 실행은 검증되지 않았다.
따라서 Desktop을
`Qualified`나 `Released`로 표기하지 않는다. 실제 qualified Release asset의 브라우저 CORS/redirect 수신과
payload admission도 아직 제품 smoke가 없어 `Open`이다. 성능 ABBA는 사용자
지시에 따라 다음 단계로 미뤘으며, 이번 단계의 타입
검사나 Svelte 컴파일은 성능 채택 증거가 아니다.

native lifecycle은 catalog의 `active_session_shared_bytes`를 실제 parser가 계산한
공유 상주량의 서명된 상한으로 대조한다. allocator capacity가 toolchain마다 달라도
실제 값이 상한 이하면 허용하고, 상한을 넘으면 자산을 거절한다. 같은 process에서 같은 generation과 서명 statement가
이미 설치돼 있으면 payload를 다시 읽지 않고 단일 `Arc` owner를 재사용한다.
명시 삭제는 active session lease가 없을 때 in-process owner를 먼저 제거한 다음
persistent pointer를 지운다. 이 경계는
worker별 복제를 허가하거나 Web worker의 공유 소유권을 증명하지 않으며, 후자는 계속
`Open`이다. legal-board와 conditioned-reachability의 설치·삭제는 공통 mutation
경계에서 직렬화하여 동시 설치가 각각 상대 자산 부재를 관찰한 뒤 합산 128 MiB를
초과하는 경합을 금지한다. 명시 다운로드 저장소는 첫 쓰기 전에 기존 조상 경로의
link/reparse 여부를 검사하고, 전송·동기화·digest·구조 자격 중 어느 단계가 실패해도
staging 파일을 제거한다.

## 2. 릴리스 순서와 No-Go

1. v0.8.1에서 기존 solver 안정화, 다섯 profile의 exact legal-board,
   소형 조건부 도달성 BuildUp 가속기를 완료한다.
2. v0.8.1 exact SHA를 CLI, GUI, Discord 순으로 배포하고 P0/P1 회귀가 없음을
   대표 결과와 provider provenance로 readback한다.
3. v0.9.0을 accepted v0.8.1 위에 재기준화한다.
4. 전체 자격을 통과한 PC4 TB profile만 독립 활성화하여 v0.9.0을 배포한다.
5. 호환되는 upstream dataset generation만 v0.9.x에서 갱신한다.
6. 안정성과 운영 조건이 충족되면 v1.0.0으로 승격한다.

exact legal-board 또는 조건부 도달성 가속기 중 하나라도 정확성, 크기, 메모리,
성능 gate를 통과하지 못하면 v0.8.1은 **No-Go**다. 기능을 조용히 비활성화한
채 같은 완료 범위로 릴리스하지 않는다.

## 3. v0.8.1 필수 구현

### 3.1 다섯 profile exact legal-board

SRS, SRS+, SRS-X, Jstris 180, no-kick을 독립 생성·검증한다.

- `F_k`: 빈 필드에서 해당 profile의 정확한 규칙으로 `k`개를 놓아 도달 가능한 상태
- `R_k`: 남은 피스를 놓아 완성 필드까지 갈 수 있는 상태
- 제품 집합: `L_k = F_k ∩ R_k`

`reverse-layer-*`는 `R_k` 생성의 중간 증거일 뿐 제품 자산 또는 음성 판정
권위가 아니다. 생성기는 exact ILC, ordered first-success kick, rotation/180,

생성기의 `L_k` 역추적은 이미 완결된 `L_(k+1)`에서 geometric predecessor를
checkpoint 가능한 run으로 열거·병합하고, 정렬된 `F_k`를 한 번 순차 읽어
교집합을 만든 뒤, 남은 `(source, piece)`만 exact ILC로 재검증한다. 이는
`F_k` 전체를 매번 정방향 확장하던 조건과 같은 집합 술어이며, spill identity는
target과 forward layer digest를 모두 포함한다. 이 역추적 최적화 자체의
실행·성능 자격은 `Open`이다. 위에서 이미 기록한 다섯 profile 후보의 전체
P7P4 집합 차분은 별도로 완료된 `Locally validated` 증거이며, 최적화의
성능 자격이나 profile 전체의 `Qualified` 판정으로 확대하지 않는다.

기존 reverse 산출물은 Git 이력에서 지우지 않지만 package, catalog 및 제품

### 3.2 `BoardConditionedReachability`

exact legal-board와 별도 namespace·generation·loader를 가진 소형 조건부
도달성 계층을 구현한다. 질의 identity에는 다음을 모두 포함한다.

- compacted physical board와 원래 행 대응
- profile, piece, rotation, ordered kick와 180 의미
- 실제 도달한 entry pose 집합
- source/destination 및 앞선 kick 후보 전체의 충돌 dependency cell
- 벽·바닥·상단과 좌표 frame, 목표 lock 또는 질의 범위
- Boolean/witness/spin/finesse/CountAll 중 필요한 증거 수준
- generation과 relation schema identity

반환은 검증된 entry→exit/lock 관계, 합성 가능한 witness/macro, 완전성이 증명된
폐쇄 범위의 unreachable, 또는 `Unknown`/`OutOfScope`/`NotLoaded`/
`InvalidAsset` 중 하나다.

- first-success ordered kick을 보존한다.
- 장애물 추가로 뒤 kick이 열릴 수 있으므로 점유 단조 감소를 가정하지 않는다.
- 전역에서 실제 도달한 entry pose에만 국소 relation을 적용한다.
- 창 밖 우회, boundary 밖 footprint, dependency 누락 가능성이 있으면 fail-open한다.
- Boolean이 witness/spin/multiplicity를 보존하지 못하는 모드는 기존 exact 경로다.
- decision DAG, bounded entry/exit macro, bounded exact cache를 각각 비교한 뒤
  채택한다.
- solver hot loop에서 HTTP를 호출하지 않는다. host가 pack을 검증하고 session의
  immutable generation을 고정한다.
- 1~6L 및 초기 필드 요청도 검증 domain이면 사용할 수 있다. legal-board의 4L
  empty-origin 제한을 전파하지 않는다.

하드 gate는 16 MiB/profile, 다섯 profile 80 MiB, active-session 합산 공유 peak
128 MiB다. profile별로 독립 설치·교체하고 다운로드 전 실제 bytes를 표시한다.

### 4.4 generation과 조회

- mutable HF ref는 discovery 전용이다.

  KAT version이 든 immutable generation에 고정한다.
- digest는 코드에 영구 고정하지 않고 generation manifest에 기록한다.
- 기본 온라인 조회는 정확한 Range만 허용하고 전체 파일 `200`은 거절한다.
- 명시 로컬 다운로드만 `tablebase check|download|status|remove --profile PROFILE`
  경로에서 허용한다.
- Jstris 180 약 661 MiB는 관측값이며 상수가 아니다.
- 로컬 파일과 HTTP Range는 같은 parser/materializer/reducer를 사용한다.
- CLI는 `--offline-fallback` 없이 heavy offline exact search를 시작하지 않는다.
- CLI의 `--offline-fallback`은 `--tablebase`와 함께만 유효하며, lookup 실패 때
  tablebase 표시만 제거한 동일 typed 요청을 기존 exact executor로 보낸다. 사용자가
  취소한 tablebase 요청은 fallback으로 재시작하지 않는다.
- GUI와 Discord도 사용자가 선택하기 전에 heavy fallback을 시작하지 않는다.

### 4.5 Setup 경계

TB는 complete PC candidate family만 공급한다. 기존 Setup engine이 shape, spin,
score, BuildUp, probability를 평가한다. PC Search와 SetupSearch 자격을 분리하고,
동일 query의 offline/TB digest와 candidate·coverage count가 같을 때만 Setup
acceleration을 활성화한다. offline이 완료되지 않고 TB만 완료한 경우
`feasibility dominance`로 기록할 수 있으나 제품 활성화 증거는 아니다.

### 4.6 v0.9.x와 v1.0.0

호환 generation 갱신은 발견 → candidate manifest → format/index/provenance/license
검증 → KAT/offline differential → Range/materialization A/B → canary → production
pointer 원자 promote → 이전 N개 generation 보존 순서다. schema, rule,
completeness 또는 공개 결과 의미가 바뀌면 data-only patch가 아니다.

n-PC 확률, Krylov 및 V* recommendation은 v0.9.x/v1.0.0 선행조건이 아니다.
관련 port/type은 feature-off, 무 I/O, 공개 surface 비노출 상태로만 유지한다.

## 5. 공용 provider·실패 계약

| 제품 | 권위 | namespace | 음성 판정 |
| --- | --- | --- | --- |
| exact legal-board | qualified `F∩R`, 4L domain | profile별 legal-board generation | 완결 domain에서만 |
| 조건부 도달성 | 검증된 국소 entry/exit relation | relation pack generation | 폐쇄 국소 domain에서만 |
| PC4 Tablebase | qualified all-outgoing graph | TB Range/local generation | miss 자체는 UNSAT 아님 |

공통 typed 상태는 `Ready`, `NotLoaded`, `OutOfScope`, `NotQualified`, `Miss`,
`InvalidAsset`, `SnapshotMismatch`, `RateLimited`, `Offline`, `Cancelled`다.
UI 기본 설명은 내부 hash/raw candidate ID를 숨기고 진단 export에만 provider,
profile, generation, completeness scope를 남긴다. 모든 provider는 동일 canonical
candidate stream과 기존 reducer로 진입하며 별도 minimum/score/probability 의미를
만들지 않는다.

## 6. 검증, CI, 배포, rollback

### 6.1 정확성

- 삭제 행 전체 조합, codec round-trip, 다중 삭제와 replay 원좌표
- ordered kick 앞 후보 성공/실패/경계/180 및 장애물 추가 비단조 사례
- 같은 내부 점유와 다른 외부 통로/entry pose, 창 밖 우회 후 재진입
- Boolean/witness/spin/finesse/CountAll 의미 분리
- profile별 legal-board exhaustive differential와 no-false-negative KAT
- relation 대 독립 primitive reference bounded exhaustive
- corrupt/truncated/wrong-profile/wrong-generation/stale-cache fail-open
- graph path 대 placement/replay offline parity
- fixed queue/hold/pattern/bag denominator/reducer parity
- Setup candidate/coverage/result digest parity

### 6.2 크기·자원·성능

profile별 compressed/decoded 크기, 공유/복제량, cold Range 수·bytes, session 수신량,
persistent cache/eviction, reader lease를 측정한다. 기존 solver, legal-board,
relation, 결합 후보를 ABBA하고 CandidateProjection/reachability/BuildOrderGraph/
language/reducer/render를 분리한다. 1~6L, 초기 필드, fixed queue, 큰 pattern,
build probability, minimum, replay를 포함하며 4L P7P4의 first page와 full export를
별도로 기록한다. profiling과 사용자 wall time 실행을 분리한다.

### 6.3 CI·배포

변경 owner 집중 테스트 → bounded exhaustive/fuzz/differential → Core/App/CLI →
Web/Desktop/Discord parity → exact source build-once artifact 재사용 → 배포 직전
canonical acceptance 1회 → Pages/CLI candidate smoke → Discord light/heavy 및 Oracle
path proof → publish/promote 결정 1회 → 모든 surface readback → tag/immutable release
순서다.

### 6.4 rollback

- v0.8.1: v0.8.0 application과 명령 registry로 전체 rollback
- v0.9.0: v0.8.1 application과 이전 static beta 상태로 전체 rollback
- v0.9.x: generation pointer를 이전 qualified generation으로 우선 rollback
- parser 비호환: application과 manifest 원자 rollback
- in-flight session: 시작 generation으로 완료하거나 typed cancellation
- health endpoint만이 아니라 CLI/Pages/Discord 대표 결과와 provenance readback

## 7. 최종 완료 판정

v0.8.1은 다섯 profile의 legal-board와 relation pack이 모두 `Qualified`, 모든
크기·메모리·성능 gate 통과, PC/Build reducer 및 세 surface parity, exact SHA
acceptance/deploy/rollback readback까지 끝나야 `Released`다.

v0.9.0은 최소 한 profile의 graph/target/materializer 전체 자격, signed production
generation, offline complete family parity, 실제 adapter와 fallback UX, Discord TB
hit의 heavy Cloud Run 0, provider 무음 혼용 없음, exact app SHA+generation acceptance와
rollback을 요구한다.

새 문서, generator 존재, reverse layer, synthetic CI 또는 한 번의 benchmark만으로
어떤 항목도 자동 완료하지 않는다.
