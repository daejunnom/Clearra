# I18N

Clearra uses `clearra-i18n` for language resolution and translation catalogs.
The default language is English.

## Language rollout state

Language recognition, catalog completeness, and product exposure are separate
decisions. A locale must not become selectable merely because a draft catalog
exists.

| Locale | Shared Rust catalog | CLI | GUI | Discord | State |
| --- | --- | --- | --- | --- | --- |
| `en` | complete | released | released | released | released |
| `ko` | complete | released | released | released | released |
| `ja` | complete small shared catalog | blocked | draft catalog only | draft message/slash seeds only | planned |

`LanguageId::parse_known`, `matchKnownWorkspaceLocale`, and
`matchKnownDiscordLocale` recognize `ja`/`ja-JP` for translation tooling. The
released parsers and selectors intentionally reject it. Until the activation
gate below passes, `--lang ja` is invalid, GUI language controls omit `JA`, a
Japanese browser or OS locale resolves to English, and Discord never registers
Japanese localization metadata or stores `ja` preferences.

Rust CLI and Rust shell resolution is intentionally dependency-free and
unsafe-free:

1. Explicit `--lang`.
2. `CLEARRA_LANG`.
3. POSIX-style environment locale variables: `LC_ALL`, `LC_MESSAGES`,
   `LANGUAGE`, then `LANG`.
4. English fallback.

Native GUI resolution owns platform OS locale calls:

1. User-selected language.
2. Stored GUI preference.
3. `CLEARRA_GUI_LANG` or CLI-compatible language bridge.
4. OS locale detection such as Windows `GetUserDefaultLocaleName`.
5. English fallback.

Released locale values beginning with `ko` resolve to Korean; English locale
values resolve to English. Known but unreleased locales and unknown locales
resolve to English. Resolution reports carry both the resolved language and
source, for example `language=ko` and
`language_source=windows-user-default-locale` or
`language_source=environment`.

UI schemas carry translation keys plus English fallback labels. The fallback
keeps the GUI usable even when a translation catalog is incomplete.

JSON contract keys are never translated. Translating labels such as
`Total solutions` is allowed; translating `total_solution_count` is not.

## Japanese preparation ownership

- Shared Rust terms live in
  `crates/clearra-i18n/src/catalog/japanese_catalog.rs` and already have exact
  key parity with the small shared English catalog.
- The GUI rollout manifest lives in
  `packages/clearra-ui/src/lib/i18n/languageManifest.ts`. The partial Japanese
  workspace catalog lives beside it in `japaneseWorkspaceCatalog.ts` and is not
  read by production rendering.
- The Discord rollout manifest lives in
  `apps/clearra-discord-bot/src/discord/locale-rollout.mjs`. Japanese reply and
  slash-command seeds live in `japanese-i18n-draft.mjs` and are not published.
- CLI language selection remains owned by the shared released-language parser;
  product help bodies must be translated before `ja` joins that set.

## Japanese activation gate

Japanese can move from `planned` to `released` only in one change that proves
all of the following:

1. The GUI draft contains every `WORKSPACE_MESSAGE_KEYS` entry with identical
   interpolation placeholders, and every remaining binary EN/KO component
   branch has moved into an exhaustive locale map.
2. CLI top-level and product help, validation, progress, and result text are
   Japanese; `--lang ja` parity tests cover text and structured output without
   translating JSON keys.
3. The Discord message catalog has full English-key and placeholder parity;
   validation adapters, modals, command names, option names, choice names,
   descriptions, notes, and every `/help` page have Japanese coverage.
4. Discord registration-size limits and localized-name collision tests pass for
   `ja`, and persisted locale migration accepts `ja` without changing existing
   `en`/`ko` records.
5. CLI, GUI, and Discord expose Japanese together. A product-specific early
   activation and per-key English fallback in a Japanese user session are both
   release blockers.
