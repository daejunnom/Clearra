# Clearra v0.8.0 안정화 및 v0.9.0 PC4 구현·배포 계획

## 1. 문서 권위와 릴리스 순서

이 문서는 v0.8.0 안정화부터 v0.9.0 PC4 온라인 기능 배포까지의 활성 실행
계획이다. `docs/v0.8.0-remaining-work-plan.md`는 당시 구현 및 배포 증거를 설명하는
역사 문서로 보존한다. 과거 문서의 `blocker 0`, `source complete`, `ready` 판정은
현재 Go 판정이 아니다. 이후 수동 점검에서 발견된 준비 단계 정지, 해법 누락,
내부 `ctk1` 표현 노출, 구축 확률 옵션 미반영 등은 구현 단계에서 다시 열어
코드와 회귀 테스트로 닫는다.

공개 릴리스 기준선은 `v0.7.4`다. `v0.7.5`는 릴리스 태그가 아니며, 문서에서
언급되는 경우에도 과거 rollback source 또는 7개 상단 메뉴의 미출시 UI 참고안만
뜻한다. 배포 및 누적 변경 비교의 기준으로 사용하지 않는다.

릴리스는 반드시 다음 순서로 진행한다.

1. **v0.8.0**: v0.7.4 회귀 수정, 입출력 경계와 SRP 강화, GUI/CTK/watchdog,
   canonical gate 및 선택 배포 개선.
2. v0.8.0 배포, 20분 이상 관찰, 태그와 immutable release 확정.
3. **v0.9.0**: 기존 정적 PC4 베타를 제거하고 PC4 V\* Policy Advisor를 추가한다.
   Krylov/n-PC 확률은 공개 기능으로 넣지 않고 후속 기능용 비활성 SRP seam만 준비한다.
4. v0.9.0 배포 뒤 자격을 통과한 호환 Policy generation 갱신은 v0.9.x,
   안정화 이후 별도 계획으로 v1.0.0.

v0.8.0과 v0.9.0은 각각 독립된 exact-SHA Go gate를 갖는다. v0.8.0이 실제로
배포·관찰·확정되기 전에는 v0.9.0 production mutation을 하지 않는다.

2026-09-02에 HF API와 공개 `main`을 다시 확인한 별도
[`muse918/tetris-4lpc-survival-krylov`](https://huggingface.co/datasets/muse918/tetris-4lpc-survival-krylov)
snapshot의 최신 공개 revision은 여전히 `519a0cb1...`이며 그 뒤의 공개 commit은
발견되지 않았다. 이 snapshot은 전체 PC 해법, Setup 해법, 최종 policy의 정확한 n-PC
성공 확률이 아니라 과거 `pi_policy_v3` 아래의 layer-0 생존 연구 자산이다. 따라서
v0.9.0 Policy Advisor의 기능·배포 blocker와 분리하고, §5.2의 자격 조건이 후속
release에서 충족될 때까지 사용자 표면과 production data path를 만들지 않는다.
새 공개 revision이 생겨도 이 문서의 관찰 SHA를 실행 상수로 승격하거나 기능 범위를
자동으로 넓히지 않고, 그 시점의 manifest와 compatibility를 다시 자격 심사한다.

## 2. v0.8.0 안정화

### 2.1 구현 단계 버그 탐색과 SRP

각 결함은 `surface input -> canonical CLI argv -> shared command compiler -> typed
AppRequest/AppCommand -> use case/coordinator -> domain result -> typed projection ->
presenter` 경로를 따라 재현한다. 내부 bitfield, worker
메시지, cache key 또는 실행 ID를 사용자 결과로 직접 투영하지 않는다. 요청
수명주기는 `preparing -> running -> terminal`로 수렴하고 성공, 빈 결과, 취소,
실패, stale response를 서로 다른 상태로 유지한다.

PC 탐색의 알고리즘 불변식은 inverse lock-clear(ILC)다. 모든 PC 제품은 먼저
`GeometryCatalog`가 concrete inverse lock-clear realization을 컴파일하고 같은
Geometry skeleton exact-cover family를 완전 탐색한다. `tiling`은 이 family를 결과로
물질화하고, `path`·`chance`·`minimals`·`score`·`saves` 등 non-tiling 제품은 같은 ILC
후보에 BuildUp, queue/hold 도달성, coverage 및 각 제품의 objective reducer를 추가한다.
따라서 이 문서에서 non-tiling은 ILC를 사용하지 않는 경로를 뜻하지 않는다. forward
placement 열거, 대표 해법 하나, Discord 전용 탐색기 또는 presenter 측 조합을 ILC의
대체 backend로 만들지 않는다.

Git 기준선 비교에서 v0.7.4 GUI의 최소 해법은 native bare-PC 호환 문법인
`clearra pc ... --objective minimum-cover`로 내려갔지만
`7aacad0`(`feat: complete v0.8.0 product release`)부터 GUI와 Discord에 별도 제품
의미를 이식하면서 `clearra pc minimals ...` 및 표면별 builder/parser가 추가됐다. 같은
변경에서 product capability가 있다는 이유만으로 WASM 요청을 무조건 serial로 보내는
경계도 들어왔다. ILC 자체가 교체된 것은 아니지만, 입력의 출처와 제품 ingress가 실행
계획 및 terminal projection을 바꿀 수 있게 된 것이 회귀 경계다.

Discord 명령어 재설계 기준선은 `1ce3e06`(`Fix search option and result contracts`)이다.
이 변경은 slash catalog/input, packed options, text command, modal, 도움말·지역화와
`public-search-contract`를 한 번에 재설계했다. 현재 Git 이력에서는 이 commit이 새
main의 선형 조상으로 남아 있지 않지만, 후속 저장소 재구성 commit `701454b`에 핵심
catalog/input/packed/text/public-contract blob이 byte-identical하게 들어왔음을 확인했다.
따라서 v0.8.0은 조상 관계나 과거 파일명을 기준으로 재설계를 되돌리지 않는다. 현재
46개 공개 command surface, packed option 의미, modal/text/slash routing, locale/help를
고정한 contract를 기준선으로 삼고, CLI-first 변경은 그 아래의 요청 컴파일과 결과
권위만 교체한다. command 이름·옵션·등록·응답 UX 변경이 필요한 diff가 생기면 별도
제품 변경으로 취급해 이 release에서 거부한다.

v0.8.0에서는 이 Discord-to-GUI 기능 이식 방향을 취소한다. Discord나 GUI 구현을 다시
다른 표면에 복사하지 않고, canonical CLI 문법과 그 문법을 typed `AppRequest`로 만드는
순수 command compiler를 유일한 입력 의미 권위로 삼는다. 제품 command는 입력/결과
계약만 고정하며, ILC candidate producer, worker 분할, 취소/progress, exact objective
reducer 또는 terminal payload 선택 권위를 갖지 않는다. executor와 coordinator는
surface, named-product ingress, `ProductCapabilityContract`의 출처가 아니라 컴파일된
query/objective/evidence requirement만 본다. `PcMinimalsIngressOrigin` 같은 출처 구분이
진단 provenance로 남더라도 scheduling, serial/distributed 선택, 해법 의미 및 결과
완전성 분기에는 사용하지 않는다.

native bare-PC 문법은 v0.7.4 호환 경계로만 보존한다. `clearra pc --objective
minimum-cover`의 기존 옵션, 기본값과 legacy 출력은 깨뜨리지 않되 GUI와 Discord가 새
기능을 호출하는 canonical 문법으로 사용하지 않는다. named product인 `clearra pc
minimals`는 subcommand를 generic PC option보다 먼저 확정하고, 제품 의미를 바꾸는
`--objective`나 `--count` override를 계속 거부한다. 이 제품의 고정
`CountUnique`는 한 concrete candidate의 실행/중복 계수 정책이다. 이는 최소 cardinality가
같은 **모든 portfolio alternative**를 열거하는 tie 정책과 다른 축이다. 따라서
`CountUnique`를 `CountAll`로 바꾸거나 path 중복을 늘려 tie를 만드는 대신, 완전한
candidate coverage row에서 exact two-pass reducer가 모든 최소-cardinality portfolio를
복원한다. GUI와 `--ties`를 명시한 CLI는 그 전체 tie family를 bounded paging하고,
기본 CLI와 Discord는 canonical 첫 portfolio를 사용한다. v0.7.4 bare minimum-cover와
named `pc minimals`의 회귀 비교는 서로 다른 공개 출력 모양이나 raw path count를 억지로
동일시하지 않고, 정규화된 ILC candidate family, coverage union, 최소 cardinality와
canonical portfolio 의미를 비교한다.

다음 항목은 재현 테스트 없이 완료 처리하지 않는다.

- 전체 replay 및 일부 탐색이 준비 단계에서 끝나지 않는 문제.
- 최소 해법뿐 아니라 전체 해법, save, score 및 Build 계열에서도 공통 Geometry
  producer/coordinator가 준비 또는 Geometry 단계에서 더 진행하지 않는 문제. Geometry는
  요청 generation에 결속된 실제 progress를 내보내고, 입력 분할 0개, 해법 0개, 자원
  거부, 취소, worker 실패를 각각 하나의 terminal 결과로 수렴시켜야 한다. 진행 가능한
  work가 남았는데 progress와 bounded work counter가 함께 정지하는 경우를 재현하는
  watchdog 테스트를 제품별 문자열 분기가 아닌 공통 실행 계약에 둔다. PC verifier가
  256-candidate batch 전체를 한 번의 동기 WASM 호출로 소비해 heartbeat를 막는 현재
  경계는 candidate와 내부 work 양쪽의 bounded cursor/`continue_work`로 나눈다. 단순히
  batch 크기만 줄여 한 candidate의 장시간 실행을 숨기지 않으며, 각 slice 사이에서
  progress, cancel 및 generation 폐기를 처리한다.
- 배포된 직렬 fallback 회귀와 새 분산 verifier의 long-tail 문제를 별도 결함으로
  취급한다. 전자는 canonical 제품 command가 v0.7.4의 ILC 병렬 실행 경로를 잃지 않도록
  복구하고, 후자는 한 candidate 또는 한 batch가 worker heartbeat를 독점하지 않도록
  resumable slice로 만든다. 하나를 고쳐 다른 하나가 가려진 상태를 Go로 판정하지 않는다.
- 성공한 해법이 presenter에서 사라지는 문제.
- 100개를 넘는 tiling/해법 family에서 governed page ABI가 후속 페이지를 거부해 첫
  page 뒤의 해법이 열리지 않는 문제. count와 materialization authority가 complete면
  같은 result identity와 generation에 결속된 bounded page 요청이 terminal page까지
  진행돼야 하며, 미지원 ABI를 성공 count로 광고하지 않는다.
- 기존 GUI 필드 대신 해법 종류가 `ctk1` bitfield로 표시되는 문제. GUI는 항상
  기존 field/board/queue/hold/operation 표현을 우선한다.
- Build probability 옵션 변경이 request snapshot, worker input 및 cache identity에
  전달되지 않는 문제.
- `pc.score`의 필드 평균 점수가 score-optimal 최소 해법 portfolio로 잘못 투영되는
  문제. v0.7.4의 제품 의미를 복원해 complete normalized solution field family의
  **모든 필드**를 반환한다. 각 필드의 score는 패턴별 합법 trace 중 score-only
  최고값을 취한 뒤, 그 필드가 해결하지 못한 패턴을 0으로 두고 전체 materialized
  universe weight로 평균한다. overall score는 각 패턴에서 전체 필드 중 score-only
  최고값을 같은 full-universe 분모로 가중한 값이고, covered-pattern 조건부 평균은
  진단값으로 분리한다. 패턴당 canonical 필드 하나를 대표로 골라나 필드를 해법
  조합으로 축약하지 않으며, 이 summary에는 portfolio alternative, candidate ID, attack
  또는 membership 권위를 넣지 않는다.
- 위와 구별되는 최고 점수 최소 해법 집합은 `pc.score-minimals`가 소유한다. 각
  pattern에서 score-only 최고 candidate row를 만든 뒤 minimum-cardinality cover와 모든
  동률 alternative를 계산하되 attack을 equality·membership·정렬에 사용하지 않는다.
  GUI/명시적 CLI는 portfolio 내부 ID나 조합 문자열 대신 전체 해법과 같은 기존 field
  board 목록 및 bounded paging으로 member와 alternative를 보여준다.
- Build probability 집계가 옵션을 받았어도 예전 aggregation/cache authority를 재사용하는
  문제. candidate variant 확률을 더하지 않고 coverage row의 OR-union으로 pattern을 한
  번만 집계하며, 동일한 pattern universe/weight model에서 full-universe 확률, PC 조건부
  확률, 실패 pattern, count와 per-solution availability/completeness를 원자적으로 만든다.
- 분산 PC/Build 결과가 같은 pattern count만으로 다른 universe나 weight authority를
  현재 coordinator에 합치거나, 중복 authority field와 dirty tail padding을 정규화한 뒤
  정상 결과처럼 받아들이는 문제. piece source, universe, weight model, aggregation contract,
  denominator와 completeness는 모두 exact-one canonical field로 검증하고, 외부 bitset의
  word count와 padding은 canonicalization 전에 검사한다. 어떤 coverage도 이 검증보다 먼저
  OR-union하거나 typed evidence로 승격하지 않는다.
- count 비례 score/wire 벡터가 요청 원소 수만 사전 승인하고 allocator가 돌려준 더 큰
  capacity를 전체 live peak에 다시 포함하지 않는 문제. reserve 직후 실제 capacity와 이미
  살아 있는 입력·중간 결과·다음 투영을 함께 재승인하며, 승인 전에는 외부 row를 읽거나
  벡터를 채우지 않는다.
  queue knowledge, hold, rule, source pieces, objective, finesse 및 score option 중 하나라도
  바뀌면 request generation과 cache identity가 바뀌고 이전 aggregation은 새 결과에
  합쳐지지 않아야 한다. 실행 시작 시 고정한 aggregation snapshot과 terminal
  `build_probability_aggregation` typed field를 exact join한다. terminal field의 부재,
  중복, 비정규 값 또는 snapshot 불일치는 presenter에서 metric/해법을 숨기고 재실행을
  요구하는 fail-closed 결과가 되며, 현재 control 값으로 과거 결과를 다시 이름 붙이지 않는다.
- Build probability가 PC 탐색과 공유할 집계 경계는 구현 단계에서 source와 fixture로
  다시 분류한다. pattern universe/weight의 정규화, candidate coverage row의 OR-union,
  한 번만 세는 성공 pattern, 실패 pattern, full-universe/성공 조건부 분모, completeness와
  availability처럼 입력 domain과 수학적 의미가 완전히 같은 부분은 제품 중립 shared typed
  aggregation primitive로 추출해 양쪽이 사용한다. 반대로 Build의 fixed placement,
  setup/finesse constraint, variant provenance, Build 전용 score/objective reducer 및
  solution/portfolio identity처럼 PC와 domain·분모·선택 단위 중 하나라도 다른 항목은
  공용 집계에 넣지 않고 exclusion 사유와 소유 모듈을 compatibility ledger에 기록한다.
  이름이나 필드 모양이 비슷하다는 이유만으로 cast하거나 presenter에서 합치지 않는다.
  shared primitive의 출력도 실행 시작 시 고정한 request/options, pattern-universe 및 weight
  identity와 terminal Build result를 exact join한 뒤에만 공개하며, cache hit도 같은 전체
  identity를 증명해야 한다.
- 연속 실행·취소·다시 실행에서 이전 세대 결과가 새 요청을 덮는 문제.
- 빈 결과와 실패 결과가 같은 화면으로 나타나는 문제.

파서, 실행 coordinator, result projection, presenter, renderer, watchdog은 별도
소유자로 유지한다. 공통 계약 변경은 표면별 문자열 분기 대신 typed boundary에서
한 번 수행한다.

### 2.2 CLI-first 명령 권위와 표면 migration

CLI-first는 브라우저에서 로컬 `clearra.exe`를 실행한다는 뜻이 아니다. native CLI의
canonical argv grammar, default/validation 규칙 및 `AppRequest` lowering을 process I/O와
분리된 공유 Rust compiler로 추출하고, 같은 compiler를 native와 WASM에 각각 링크한다.
권위 흐름은 다음 하나뿐이다.

`canonical argv -> shared command compiler -> typed AppRequest -> shared application use
case -> typed AppResponse/product result`

이 변경은 이미 설계한 Discord 공개 UX를 취소하지 않는다. slash command 구조, text
command와 alias, modal 입력 흐름, localized help/error, canonical command 이름과 option
노출은 그대로 보존한다. CLI-first는 그 UX **아래**에서 default, validation, query lowering,
실행과 결과 의미의 권위를 하나로 만드는 강화다. Discord text/slash/modal layer는 플랫폼
입력을 canonical argv token으로 옮기고 도움말과 상호작용을 표현할 수 있지만, 같은 값을
독립 규칙으로 다시 해석하거나 `AppRequest`를 직접 만들 수 없다. 따라서 이 migration을
이유로 기존 Discord command를 legacy 문법으로 되돌리거나 modal/help를 삭제하지 않는다.

표면별 책임은 다음과 같이 제한한다.

- native CLI binary는 argv 수집, 표준 입출력, exit code, 언어와 text/JSON/document
  renderer를 소유한다. 문법과 `AppRequest` 의미는 공유 compiler에 위임하며, 제품
  command를 Web 전용 parser로 재위임하지 않는다. CLI process E2E를 모든 표면의 첫
  acceptance 기준으로 삼는다.
- Pages GUI는 form state를 escaping이 끝난 canonical argv token 배열로 만드는 input
  adapter와 typed 결과 presenter만 소유한다. 브라우저는 로컬 binary를 호출할 수 없으므로
  Worker/WASM 안에 같은 compiler와 application boundary를 컴파일해 호출한다. 별도
  `WebCommandParser`가 제품 기본값, count/objective, query, resource policy 또는
  `AppRequest`를 다시 조립하지 않는다. 기존 GUI 변경 중 field/board renderer, paging,
  CTK와 watchdog처럼 presentation 책임인 수정만 유지하고, Discord 제품 의미를 GUI에
  복제한 request/result assembly는 제거한다.
- Desktop GUI도 form DTO에서 별도 `SearchProblem`을 만들지 않고 동일한 canonical argv
  token 배열을 native host에 전달한다. host는 shared compiler를 한 번 호출하고 typed
  result를 돌려준다. Web과 Desktop의 차이는 transport와 renderer capability뿐이다.
- Discord slash/text adapter는 interaction을 canonical argv로 변환한 뒤 direct 및 Cloud
  양쪽에서 CLI의 versioned JSON 출력을 실행·수신한다. Discord capability registry는
  command/help 노출, localized modal field metadata와 i18n, 권한/크기/timeout/attachment
  같은 플랫폼 안전 정책만 소유한다. Discord interaction adapter는 modal session과
  응답 수집을 소유하되 그 결과를 argv로만 내린다. semantic parser/query lowering,
  검색, score/coverage 집계, portfolio 선택을 재구현하지 않는다. canonical 첫
  portfolio와 stable candidate order는 typed product result가 이미 확정하며 Discord는
  이를 표시할 뿐이다. token 배열을 shell 문자열로 다시 합치지 않으며 process exit,
  schema version, terminal status와 payload completeness를 모두 확인한다.
- `AppResponse` 및 versioned typed product result가 성공, 빈 결과, 완전성, availability,
  score, coverage, solution family와 portfolio paging의 유일한 의미 권위다. CLI text,
  CLI JSON, GUI board, Discord message는 그 payload의 서로 다른 projection일 뿐이며,
  presenter가 빠진 값, raw `ctk1`, candidate ID 또는 현재 form state로 결과를 보충하지
  않는다.

migration은 한 번에 뒤집되 다음 순서로 증거를 쌓는다.

1. 현재 native CLI, Web, Desktop host, Discord가 만드는 command/default/query/result
   matrix를 fixture로 동결한다. 의도된 차이는 bare-PC legacy 출력 및 표면 안전 제한뿐이며,
   나머지 차이는 회귀로 분류한다.
2. pure command compiler를 추출해 native CLI가 먼저 사용하도록 바꾸고 canonical 제품과
   bare-PC 호환 E2E를 통과시킨다. compiler는 filesystem, stdio, browser, Discord,
   renderer 또는 process 실행에 의존하지 않는다.
3. Pages Worker/WASM과 Desktop host를 같은 argv/compiler 경계로 옮긴 뒤 기존 제품별
   GUI request builder와 Web-only semantic parser를 제거하거나 transport-only adapter로
   축소한다.
4. Discord direct executor와 Cloud gateway를 같은 CLI JSON 계약으로 옮긴 뒤 Discord
   내부의 semantic query lowering, 탐색/집계/대표 선택 구현을 제거한다. slash/text/modal/
   help adapter와 canonical command registration은 유지한다. direct와 Cloud는 같은 argv 및
   typed JSON fixture에서 byte-equivalent 의미 payload를 내야 한다.
5. 마지막으로 product ingress/surface를 보는 serial/distributed, projection 및 completion
   branch를 제거하고, compiled query와 typed evidence capability만으로 실행 계획을
   선택한다. old path가 조용히 되살아나지 않도록 architecture/static dependency gate를
   추가한다.

다음 migration 검증을 focused gate로 둔다.

- bare 호환 PC와 함께 최소한 `pc minimals`, 전체 해법, `pc score`,
  `pc score-minimals`, replay 및 Build probability를 포함해 둘 이상의 표면이 공개하는
  canonical command는 동일 입력에서 같은 normalized token vector를 만든다. GUI에서
  제외하는 `pc saves`와 `pc best-save`는 native CLI와 Discord adapter 사이의 argv parity를
  검증하고 Pages/Desktop GUI에는 해당 argv producer가 없음을 별도로 검증한다.
- 같은 canonical argv를 native와 WASM compiler에 넣으면 `AppCommand`, query defaults,
  problem/result identity, resource request 및 product result contract가 fieldwise 동일하다.
- native bare `pc`는 동결된 v0.7.4 호환 fixture를 지키고, named subcommand나 알 수 없는
  option을 generic queue/field로 오인하지 않는다. GUI/Discord source에는 bare-PC
  compatibility lowering이 없어야 한다.
- `pc minimals`는 항상 `CountUnique`로 컴파일되고 override를 거부하면서도, 0개·1개·여러
  개의 최소-cardinality portfolio tie를 정확히 증명한다. GUI/명시적 CLI의 next/previous,
  cancel/restart 및 terminal total count와 Discord canonical-first 결과를 같은 result-bound
  fixture로 검증한다.
- 동일 typed request의 serial/distributed 실행이 ingress와 surface를 바꿔도 같은 ordered
  solution identities, coverage, objective, completeness 및 zero-result terminal을 만든다.
- CLI JSON schema/version/완전성 오류와 알려지지 않은 result kind는 GUI와 Discord에서
  fail-closed하며, presenter가 계산으로 복구하지 않는다.
- Discord slash registration, text alias, modal field와 localized help snapshot은 migration
  전의 승인된 canonical UX와 같고, 각 입력이 만드는 argv만 shared compiler parity
  fixture로 추가 검증한다.
- Build probability와 PC가 공유한다고 판정한 각 aggregation primitive는 같은 universe,
  weights와 coverage fixture에서 fieldwise 같은 typed summary를 만든다. exclusion ledger의
  Build-only 차원은 공용 타입에 유입되지 않고 전용 reducer가 소유한다. option/cache/request/
  terminal identity 중 하나를 바꾼 negative fixture는 exact join을 거부한다.
- static architecture test는 GUI/Discord의 `AppRequest` 직접 조립, Web-only 제품 semantic
  parser, Discord search/reducer, surface/product-origin 기반 executor branch 및 core의 UI
  의존을 금지한다.

### 2.3 GUI, 결과 paging, CTK와 watchdog

- 기본 상단 메뉴는 PC, Setup, Build probability, Damage, Spin Finder, CTK,
  Player의 7개만 노출한다. 고급 route는 삭제하지 않되 기본 메뉴에서 숨긴다.
- GUI의 PC 탐색 표면에서는 `pc.saves`와 `pc.best-save` 입력, tab, 결과 route 및 도움말
  노출을 제거하고 canonical argv도 생성하지 않는다. 저장된 UI state나 과거 deep link가
  이 제품을 가리키면 다른 PC 모드로 조용히 바꾸거나 실행하지 않고 GUI 미지원 표면으로
  명시한다. 이는 GUI 복잡도 축소일 뿐이므로 native CLI와 Discord의 saves/best-save 명령,
  shared command compiler의 문법, typed result 및 core capability는 그대로 유지하고 각각의
  process/adapter 회귀 테스트를 계속 실행한다.
- 독립 Render 화면은 CTK에 합친다.
- GUI/명시적 CLI의 portfolio tie는 canonical candidate ID 오름차순으로 모든
  후보를 bounded paging한다. score, 최소 해법 수, 동일 확률 등 최종 선택 축의
  모든 tie에 같은 규칙을 적용한다.
- score tie에는 attack을 혼합하지 않는다. Discord는 가장 작은 양의 canonical
  candidate ID 하나로 고정한다.
- `pc.score` 화면은 기존 전체 해법 gallery와 동일한 field 우선 renderer, page
  loader와 export 경계를 사용해 모든 normalized solution field를 보여 준다. 각 board에
  그 필드의 full-universe 평균 score를 붙이고, 상단에 overall score를 별도로
  표시하며 covered-pattern 조건부 평균은 진단으로만 둔다. `pc.score-minimals`는
  score-optimal minimum-cover alternative와 그 member family만 소유하며, 두 화면 모두
  internal candidate ID, `ctk1` 문자열 또는 attack을 사용자용 라벨로 표시하지 않는다.
- CTK와 Discord는 page당 500 ms, 같은 frame 수, 주석 위치와 줄바꿈을 사용한다.
- 빈 셀에는 낮은 불투명도의 grid를 유지하고, 같은 색이면서 같은 owner인 인접
  셀 사이의 내부선만 제거한다. field와 active operation은 동색이어도 경계를
  보존한다.
- `127.0.0.1:8790`과 개발 GUI `4194`를 1분마다 확인한다. 해당 port listener,
  watchdog 소유의 진행 중인 startup 또는 같은 명령의 기존 process가 하나라도 있으면
  활성 세션으로 간주해 재시작하지 않는다. 모두 없을 때만 단일 mutex와 Task Scheduler
  `IgnoreNew`로 중복 PID를 막고 `node.exe`/`ssh.exe`를 shell 중계 없이 숨김 창으로
  재실행한다. SSH 자체 keepalive와 연결 실패 종료를 사용한다.

### 2.4 v0.8.0 Go 조건

- 위 결함별 최소 reproducer와 회귀 테스트가 통과한다.
- 최소·전체·save·score·Build의 Geometry 경로를 포함한 모든 실행 경로가 terminal 상태
  또는 명시적 취소로 끝나며, zero-result도 실패나 무한 `preparing`으로 표시되지 않는다.
- native CLI의 shared compiler가 canonical argv/AppRequest의 유일한 의미 권위이며 Pages,
  Desktop과 Discord에는 독립 query/SearchProblem/product-result assembler가 없다. 브라우저
  WASM compiler와 native compiler의 fieldwise parity 및 Discord direct/Cloud CLI JSON parity가
  동결 fixture에서 통과한다.
- v0.7.4 bare minimum-cover와 canonical `pc minimals`가 같은 ILC algorithm identity,
  normalized concrete candidate family, coverage 및 exact minimum-cover 의미를 내고, 각각의
  문서화된 CountAll/CountUnique 계수 정책과 공개 출력 경계만 다르다. `pc minimals`의
  CountUnique와 모든 optimal portfolio tie paging이 독립적으로 검증된다. `IIOOO` 고정
  fixture에서 v0.7.4형 bare CountAll, Web command text, Desktop exact argv와 native CLI가
  동일한 4개 normalized candidate, 4개 coverage row, 최소 cardinality 1 및 네 개의 단일-member
  alternative를 내야 한다. Desktop transport는 argv 밖의 `count_policy`를 무시하지 않고
  unknown DTO authority로 명시적으로 거부해야 한다.
- worker 수, surface, named-product ingress 또는 projection 선택이 해법 의미를 바꾸지
  않는다. serial fallback과 distributed execution은 성능 경로만 다르고 typed terminal
  payload는 동등하며 product-origin 실행 branch가 남아 있지 않다.
- 분산 wire와 coordinator는 count 비례 reserve의 실제 capacity를 whole-live memory
  authority에 재결속하고, aggregate 및 row bitset의 non-zero padding, authority field의
  누락·중복·비정규 정수/불리언, 같은 cardinality의 foreign universe/weight/source를 commit
  전에 거부한다. public aggregate만으로 누락된 product-private evidence를 합성하지 않는다.
- `pc.score`는 complete normalized solution field family의 모든 member와 member별
  full-materialized-universe 평균(miss=0), covered/pattern count, completeness 및 별도 overall
  score를 typed payload로 낸다. GUI는 이 typed 값을 재계산하지 않고 기존 solution
  gallery에 board+평균으로 투영한다. `pc.score-minimals`의 score-optimal 최소 해법
  family와 두 계약이 타입·renderer·CLI JSON에서 서로 바뀌지 않으며, internal ID/attack이
  `pc.score` gallery에 노출되지 않는다. Build probability의 union 및 가중 집계는
  serial/distributed와 Web/Desktop에서 byte-equivalent typed payload를 만든다.
- GUI source, generated navigation, help와 runtime command에는 `pc.saves` 및
  `pc.best-save`가 없고 stale GUI state는 명시적 unsupported-surface로 끝난다. 같은 candidate
  SHA의 CLI/Discord catalog, help, process/adapter E2E와 core registry에는 두 capability가
  그대로 존재하고 실행 가능하다.
- Build probability는 compatibility ledger에서 승인된 PC 공용 aggregation primitive만
  shared typed boundary로 재사용한다. 제외된 Build-only 의미는 전용 owner에 남고,
  request/options, universe/weights, cache 및 terminal result exact join의 positive/negative
  fixture가 모두 통과한다.
- CLI process E2E가 먼저 통과하고 Pages/Desktop/Discord adapter acceptance가 같은 typed
  결과와 CTK golden을 사용한다. Discord registry는 노출/i18n/platform safety 외 의미를
  소유하지 않으며 기존 slash/text/modal/help/canonical command UX snapshot을 유지한다.
- v0.7.4 대비 의도하지 않은 기능 삭제가 없다.
- v0.8.0에는 새 PC4 온라인 기능이나 정적 베타 제거를 넣지 않는다.
- candidate SHA에서 canonical full gate를 정확히 한 번 수행해 통과한다.

## 3. 테스트와 배포 파이프라인

### 3.1 테스트 계층과 canonical gate

- 평상시에는 변경 영향에 해당하는 focused unit/contract/static/surface 테스트만
  실행한다.
- component acceptance는 실제로 바뀐 Pages, Desktop, CLI, Discord, Cloud
  component에만 수행한다.
- full ReleaseAcceptance는 frozen exact-main SHA의 배포 직전에 한 번만 실행한다.
- tag publication은 같은 run/attempt의 accepted artifact와 evidence를 검증해
  재사용하며 test/build를 반복하지 않는다.

기존 Foundation/Sanitizer/Rust/Pages의 의미상 stage 집합은 유지한다. 실제 GitHub
Actions timing을 evidence에 기록하고, stage 중앙값을 이용한 longest-processing-time
고정 shard map으로 tail을 줄인다. `NoProductDebt`, `AdversarialCorrectness`,
`DesktopHost`는 독립 leaf로 나누고, Rust/ProductE2E/Render는 sealed build artifact를
공유해 테스트나 컴파일을 중복하지 않는다. mutable target, port 또는 process-global
상태를 공유하는 테스트는 직렬 owner에 남긴다. fan-in은 닫힌 stage 목록, exact
SHA, artifact digest와 deferred evidence owner를 검증한다. 여섯 acceptance leaf의
cache는 모두 restore-only이며 job 종료 시 저장·압축하지 않는다. Windows product
build는 CLI를 restore-only reader, GUI를 유일한 writer로 둔다. 두 job 모두 lock
fingerprint와 exact source SHA를 포함한 key를 사용하고, 직전 exact-SHA cache와 기존
lock-only `product-v2` cache를 순서대로 복원할 수 있어야 한다. cache는 현재 source의
실제 build, artifact digest 또는 canonical evidence를 대체하지 않는다.

최초 shard 구조 변경에 한해 비권위 benchmark를 한 번 허용한다. warm/cold hosted
runner를 모두 기록하고, leaf가 중앙값의 약 125%를 지속적으로 넘지 않으며 최신
canonical baseline보다 wall time을 30% 이상 줄이는 것을 목표로 한다. 테스트 삭제,
skip 또는 중복 실행으로 성능 조건을 맞추지 않는다.

허용된 비권위 benchmark run `33551509127`은 13분 22초로 직전 25분 56초 기준보다
약 48% 짧았고 모든 job이 통과했다. 당시 Foundation은 9분 24초, Windows GUI는
12분 23초였으며 GUI의 11분 26초 build 중 Cargo release가 10분 41초를 차지했다.
이는 `product-v2` 첫 cache miss 뒤 약 523 MB cache를 저장한 cold run이었다. 따라서
Foundation을 위 세 leaf로 더 나눈 구조와 exact-SHA product cache의 최종 성능 판정은
새 frozen SHA의 단 한 번뿐인 canonical run에서 한다. warm run에서도 GUI가 계속
critical tail이면 sccache나 runner 등은 다음 버전의 별도 측정 과제로 넘기고,
v0.8.0에서 compiler profile이나 제품 feature를 바꾸지 않는다.

### 3.2 변경 영향과 선택 배포

workflow는 `pages`, `desktop_gui`, `cli`, `discord_gateway`, `heavy_cloud_runtime`,
`pc4_lookup_service`, `pc4_activation_manifest`, `release_infrastructure` 변경 벡터를
계산한다. 변경되지 않은 component는 마지막 accepted digest와 deployment receipt를
carry-forward한다. 공통 계약 또는 release infrastructure 변경은 보수적으로 모든
관련 component를 선택한다.

GUI-only, CLI-only, Discord-only, snapshot-only 수정은 관련 없는 build, full gate
또는 배포를 실행하지 않는다. 다만 v0.8.0의 누적 변경은 모든 기존 표면에 영향을
주므로 최초 v0.8.0 배포에서는 Pages, Desktop/CLI, Oracle/Cloud runtime 및 Discord를
모두 배포·관찰한다.

## 4. v0.9.0 PC4 제품 계약

### 4.1 제품 의미

`muse918/tetris-4lpc-mdp-vstar-policy`는 전체 해법 TB가 아니라 상태별 V\*와 하나의
policy action을 제공한다. 따라서 제품명은 **PC4 V\* Policy Advisor**이고,
`solution_family=false`, `solution_count=null`, `completeness_claim=none`을 항상
명시한다. Setup, Pattern, 모든 PC 해법 열거, exact pruning 또는 score/tie 권위로
사용하지 않는다.

upstream u16 policy action은 piece ID와 `graph.edges(field, piece)`의 edge index이며
rotation, x/y, kick 또는 input sequence가 아니다. GUI/CLI가 기존 placement 표현을
보여주기 전에 `PcPolicyPlacementMaterializer`가 선택 profile의 Clearra geometry를
열거해 source/target field와 일치하는 합법 placement를 재구성한다. 일치 항목이
없으면 `data_invalid`, 여러 항목이 같은 target occupancy로 접히면 canonical candidate
ID가 가장 작은 하나를 **Clearra 재구성 배치**로 표시한다. upstream이 구체 kick/input
sequence까지 선택했다고 주장하지 않는다.

별도 Krylov snapshot은 fixed-policy 생존/death projection이며 전체 해법, Setup 후보,
policy action, 최적 n-PC 성공 확률을 제공하지 않는다. v0.9.0에서는 이를 조회하거나
결과 선택에 사용하지 않는다. 후속 정확 n-PC 성공 확률은
`PcNextProbabilityProvider`, fixed-policy 생존 모델은 `PcSurvivalModelPort`로 의미를
분리하고 둘 다 비활성 내부 포트로만 예약한다. 어느 쪽도 v0.9.0 공개 기능, 데이터
조회, registry capability 또는 fallback에 추가하지 않는다.

| 기능/자산 | v0.9.0 판정 | 공개 의미 |
| --- | --- | --- |
| 현재 state의 policy action 하나와 V\* | 다섯 profile 자격 뒤 활성 | Policy Advisor |
| 전체 PC 해법/tie family | 미지원 | 기존 exact PC search가 소유 |
| Setup/Pattern search 또는 pruning | 미지원 | 기존 exact search가 소유 |

### 4.2 공개 명령과 표면

`pc policy`는 rule, field, hold/current/preview, bag remainder로 **현재 관측 상태의
upstream policy action 하나와 V\***를 반환한다. bag remainder는 다음 reveal의 가능한
집합이지 순서가 아니므로, 임의의 canonical reveal을 골라 현재 PC 끝까지 하나의
continuation인 것처럼 표시하지 않는다. 다음 piece가 공개되면 새 boundary로 다시
조회한다. 전체 continuation이 필요해지는 후속 버전에서는 reveal마다 갈라지는 bounded
decision-tree 계약을 별도 capability로 설계하며, provenance로 완전한 ordered hidden
reveal을 실제로 아는 입력만 단일 관측 경로로 연장할 수 있다.

- GUI는 기존 beta tablebase control의 위치를 유지하되 beta 문구를 모두 제거하고
  Policy Advisor 명시 opt-in으로 바꾼다. 현재 PC policy만 제공하고 Krylov/n-PC
  자산은 읽지 않는다. rule dropdown에는 `no-kick`을 추가한다. Web/Desktop persisted
  migration은 기존 `tablebaseEnabled` 값과 무관하게 새 `policyAdvisorEnabled=false`로
  시작한다. legacy opt-in을 새 외부 HF read 동의로 승계하지 않고, 사용자의 새 명시
  동작 뒤에만 최초 Policy request를 허용한다.
- native CLI는 `pc policy`를 generic Web Product parser보다 먼저 인식한다.
  `pc survival`은 v0.9.0 명령이 아니며 기존 PC search로 낮추지 않고 unknown-command로
  fail-closed한다.
- Discord는 명시적인 policy 경로와 필요한 modal을 제공한다. hit, miss, 장애
  모두에서 heavy PC/Setup Cloud Run을 자동 실행하지 않는다.
- 기존 정확 PC 탐색은 독립 제품으로 남는다. policy 실패 시 자동 fallback하지
  않고 사용자가 정상 PC 명령을 별도로 실행할 수 있게 안내한다.

### 4.3 canonical boundary와 bag

`BoundaryContextV1`은 schema ID, rule profile, canonical 10x4 field/u40, hold state,
active/current, ordered preview, non-empty unique `bag_remaining`,
`placements_since_pc_boundary` (`pc_phase`, 0..9), bag/source provenance, request
generation과 snapshot identity를 가진다. upstream `layer0..9`는 field 높이가 아니라
현재 PC cycle의 placement step이므로 이 값이 layer 선택의 필수 권위다.

- hold가 있으면 unordered `{hold,active}`와 정확히 5개의 ordered preview를 쓴다.
- empty hold이면 active를 포함한 queue 7개, 즉 첫 두 piece를 upstream unordered
  `{hold,current}`로 정규화하고 다음 5개를 ordered preview로 사용한다. upstream
  qstate와 exhaustive equivalence/KAT가 통과하기 전에는 활성화하지 않는다.
- policy preview는 명시 입력을 우선하며 Player 또는 generator provenance가 보존될
  때만 생성할 수 있다.
- `bag_remaining`만으로 hidden reveal 순서를 만들지 않는다. policy 응답은 현재 action,
  V\*, snapshot provenance와 다음 조회에 필요한 공개 context를 반환하며, 새 reveal 뒤
  client가 boundary를 갱신해 재조회한다.
- Player history처럼 PC 직후부터의 placement 수를 증명하는 source에서는
  `placements_since_pc_boundary`를 자동 도출한다. 임의 GUI field, CLI 또는 Discord
  입력에서 유일하게 알 수 없으면 prompt/명시 옵션을 요구하고
  `needs_boundary_context`로 실패한다. field cell count나 높이로 추측하지 않는다.
- bag remainder는 provenance로 유일하게 추론되면 자동 입력한다. 그렇지 않으면
  GUI prompt, CLI TTY 또는 Discord modal로 남은 piece를 묻는다. raw bag round나
  qid는 묻지 않는다. noninteractive CLI는 `--bag-remaining`을 요구하며 추측하지
  않는다.

### 4.4 독립 타입과 SRP

Policy와 후속 Probability/Survival seam은 기존 `pc.chance`, `PatternBitSet`,
`CoverageRow`, `PcResultProjection`, `AppTablebaseSession`을 재사용하지 않는다.

- Policy: `AppCommand::PcPolicy`, `QueryEnvelope::PcPolicyBoundary`,
  `ProductCapabilityContract::PcPolicy`, `PcPolicyLookupPort`,
  `pc-policy-advice.v1`.

후속 확장 seam은 `PcNextProbabilityProvider`, `PcSurvivalModelPort`,
`KrylovSurvivalSnapshotAdapter`로 분리한다. 이 타입들은 v0.9.0의 `AppCommand`,
`QueryEnvelope`, `ProductCapabilityContract`, registry, surface route 또는 presenter에
연결하지 않는다. adapter는 discovery metadata와 synthetic fixture를 fail-closed로
해석하는 내부 feature-off 구현까지만 허용하며 실제 HF data를 production에서 읽지
않는다.

boundary canonicalizer, manifest resolver, policy reader, placement materializer, resumable
lookup machine, request coordinator, presenter 및 telemetry는 별도 책임으로 둔다. Krylov
parser/projector는 위 비활성 adapter 내부에 남기고 Policy machine과 공유하지 않는다.
v0.8 registry v1은 동결하고 v0.9 registry delta/v2를 추가한다.

기존 solver `AppContext::run`은 동기 경계이므로 그 안에서 browser Fetch나 native HTTP를
시작하지 않는다. `clearra-app`이 소유하는 별도 `PcPolicySessionPort`는
`start(PcPolicyRequest)`, `provide_range(session_id, generation, request_id, bytes)`,
`cancel(session_id, generation)`을 제공하고 `PcPolicyExecutionStep::{NeedRange, Complete,
Error, Cancelled}`로 수렴한다. `NeedRange`는 snapshot/artifact/offset/length와 opaque
request ID를 포함한다. supplied bytes는 session, generation, request ID, snapshot과
정확히 일치할 때만 소비하며 stale reply는 결과를 바꾸지 않는다. cancel은 terminal이고
그 뒤 byte 공급이나 Complete를 금지한다.

advisor core 자체는 순수 resumable machine이며 위 application port만 state와 수명을
소유한다. Browser Worker, Desktop native host, native CLI 및 전용 lookup service는
AppCommand를 host에서 가로채거나 `AppContext::run` 안에 HTTP를 넣지 않고 모두 같은
port를 각자의 비동기 Range adapter로 구동한다. `AppCommand::PcPolicy`는 typed policy
request/result 계약을 소유하되 blocking network의 소유자가 되지 않는다.

공통 typed error는 `needs_boundary_context`, `invalid_preview_length`,
`invalid_bag_state`, `state_not_in_model`, `dataset_unavailable`, `rate_limited`,
`snapshot_mismatch`, `data_invalid`다. machine JSON은 code와 구조화 필드만 포함하고
인간 설명은 presenter가 소유한다. NaN, Infinity 또는 범위 밖 V\*는 clamp하지 않고
`data_invalid`로 실패한다. 후속 확장 error는 공개 policy error enum에 미리 섞지 않는다.

## 5. PC4 데이터와 실행 토폴로지

### 5.1 Policy 자격 조건

v0.9.0은 muse918가 `srs-plus`, `srs`, `srs-x`, `jstris-180`, `no-kick` 다섯 프로필의
완전한 graph/policy/value/field-order 자산을 게시할 때까지 release-blocked다. 일부
프로필만 준비된 상태는 staging할 수 있지만 활성화하지 않는다. 각 profile manifest는
graph, offsets, hash index, policy, V\*, state order, rule/kick, hold/bag semantics를
하나의 generation으로 결합한다. graph만 바꾸거나 기존 policy를 다른 kick graph에서
재해석하지 않는다.

2026-09-02 조사 기준 공개 policy dataset은 777,839,676,792 bytes/46 files의 단일
flat generation이고 다섯 profile identity나 profile manifest가 없다. `graph.bin`,
`graph_offsets.u32.bin`, `field_hash_to_id.v1.bin`은 실제로 존재하고 immutable revision의
Range 요청도 206으로 동작한다. `FHIDIDX1`은 15,185,706개의 8-byte record,
`GOFFIDX1`은 같은 field count의 `(count + 1)` u32 offset을 가진다는 header/size 사실을
독립 검증할 수 있어 bounded random access의 기술적 가능성은 확인됐다.

그러나 dataset README는 여전히 `graph.bin`이 없다고 쓰고, loader spec으로 연결한
`muse918/zxcl-pc-jstris-tbp/docs/DATA.md`는 그 저장소에 없다. 대응 문서는
`muse918/zxcl-pc/docs/DATA.md`에서 찾을 수 있지만 dataset generation이 이를 직접
권위로 봉인하지 않고 helper 생성기·profile·row order를 한 manifest로 묶지도 않는다.
현재 generation을 임의로 `srs-plus`로 간주하거나 다른 네 profile에 재사용하지 않는다.
promotion은 helper header, count, 정렬, bounds와 graph/policy/value/order 결합을
독립 검증한 뒤에만 가능하다.

사용자 제공 `srs_plus_srs_x_kick_tables.json`은 호환성 fixture와 upstream 생성 요청
사양의 설계 증거로 사용하며 단독 제품 권위로 사용하지 않는다. Clearra 소유의
대체 policy dataset을 만들지 않는다.

dataset 표시는 MIT이지만 `graph.bin` 원천인 randomidiot13/hydra와 관련 생성 도구는
GPL 계열이다. 이는 법률 결론이 아니라 release provenance 확인점이다. dataset 허가가
배포되는 graph/helper index까지 포괄한다는 증거를 남기고, 포맷·알고리즘 사실을
독립 구현하며 GPL 구현 코드를 Clearra에 복사하지 않는다.

### 5.2 후속 Krylov 상태 공간 분석과 비활성 adapter 조건

2026-09-01에 별도 공개된 Krylov dataset을 2026-09-02에 HF API, README, file 목록,
`model.json`과 commit 목록으로 다시 확인했다. 최신 공개 `main`의 관찰 revision은
[`519a0cb1...`](https://huggingface.co/datasets/muse918/tetris-4lpc-survival-krylov/tree/519a0cb1b3897d0e7b0ab4ce974df2925bca6424)다.
공개 history에는 initial commit과 이 upload revision만 있고, 이 재확인 시점에 더
새로운 state-space generation은 없었다. 이는 조사 evidence일 뿐 제품 source 상수나
영구 pin이 아니다. snapshot은 `pi_policy_v3`, `k=14`, layer-0 quotient 817,740 states를
사용하며 다음 자산을 포함한다.

- `state.bin`: 1,104 bytes. 논리 u64 magic은 `0x535552564b525931` (`SURVKRY1`)이고
  raw little-endian octet은 `31 59 52 4b 56 52 55 53`이다. 뒤에 state count, `m=14`,
  beta, lambda, 14 colsums와 ragged Hessenberg column이 온다.
- `basis.f64.bin`: 98,128,800 bytes. 실제 크기는
  `15 * 817,740 * 8`이므로 Arnoldi resume용 `m + 1` vector까지 15개가 저장된다.
- `dpi.f64.bin`: 6,541,920 bytes, 즉 state별 f64 one-PC death hazard 817,740개.
- `model.json`과 `survival_table.csv`: aggregate uniform/stationary start 요약 및
  N=1..100 표.

이 업데이트에서 말하는 **상태 공간 해석**의 범위는 명확히 제한한다.

- `basis.f64.bin`과 `dpi.f64.bin`의 position은 Policy dataset의 기존
  `layer0q_pruned` row order에 맞춘 투영 좌표다. 별도의 field/qstate 역색인이나
  합법 배치 목록을 추가한 것이 아니다.
- `state.bin`은 Arnoldi를 이어 계산할 Hessenberg/Krylov snapshot이다. 817,740-state
  transition graph, 전체 해법 table, Policy action table 또는 Setup 역색인이 아니다.
- `basis`와 `state`로 계산할 수 있는 값은 주어진 layer-0 row에 대한 과거 fixed-policy
  death/survival projection이다. 현재 boundary를 row에 연결하는 decoder, 최종 Policy
  generation과의 원자적 호환성, profile identity와 state별 오차 계약은 제공하지 않는다.

따라서 v0.9.0 적용 판정은 다음처럼 고정한다.

| 적용 지점 | v0.9.0 판정 | 이유 |
| --- | --- | --- |
| Policy Advisor의 action/V\* 조회 | 미적용 | Policy dataset만으로 완결되며 Krylov는 action을 제공하지 않음 |
| 전체 PC 해법 또는 Setup 후보 조회 | 미적용 | placement family/역색인/완전성 증거가 없음 |
| 공개 n-PC 성공·생존 확률 | 후속 과제로 보류 | `pi_policy_v3`, layer-0 전용, state별 certified error와 최종 Policy binding이 없음 |
| 내부 SRP seam | 적용 | descriptor/parser/projector와 disabled provider를 synthetic fixture로 검증 가능 |
| 연구 drift/호환성 evidence | 적용 | 공개 `main`의 변화와 Policy row-order/profile 결합 가능성을 비권위로 추적 가능 |

즉 v0.9.0에 가져오는 것은 **형식 이해를 캡슐화한 비활성 adapter와 negative test**뿐이다.
실제 HF Krylov bytes, 관찰 revision, 수치 결과, network route 또는 공개 command는
가져오지 않는다. 이 결정은 n-PC 기능을 후속 과제로 미룬 제품 범위와 일치하며, 새
dataset upload만으로 production 기능이 켜지는 경로를 만들지 않는다.

dataset README는 basis를 `k * n_boundaries`, 즉 14 vectors로 설명하므로 실제 bytes와
불일치한다. 공개
[`muse918/zxcl-pc` source](https://github.com/muse918/zxcl-pc/blob/1f9dffa691b7a519f46028f5d56728873f406ecf/src/main.rs#L9449-L9458)는
첫 14개 vector만 현재 `H_14` projection에 사용하고 15번째를 resume용으로 저장하는
[state 형식](https://github.com/muse918/zxcl-pc/blob/1f9dffa691b7a519f46028f5d56728873f406ecf/src/main.rs#L9657-L9743),
[per-boundary projection](https://github.com/muse918/zxcl-pc/blob/1f9dffa691b7a519f46028f5d56728873f406ecf/src/main.rs#L9860-L9921),
[resume 검증](https://github.com/muse918/zxcl-pc/blob/1f9dffa691b7a519f46028f5d56728873f406ecf/src/main.rs#L10110-L10184)과
다음 재구성식을 보여준다.

```text
w_N = beta * sum(j=0..N-1) H^j e_1
p_die(s, N) ~= sum(i=0..13) basis[i, s] * w_N[i]
```

그러므로 기술적으로는 `stored_basis_vectors=15`, `queried_basis_vectors=14` reader를
독립 구현할 수 있다. 현재 immutable snapshot의 Range 검산에서 qid 48은
`dpi=0.004761874675750732`, N=2 약 `0.004893205244707640`, N=10 약
`0.006672970472855619`, N=100 약 `0.027105388364420363`으로 독립 Range reconstruction을
수행했고 N=1에서 `dpi = beta * basis[0,s]` invariant를 확인했다. N>=2 수치는 공개
expected와 대조한 확정 KAT가 아니라 future qualification seed이며, 이 값과 revision은
제품 상수가 아니다. GPL source는 format/algorithm 사실 확인에만 사용하고 구현 코드를
복사하지 않는다.

계산 가능성과 제품 자격은 분리한다. 이 snapshot은 최종 `pi_policy_v5_f64`가 아닌
미수렴 `pi_policy_v3` 기반이고, 최종 V\*와의 0.28% aggregate 교차검증은 policy
동일성이나 state별 오차 증명이 아니다. N=1 `dpi`도 frozen source policy에서만 직접
hazard이며 N>=2 projection에는 per-state certified error bound가 없다. uniform 또는
quasi-stationary aggregate curve를 임의 사용자 boundary 결과로 대신 반환하지 않는다.
또한 독립 `qstate_key -> qid` index, profile identity 및 policy/row-order compatibility
manifest가 없어 Clearra canonical boundary를 row에 연결하려면 clean-room exhaustive
equivalence/KAT가 더 필요하다.

따라서 v0.9.0은 descriptor/parser/projection core와 disabled provider를 synthetic
fixture로만 검증한다. production factory, activation manifest, registry, GUI, CLI,
Discord, network adapter 및 HF read에는 연결하지 않는다. 후속 공개 활성화에는 source
policy revision/profile/layer-0 row-order와 Krylov revision의 atomic compatibility root,
15-stored/14-queried 공식 계약, boundary row KAT, state별 수치 오차 계약, 실제 Pages
CORS/14-stride latency, 별도 command/result UX와 새 full Go gate가 모두 필요하다.

이 Krylov basis는 fixed-policy transition projection이지 quotient 동등성 증명이 아니며
전체 해법이나 Setup 역색인도 포함하지 않는다. 상태 축소 연구는 후속 과제로 둔다.
Clearra 공개 의미에만 동등한 경우 별도 파생 cache를 검토하고, 모든 해법에 보편적으로
동등하며 유의한 축소가 가능한 경우에는 upstream graph/policy 재생성을 요청한다. 둘 다
아니면 quotient 계획을 취소하고 Markov 직접 계산을 검토하며, 불가능하면 그 후속
기능에서 기존 Krylov 상태를 유지한다.

이 분기의 deferred decision contract도 미리 고정한다. “Clearra 의미 동등”은 당시
공개하려는 command/result의 canonical boundary 전체와 모든 지원 rule profile에 대해
action, materialized target field, V\*, terminal/error class가 정해진 tolerance 안에서
같다는 exhaustive 또는 증명 가능한 quotient KAT를 요구한다. tolerance는 배치·해법
family·terminal class에는 0이고, 수치 V\*에는 별도로 승인된 state별 certified bound만
허용한다. “전체 해법 보편 동등”은 upstream의 전체 합법 state/action/edge domain에서
row equivalence와 solution-family membership이 정확히 같아야 하며 허용 오차는 0이다.
“유의한 축소”의 최소 byte/state 감소율과 end-to-end Range latency 개선율은 연구를
시작할 때 workload·비용과 함께 수치로 동결하고, 둘 중 하나라도 기준에 못 미치면
upstream 재생성을 요청하지 않는다. 이 수치가 정해지기 전에는 어느 분기도 Go로
판정하지 않는다.

Markov가 불가능해 기존 Krylov 상태를 유지하는 마지막 경우의 data authority는
muse918의 공개 dataset을 계속 사용할지 개인 HF dataset을 별도로 게시할지에 대한
upstream의 명시 답변을 계획 단계에서 받을 때까지 결정하지 않으며, 답변 전에는 후속
n-PC 기능의 구현 단계로 넘어가지 않는다. v0.9.0 Policy Advisor의 state order에는
어떤 추가 quotient 축소도 적용하지 않는다.

### 5.3 snapshot 수명주기

HF SHA256 또는 commit을 제품 소스 상수로 고정하지 않는다. moving `main`은 discovery
전용이다. Policy promotion workflow가 immutable revision,
file OID/size/digest/schema/profile을 동적으로 검증해 서명된 activation manifest를
만든다. 요청은 시작 시 하나의 manifest와 snapshot을 pin하며 cache key에 generation,
revision, schema, profile, state를 포함한다. rollback은 이전 manifest로 전환한다.

Policy는 다섯 profile의 atomic generation만 활성화한다. source policy, schema,
rule/kick 또는 공개 의미가 바뀌면 자동 활성화하지 않는다.

v0.9.0 promotion workflow와 runtime은 Krylov repository를 discovery하거나 activation
manifest에 포함하지 않는다. 연구 문서의 observed revision은 실행 입력이 아니다.
향후 활성화 시에만 Policy revision/profile/source-policy ID/layer-0 row-order digest와
Krylov revision을 하나의 compatibility root로 동적으로 pin한다. data update나 moving
`main` 변화만으로 disabled provider가 활성화될 수 없다.

### 5.4 실행 위치

- Pages GUI: browser Worker/WASM shared reader가 immutable HF Range에서 Policy
  graph/index/value/action만 읽고 현재 policy를 표시한다. 실제 Pages 환경에서
  CORS/Range가 실패하면 v0.9.0을 차단하고 승인 없이 Cloud fallback으로 바꾸지 않는다.
- Desktop GUI: 같은 `PcPolicyLookupMachine`을 native host Range adapter로 구동한다.
  사용자가 Policy Advisor를 명시 실행할 때에만 HF를 직접 읽으며 Clearra server를
  호출하지 않는다.
- CLI: shared native Rust reader가 immutable HF Range에서 Policy 자산만 직접 읽는다.
- Discord: Oracle Gateway가 service-authenticated 전용 lightweight PC4 lookup Cloud
  Run의 Policy 경로를 호출한다. 공개 anonymous endpoint는 두지 않는다.
- dedicated service의 cache/derived layout은 폐기 가능한 최적화일 뿐 데이터 권위가
  아니며 모든 응답은 원본 HF snapshot provenance를 포함한다.
- 기존 8-vCPU heavy runtime은 일반 PC/Setup 검색만 소유한다.
- GUI, CLI, Discord, lookup service 어느 곳도 v0.9.0에서 survival repository를 읽지
  않는다.

policy 한 건은 전체 해법 O(1) 조회가 아니다. field-hash index, graph offset/record,
layer field block, quotient-chain ID, policy/value를 검증하는 bounded
`O(log fields + log blocks + log chains)` random access다. page cache는 round trip을
줄일 뿐 의미 권위가 아니다. Range adapter는 immutable revision URL, HTTP 206,
정확한 `Content-Range`/전체 크기, redirect 대상, short read와 non-zero Range의 200
full-body 거부, generation/revision/schema/profile/path/page cache key, bounded LRU 및
in-flight coalescing을 fail-closed로 소유한다. 전용 service는 arbitrary URL/Range
proxy가 될 수 없고 activation manifest allowlist 밖 byte를 읽지 않는다.

miss, offline, 429, timeout, truncated range, snapshot mismatch는 typed error로 끝난다.
CLI는 별도 명시 옵션 없이 offline exact search를 자동 실행하지 않는다.

### 5.5 기존 정적 베타 제거

다섯 policy profile이 qualification을 통과한 v0.9 migration에서만
`pc4-compact-exact-v12.bin`, web worker/static asset, Rust loader/runtime, CLI embed,
WASM/Discord packaging과 관련 impact mapping을 함께 제거한다. PC의 기존
`--tablebase`는 의미가 다른 policy로 alias하지 않고 typed migration error와 명시적인
`pc policy` 또는 flag 없는 exact PC search 안내를 반환한다. Setup의 기존
`--tablebase`는 Policy Advisor를 대체 기능으로 안내하지 않고 flag 없는 exact Setup
search 재실행만 안내한다. 이를 위해 accelerator enable/lowering/embed 경로는 제거하되
deprecated ingress tombstone parser는 부작용 없이 유지한다. Setup은 accelerator만
잃으며 정확 기능 자체를 삭제하지 않는다. 정적 beta와 온라인 policy를 두 개의 runtime
권위로 함께 활성화하지 않는다.

제거 감사에는 Web worker asset/runtime, static binary, Rust tablebase loader와 core
executor backend, CLI `include_bytes!`와 `--tablebase`/`--tb` accelerator routing, GUI
`tablebase_requested`/enable 상태, WASM ABI install/release export, Discord image/parser
allowlist 및 deployment impact mapping을 모두 포함한다. 일부 표면에 legacy asset
authority가 남으면 migration을 완료하지 않는다. native CLI, Web text command와 Discord
text ingress의 tombstone은 PC/Setup별 migration 안내만 반환하며 solver, HF 및 Cloud
호출이 0회여야 한다.

## 6. v0.9.0 검증과 배포

필수 검증은 다섯 profile manifest의 닫힌 집합, graph/policy/value/order 상호 결합,
u16 policy decode, profile별 합법 placement, upstream known-state KAT, layer 0..9 및
2LPC/4LPC terminal 전이, empty-hold qstate equivalence, PC phase와 bag prompt/inference,
unordered bag에서 임의 단일 continuation을 만들지 않는 계약과 reveal 뒤 재조회,
graph edge에서 Clearra placement로의 profile별 합법 materialization,
invalid-float fail-closed, 정확한 206/`Content-Range`, 200/short-read/429/timeout 거부,
Range/cache/revision pin, 실제 Pages CORS, CLI direct-HF,
Oracle-to-Cloud auth와 anonymous rejection, heavy-job 비호출, static beta 부재를
포함한다. 배포 compliance evidence에는 graph/helper index의 dataset 허가 범위와
독립 구현 provenance도 포함한다.

모든 Policy host는 동일한 `PcPolicySessionPort` contract test를 통과해야 한다. start,
다중 `NeedRange`, Complete/Error, cancel, generation 교체, stale/wrong request ID,
snapshot mismatch와 cancel 후 late bytes를 포함하고, terminal은 한 번만 발생한다.
Desktop native host는 immutable revision/206와 exact `Content-Range`, non-zero Range의
200 거부, cancellation/stale generation, Pages/CLI와의 typed result parity 및 Clearra
server 0회 호출을 별도로 검증한다. legacy `tablebaseEnabled=true` 복원 직후 Web/Desktop
Policy HF read는 0회이고, 새 opt-in 뒤에만 최초 read가 일어나야 한다. PC/Setup별
tombstone parser도 native CLI, Web text, Discord text에서 안내만 반환하고 solver/HF/Cloud
호출이 모두 0회인지 검증한다.

비활성 future seam은 synthetic descriptor/parser/projection fixture에서 817,740 states,
`k=14`, 15 stored/14 queried, ragged state 크기, overflow/non-finite 및
policy/profile/row-order binding 누락을 fail-closed로 검증한다. `state.bin`을 transition
graph나 row decoder로 취급하지 않고, basis position만으로 Clearra boundary를 추측하지
않는 negative test도 포함한다. 동시에 다음 negative evidence를 요구한다.

- native CLI와 CLI parser가 `pc survival`을 공개 명령이나 기존 PC search로 인식하지
  않는다.
- Discord catalog/modal과 GUI source/render에 survival surface가 없다.
- registry v2, public `AppCommand`, `QueryEnvelope`, capability 및 result payload에
  survival variant가 없다.
- Oracle과 lookup service는 survival capability/route/input을 인증 뒤가 아니라 fetch
  전에 거부한다.
- Policy activation manifest는 승인된 Policy repository와
  `graph/index/order/policy/value` artifact role의 닫힌 집합만 허용하고 Krylov
  repository/path/role을 거부한다.
- production provider factory, build feature, environment, secret 또는 runtime config에
  disabled provider를 등록·활성화하는 switch가 없다.
- `PcNextProbabilityProvider`, `PcSurvivalModelPort`, `KrylovSurvivalSnapshotAdapter`는
  production crate root, ABI 또는 serde/public schema에서 re-export하지 않는다.
- production activation manifest에 Krylov provider/repository/revision이 없고 최하위
  HTTP/Range adapter spy에서 모든 surface와 service의 survival HF read가 0회다.
- disabled/unqualified 상태는 data update만으로 바뀌지 않는다.

이 내부 seam 자체의 코드·negative test 실패는 v0.9.0을 막지만, 외부 Krylov dataset의
갱신·불완전성·비자격은 v0.9.0 Policy Advisor release blocker가 아니다.

현재 upstream revision에 대한 수치 검산은 research qualification evidence이며 v0.9.0
production artifact, runtime KAT 또는 release blocker가 아니다. 후속 공개 기능은 그
시점의 dynamically pinned snapshot으로 별도 full gate를 통과해야 한다.

구현과 함께 `docs/source-references.md`는 Policy dataset과 research-only Krylov source를
분리하고, `docs/app-boundary.md`는 `PcPolicy`만 공개 경계로 추가한다.
`docs/dependency-boundary.md`에는 `host -> policy use case -> pure lookup machine -> host
Range adapter`만 허용하고 app/core의 직접 HTTP를 금지한다.
`docs/product-capability-registry.md`와 v0.9 registry v2에는 `pc.policy`만 추가하며 v0.8
registry v1 fixture는 수정하지 않는다.

배포 순서는 다음과 같다.

1. v080 전용 release helper를 version-neutral v2로 일반화하되 legacy v080 evidence와
   rollback reader는 유지한다.
2. 새 typed contract, shared reader, 표면 adapter와 dedicated lookup service를 구현한다.
3. 다섯-profile Policy generation만 inert staging하고 qualification/KAT를 통과한다.
   Krylov는 synthetic future-seam test 외에는 staging하거나 package하지 않는다.
4. 정적 beta를 제거하고 dual authority가 없음을 확인한다.
5. exact v0.9.0 SHA에 canonical full gate를 실행한다.
6. 현재 live v0.8 Pages의 unique canonical attempt-1 accepted artifact를 다시 자격
   확인하고, 재빌드 없이 full file set과 public bytes를 봉인한 새 `canonical-v2`
   bracket를 만든다. v0.9 accepted SHA를 그 capture run ID와 v0.8 snapshot SHA에 결속해
   Pages forward 배포하고, candidate forward receipt와 rollback bracket receipt 및 전체
   public payload readback을 함께 검증한다.
7. CLI/Desktop와 PC4 lookup Cloud Run을 선택 배포하되 lookup은 zero-traffic/inert 상태에서
   자격을 통과한다. 최종 Discord 배포는 같은 v0.9 canonical gate가 만든 자동
   `workflow_run`만 허용하고, Pages authority 뒤 `discord-path-confirmation`, Oracle/Cloud
   승격, `discord-global-command-sync` 순서로 승인한다.
8. profile별 hit/miss, Range bytes, latency, cache, rate limit과 invalid data를 canary 및
   20분 이상 관찰한다. 이전 Policy activation manifest, Pages canonical-v2 capture
   report/exact tar, lookup Cloud Run prior revision, Oracle prior/current와 Discord
   catalog/prestage/recovery authority를 각각 독립 receipt로 read-only 검증한다.
9. v0.9 Pages restore rehearsal/validator는 실제 mutation 없이
   `current_pages_sha=<v0.9-live>`, `snapshot_sha=<v0.8-live>`,
   `snapshot_run_id=<v0.8 canonical-v2 capture run>`,
   `restore_authorization=ROLLBACK:<v0.9-live>:TO:<v0.8-live>`의 exact lineage와 sentinel을
   검증한다. 표면별 rollback authority와 main/accepted SHA가 그대로일 때만 `v0.9.0`
   tag와 immutable release를 게시한다.

다섯 profile 중 하나라도 없거나 provenance가 불완전하면 v0.9.0을 배포하지 않는다.

## 7. v0.9.x와 완료 판정

새로운 다섯-profile policy generation은 코드 변경이 없어도 항상 full gate를
실행한다. 특히 `no-kick`을 포함한 전체 generation이 완료된 경우 예외를 두지 않는다.
schema, reader, graph 의미, boundary, algorithm, source policy 또는 결과 계약 변경도
full gate 대상이다.

fast patch는 이미 qualification된 동일 schema·동일 의미 generation의 재게시,
패키징 정정 또는 동등성이 증명된 snapshot 교체만 허용한다. 엄격한 diff allowlist,
data KAT, 관련 provider/client smoke, signed manifest와 이전 full-gate authority를
요구하고, 벗어나면 자동으로 full gate로 승격한다. application version과 dataset
generation은 별도 필드로 표시하며 unchanged binary는 accepted digest를 재사용한다.

Krylov dataset 변화는 v0.9.x에서 research drift evidence만 갱신할 수 있다. fast patch,
data-only promotion 또는 manifest flip으로 공개 survival/n-PC 기능을 활성화하지 않는다.
그 기능은 별도 후속 계획에서 command/result 의미, profile coverage, state decoder,
수치 자격, surface UX를 다시 승인하고 독립 exact-SHA full gate를 통과해야 한다.

새 비공개 값이 필요하면 source나 로그에 기록하지 않고 GitHub protected environment에
정확한 secret 이름과 소비 component를 먼저 정의한 뒤 값만 사용자에게 요청한다.
OIDC/WIF를 우선하며 GUI/CLI에 HF token을 내장하지 않는다.

완료는 계획 문구나 blocker 숫자가 아니라 다음 실제 증거로 판정한다.

- v0.8.0 회귀별 테스트, exact-SHA full gate, 선택 배포, 관찰, tag/release.
- v0.9.0 다섯-profile qualification, static beta 제거, surface/service smoke, future
  adapter의 비활성 및 zero-public-read 증거, exact-SHA full gate,
  배포·관찰·tag/release.
- 각 명시 요구사항과 authoritative evidence를 일대일로 대조한 최종 감사에서 미완료,
  간접 증거 또는 검증 누락이 하나도 없음.
