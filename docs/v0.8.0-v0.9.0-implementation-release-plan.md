# Clearra v0.8.0 안정화 및 v0.9.0 PC4 구현·배포 계획

## 1. 문서 권위와 릴리스 순서

이 문서는 v0.8.0 안정화부터 v0.9.0 PC4 온라인 기능 배포까지의 활성 실행
계획이다. `docs/v0.8.0-remaining-work-plan.md`는 당시 구현 및 배포 증거를 설명하는
역사 문서로 보존한다. 과거 문서의 `blocker 0`, `source complete`, `ready` 판정은
현재 Go 판정이 아니다. 이후 수동 점검에서 발견된 준비 단계 정지, 해법 누락,
내부 `ctk1` 표현 노출, 구축 확률 옵션 미반영 등은 구현 단계에서 다시 열어
코드와 회귀 테스트로 닫는다.

공개 릴리스 기준선은 `v0.7.4`다. `v0.7.5`는 릴리스 태그가 아니며, 문서에서
언급되는 경우에도 과거 rollback source 또는 7개 상단 메뉴의 미출시 UI 참고안만
뜻한다. 배포 및 누적 변경 비교의 기준으로 사용하지 않는다.

릴리스는 반드시 다음 순서로 진행한다.

1. **v0.8.0**: v0.7.4 회귀 수정, 입출력 경계와 SRP 강화, GUI/CTK/watchdog,
   canonical gate 및 선택 배포 개선.
2. v0.8.0 배포, 20분 이상 관찰, 태그와 immutable release 확정.
3. **v0.9.0**: 기존 정적 PC4 베타를 제거하고 PC4 V\* Policy Advisor와 실험적
   Krylov survival을 추가.
4. v0.9.0 배포 뒤 호환 데이터 갱신은 v0.9.x, 안정화 이후 별도 계획으로 v1.0.0.

v0.8.0과 v0.9.0은 각각 독립된 exact-SHA Go gate를 갖는다. v0.8.0이 실제로
배포·관찰·확정되기 전에는 v0.9.0 production mutation을 하지 않는다.

## 2. v0.8.0 안정화

### 2.1 구현 단계 버그 탐색과 SRP

각 결함은 `surface input -> typed AppCommand -> use case/coordinator -> domain result
-> typed projection -> presenter` 경로를 따라 재현한다. 내부 bitfield, worker
메시지, cache key 또는 실행 ID를 사용자 결과로 직접 투영하지 않는다. 요청
수명주기는 `preparing -> running -> terminal`로 수렴하고 성공, 빈 결과, 취소,
실패, stale response를 서로 다른 상태로 유지한다.

다음 항목은 재현 테스트 없이 완료 처리하지 않는다.

- 전체 replay 및 일부 탐색이 준비 단계에서 끝나지 않는 문제.
- 성공한 해법이 presenter에서 사라지는 문제.
- 기존 GUI 필드 대신 해법 종류가 `ctk1` bitfield로 표시되는 문제. GUI는 항상
  기존 field/board/queue/hold/operation 표현을 우선한다.
- Build probability 옵션 변경이 request snapshot, worker input 및 cache identity에
  전달되지 않는 문제.
- 연속 실행·취소·다시 실행에서 이전 세대 결과가 새 요청을 덮는 문제.
- 빈 결과와 실패 결과가 같은 화면으로 나타나는 문제.

파서, 실행 coordinator, result projection, presenter, renderer, watchdog은 별도
소유자로 유지한다. 공통 계약 변경은 표면별 문자열 분기 대신 typed boundary에서
한 번 수행한다.

### 2.2 GUI, 결과 paging, CTK와 watchdog

- 기본 상단 메뉴는 PC, Setup, Build probability, Damage, Spin Finder, CTK,
  Player의 7개만 노출한다. 고급 route는 삭제하지 않되 기본 메뉴에서 숨긴다.
- 독립 Render 화면은 CTK에 합친다.
- GUI/명시적 CLI의 portfolio tie는 canonical candidate ID 오름차순으로 모든
  후보를 bounded paging한다. score, 최소 해법 수, 동일 확률 등 최종 선택 축의
  모든 tie에 같은 규칙을 적용한다.
- score tie에는 attack을 혼합하지 않는다. Discord는 가장 작은 양의 canonical
  candidate ID 하나로 고정한다.
- CTK와 Discord는 page당 500 ms, 같은 frame 수, 주석 위치와 줄바꿈을 사용한다.
- 빈 셀에는 낮은 불투명도의 grid를 유지하고, 같은 색이면서 같은 owner인 인접
  셀 사이의 내부선만 제거한다. field와 active operation은 동색이어도 경계를
  보존한다.
- `127.0.0.1:8790`과 개발 GUI `4194`를 1분마다 확인한다. 해당 port listener,
  watchdog 소유의 진행 중인 startup 또는 같은 명령의 기존 process가 하나라도 있으면
  활성 세션으로 간주해 재시작하지 않는다. 모두 없을 때만 단일 mutex와 Task Scheduler
  `IgnoreNew`로 중복 PID를 막고 `node.exe`/`ssh.exe`를 shell 중계 없이 숨김 창으로
  재실행한다. SSH 자체 keepalive와 연결 실패 종료를 사용한다.

### 2.3 v0.8.0 Go 조건

- 위 결함별 최소 reproducer와 회귀 테스트가 통과한다.
- 모든 실행 경로가 terminal 상태 또는 명시적 취소로 끝난다.
- Pages/Desktop/CLI/Discord가 같은 typed 결과와 CTK golden을 사용한다.
- v0.7.4 대비 의도하지 않은 기능 삭제가 없다.
- v0.8.0에는 새 PC4 온라인 기능이나 정적 베타 제거를 넣지 않는다.
- candidate SHA에서 canonical full gate를 정확히 한 번 수행해 통과한다.

## 3. 테스트와 배포 파이프라인

### 3.1 테스트 계층과 canonical gate

- 평상시에는 변경 영향에 해당하는 focused unit/contract/static/surface 테스트만
  실행한다.
- component acceptance는 실제로 바뀐 Pages, Desktop, CLI, Discord, Cloud
  component에만 수행한다.
- full ReleaseAcceptance는 frozen exact-main SHA의 배포 직전에 한 번만 실행한다.
- tag publication은 같은 run/attempt의 accepted artifact와 evidence를 검증해
  재사용하며 test/build를 반복하지 않는다.

기존 Foundation/Sanitizer/Rust/Pages의 의미상 stage 집합은 유지한다. 실제 GitHub
Actions timing을 evidence에 기록하고, stage 중앙값을 이용한 longest-processing-time
고정 shard map으로 tail을 줄인다. `NoProductDebt`, `AdversarialCorrectness`,
`DesktopHost`는 독립 leaf로 나누고, Rust/ProductE2E/Render는 sealed build artifact를
공유해 테스트나 컴파일을 중복하지 않는다. mutable target, port 또는 process-global
상태를 공유하는 테스트는 직렬 owner에 남긴다. fan-in은 닫힌 stage 목록, exact
SHA, artifact digest와 deferred evidence owner를 검증한다. 여섯 acceptance leaf의
cache는 모두 restore-only이며 job 종료 시 저장·압축하지 않는다. Windows product
build는 CLI를 restore-only reader, GUI를 유일한 writer로 둔다. 두 job 모두 lock
fingerprint와 exact source SHA를 포함한 key를 사용하고, 직전 exact-SHA cache와 기존
lock-only `product-v2` cache를 순서대로 복원할 수 있어야 한다. cache는 현재 source의
실제 build, artifact digest 또는 canonical evidence를 대체하지 않는다.

최초 shard 구조 변경에 한해 비권위 benchmark를 한 번 허용한다. warm/cold hosted
runner를 모두 기록하고, leaf가 중앙값의 약 125%를 지속적으로 넘지 않으며 최신
canonical baseline보다 wall time을 30% 이상 줄이는 것을 목표로 한다. 테스트 삭제,
skip 또는 중복 실행으로 성능 조건을 맞추지 않는다.

허용된 비권위 benchmark run `33551509127`은 13분 22초로 직전 25분 56초 기준보다
약 48% 짧았고 모든 job이 통과했다. 당시 Foundation은 9분 24초, Windows GUI는
12분 23초였으며 GUI의 11분 26초 build 중 Cargo release가 10분 41초를 차지했다.
이는 `product-v2` 첫 cache miss 뒤 약 523 MB cache를 저장한 cold run이었다. 따라서
Foundation을 위 세 leaf로 더 나눈 구조와 exact-SHA product cache의 최종 성능 판정은
새 frozen SHA의 단 한 번뿐인 canonical run에서 한다. warm run에서도 GUI가 계속
critical tail이면 sccache나 runner 등은 다음 버전의 별도 측정 과제로 넘기고,
v0.8.0에서 compiler profile이나 제품 feature를 바꾸지 않는다.

### 3.2 변경 영향과 선택 배포

workflow는 `pages`, `desktop_gui`, `cli`, `discord_gateway`, `heavy_cloud_runtime`,
`pc4_lookup_service`, `pc4_activation_manifest`, `release_infrastructure` 변경 벡터를
계산한다. 변경되지 않은 component는 마지막 accepted digest와 deployment receipt를
carry-forward한다. 공통 계약 또는 release infrastructure 변경은 보수적으로 모든
관련 component를 선택한다.

GUI-only, CLI-only, Discord-only, snapshot-only 수정은 관련 없는 build, full gate
또는 배포를 실행하지 않는다. 다만 v0.8.0의 누적 변경은 모든 기존 표면에 영향을
주므로 최초 v0.8.0 배포에서는 Pages, Desktop/CLI, Oracle/Cloud runtime 및 Discord를
모두 배포·관찰한다.

### 3.3 v0.8.0 배포 순서

1. focused/component 테스트와 CI 성능 자격을 통과한다.
2. clean candidate commit을 main에 fast-forward하고 exact SHA를 고정한다.
3. 비권위 benchmark의 자동 Discord run `33552779320`은 promotion 전에 취소되어
   production mutation은 없었지만 recovery debt가 남았다. trusted recovery workflow를
   `original_run_id=33552779320`, `original_run_attempt=1`, 새 exact main SHA로 한 번
   수동 dispatch하여 no-mutation 해소 증거를 먼저 봉인한다. 이 repair는 배포 권위나
   최종 Discord checkpoint가 아니다.
4. exact main SHA의 canonical full gate를 정확히 한 번 dispatch한다. 실패한 run의
   rerun은 권위로 쓰지 않고 새 candidate SHA에서 다시 시작한다.
5. canonical gate와 병렬로 v0.7.4 rollback snapshot을 한 번 bootstrap-capture한다.
   대상은 annotated `v0.7.4` tag가 가리키는 exact commit
   `0438d85f90b47c4ce89835f6a6d665a0415aa25a`, annotated tag object
   `a95973dbc1c3c1919478328d12e4d25ddaedea71`, published stable Release, 최신 성공
   active Pages deployment가 모두 같은 source임을 입증해야 한다. 세 원격 객체가
   함께 이동해도 승인하지 않도록 tag 이름뿐 아니라 commit과 tag object를 코드에
   고정한다. 현재 공개 `clearra-build-identity.json`이 404인 legacy 배포이므로,
   initial과 preartifact에서 공개 768-byte manifest 및 content-addressed JS/WASM의
   실제 byte count와 SHA-256을 읽고, Git snapshot 재빌드의 동일 세 payload와 직접
   대조한다. 이 public/rebuilt digest는 sealed capture report에 포함한다.

   v0.7.4 manifest의 `contract_version=1`과 원본 bytes는 절대 바꾸지 않는다. 현재
   v0.8 contract/supply identity를 주입해 과거 binary의 의미를 발명하지 않고,
   source/tag/tag-object, 원본 manifest·JS·WASM digest, reconstruction authority와
   capture run을 기록하는 별도 typed legacy rollback identity를 site root에 추가한다.
   package validator와 restore deployment readback은 이 legacy schema 및 실제 버전
   `0.7.4`만 허용한다. 버전은 snapshot에 존재하지 않는 최신 helper를 호출하지 않고
   authority-source의 동결 reader/상수로 판정한다. 일반 capture는 기존 current
   identity를 검증만 하며 보정하지 않는다. bootstrap job에는 Pages write/deploy
   권한을 주지 않고 API readback에 필요한 최소 `deployments: read`만 추가한다.
6. canonical accepted Pages artifact와 위 rollback capture authority로 Pages를 먼저
   forward 배포하고, 공개 identity가 exact accepted SHA와 일치하는지 확인한다.
7. 최종 Discord 배포는 canonical gate가 만든 자동 `workflow_run`만 사용한다. 수동
   `workflow_dispatch`는 최종 checkpoint가 될 수 없다. Pages authority가 준비된 뒤
   `discord-path-confirmation`을 승인해 Oracle Gateway/Cloud Run을 승격하고, 이어서
   `discord-global-command-sync`를 승인한다. 변경 영향 벡터가 제외한 component에는
   배포를 만들지 않고 이전 accepted receipt를 carry-forward한다.
8. 준비 정체, 해법 누락, renderer, Pages, Oracle/Cloud 및 Discord 네 표면을 20분
   이상 exact artifact hash와 deployment receipt에 묶어 관찰한다.
9. main과 accepted SHA가 그대로이고 자동 Discord checkpoint candidate가 봉인된
   경우에만 annotated `v0.8.0` tag를 만들며, tag workflow는 같은 accepted artifact를
   재사용해 immutable 3-asset GitHub Release와 publication evidence를 게시한다.

## 4. v0.9.0 PC4 제품 계약

### 4.1 제품 의미

`muse918/tetris-4lpc-mdp-vstar-policy`는 전체 해법 TB가 아니라 상태별 V\*와 하나의
policy action을 제공한다. 따라서 제품명은 **PC4 V\* Policy Advisor**이고,
`solution_family=false`, `solution_count=null`, `completeness_claim=none`을 항상
명시한다. Setup, Pattern, 모든 PC 해법 열거, exact pruning 또는 score/tie 권위로
사용하지 않는다.

upstream u16 policy action은 piece ID와 `graph.edges(field, piece)`의 edge index이며
rotation, x/y, kick 또는 input sequence가 아니다. GUI/CLI가 기존 placement 표현을
보여주기 전에 `PcPolicyPlacementMaterializer`가 선택 profile의 Clearra geometry를
열거해 source/target field와 일치하는 합법 placement를 재구성한다. 일치 항목이
없으면 `data_invalid`, 여러 항목이 같은 target occupancy로 접히면 canonical candidate
ID가 가장 작은 하나를 **Clearra 재구성 배치**로 표시한다. upstream이 구체 kick/input
sequence까지 선택했다고 주장하지 않는다.

`pc survival`은 `muse918/tetris-4lpc-survival-krylov`의 source policy 아래에서
N PC 동안 생존하는 확률을 계산하는 별도 실험 기능이다. 이는 최적 n-PC 성공
확률이 아니며 PC/Setup 후보 선택에 영향을 주지 않는다. 후속 정확 n-PC 확률은
`PcNextProbabilityProvider`라는 비활성 내부 포트만 예약하고 v0.9.0 공개 기능,
데이터 조회 및 registry capability에는 추가하지 않는다.

### 4.2 공개 명령과 표면

`pc policy`는 rule, field, hold/current/preview, bag remainder로 **현재 관측 상태의
upstream policy action 하나와 V\***를 반환한다. bag remainder는 다음 reveal의 가능한
집합이지 순서가 아니므로, 임의의 canonical reveal을 골라 현재 PC 끝까지 하나의
continuation인 것처럼 표시하지 않는다. 다음 piece가 공개되면 새 boundary로 다시
조회한다. 전체 continuation이 필요해지는 후속 버전에서는 reveal마다 갈라지는 bounded
decision-tree 계약을 별도 capability로 설계하며, provenance로 완전한 ordered hidden
reveal을 실제로 아는 입력만 단일 관측 경로로 연장할 수 있다.

`pc survival --pcs N`은 `N=1..100` 하나에 대해 `survival_through_n_pcs`와
`death_within_n_pcs`만 반환한다. N=1은 `dpi`, N>=2는 Krylov projection을 사용한다.
공개 Krylov state order가 layer-0 quotient 전용이므로 empty/reset field이면서
`placements_since_pc_boundary=0`인 boundary만 허용한다. 임의 중간 field나 phase에서
layer-0 row를 대신 사용하거나 확률을 보간하지 않는다.

- GUI는 기존 beta tablebase control의 위치를 유지하되 beta 문구를 모두 제거하고
  Policy Advisor 명시 opt-in으로 바꾼다. 현재 PC policy만 제공하고 survival은
  노출하거나 읽지 않는다. rule dropdown에는 `no-kick`을 추가한다.
- native CLI는 `pc policy`와 `pc survival`을 generic Web Product parser보다 먼저
  인식한다.
- Discord는 명시적인 policy/survival 경로와 필요한 modal을 제공한다. hit, miss,
  장애 모두에서 heavy PC/Setup Cloud Run을 자동 실행하지 않는다.
- 기존 정확 PC 탐색은 독립 제품으로 남는다. policy 실패 시 자동 fallback하지
  않고 사용자가 정상 PC 명령을 별도로 실행할 수 있게 안내한다.

### 4.3 canonical boundary와 bag

`BoundaryContextV1`은 schema ID, rule profile, canonical 10x4 field/u40, hold state,
active/current, ordered preview, non-empty unique `bag_remaining`,
`placements_since_pc_boundary` (`pc_phase`, 0..9), bag/source provenance, request
generation과 snapshot identity를 가진다. upstream `layer0..9`는 field 높이가 아니라
현재 PC cycle의 placement step이므로 이 값이 layer 선택의 필수 권위다.

- hold가 있으면 unordered `{hold,active}`와 정확히 5개의 ordered preview를 쓴다.
- empty hold이면 active를 포함한 queue 7개, 즉 첫 두 piece를 upstream unordered
  `{hold,current}`로 정규화하고 다음 5개를 ordered preview로 사용한다. upstream
  qstate와 exhaustive equivalence/KAT가 통과하기 전에는 활성화하지 않는다.
- survival preview는 명시 입력이며 생성하지 않는다. policy preview는 Player 또는
  generator provenance가 보존될 때만 생성할 수 있다.
- `bag_remaining`만으로 hidden reveal 순서를 만들지 않는다. policy 응답은 현재 action,
  V\*, snapshot provenance와 다음 조회에 필요한 공개 context를 반환하며, 새 reveal 뒤
  client가 boundary를 갱신해 재조회한다.
- Player history처럼 PC 직후부터의 placement 수를 증명하는 source에서는
  `placements_since_pc_boundary`를 자동 도출한다. 임의 GUI field, CLI 또는 Discord
  입력에서 유일하게 알 수 없으면 prompt/명시 옵션을 요구하고
  `needs_boundary_context`로 실패한다. field cell count나 높이로 추측하지 않는다.
- bag remainder는 provenance로 유일하게 추론되면 자동 입력한다. 그렇지 않으면
  GUI prompt, CLI TTY 또는 Discord modal로 남은 piece를 묻는다. raw bag round나
  qid는 묻지 않는다. noninteractive CLI는 `--bag-remaining`을 요구하며 추측하지
  않는다.

### 4.4 독립 타입과 SRP

Policy와 Survival은 기존 `pc.chance`, `PatternBitSet`, `CoverageRow`,
`PcResultProjection`, `AppTablebaseSession`을 재사용하지 않는다.

- Policy: `AppCommand::PcPolicy`, `QueryEnvelope::PcPolicyBoundary`,
  `ProductCapabilityContract::PcPolicy`, `PcPolicyLookupPort`,
  `pc-policy-advice.v1`.
- Survival: `AppCommand::PcSurvival`, `QueryEnvelope::PcSurvivalBoundary`,
  `ProductCapabilityContract::PcSurvival`, `PcSurvivalLookupPort`,
  `pc-survival-estimate.v1`.

boundary canonicalizer, manifest resolver, policy reader, survival reader, Krylov projector,
placement materializer, resumable lookup machine, request coordinator, presenter 및
telemetry는 별도 책임으로 둔다. v0.8 registry v1은 동결하고 v0.9 registry delta/v2를
추가한다.

기존 solver `AppContext::run`은 동기 경계이므로 그 안에서 browser Fetch나 native HTTP를
시작하지 않는다. advisor core는 `NeedRange { artifact, offset, length }`를 내고 host가
정확한 byte를 공급하면 다시 진행해 `NeedRange | Complete | Error`로 수렴하는 순수
resumable machine으로 만든다. Browser Worker, native CLI 및 전용 lookup service는 같은
machine을 각각의 비동기 Range adapter로 구동한다. `AppCommand::PcPolicy`와
`AppCommand::PcSurvival`은 typed request/result 계약을 소유하되 blocking network의
소유자가 되지 않는다.

공통 typed error는 `needs_boundary_context`, `invalid_preview_length`,
`invalid_bag_state`, `unsupported_horizon`, `unsupported_survival_boundary`, `state_not_in_model`,
`dataset_unavailable`, `rate_limited`, `snapshot_mismatch`, `data_invalid`다. machine JSON은
code와 구조화 필드만 포함하고 인간 설명은 presenter가 소유한다. NaN, Infinity,
범위 밖 확률은 clamp하지 않고 `data_invalid`로 실패한다.

## 5. PC4 데이터와 실행 토폴로지

### 5.1 Policy 자격 조건

v0.9.0은 muse918가 `srs-plus`, `srs`, `srs-x`, `jstris-180`, `no-kick` 다섯 프로필의
완전한 graph/policy/value/field-order 자산을 게시할 때까지 release-blocked다. 일부
프로필만 준비된 상태는 staging할 수 있지만 활성화하지 않는다. 각 profile manifest는
graph, offsets, hash index, policy, V\*, state order, rule/kick, hold/bag semantics를
하나의 generation으로 결합한다. graph만 바꾸거나 기존 policy를 다른 kick graph에서
재해석하지 않는다.

2026-09-02 조사 기준 공개 policy dataset은 약 778GB/46 files의 단일 flat
generation이고 다섯 profile identity나 profile manifest가 없다. `graph.bin`과 helper
index는 실제로 존재하지만 README와 파일 목록이 어긋나며 `FHIDIDX1`/`GOFFIDX1`의
공개 생성기·완전한 포맷 권위도 확인되지 않았다. 현재 generation을 임의로
`srs-plus`로 간주하거나 다른 네 profile에 재사용하지 않는다. promotion은 helper
header, count, 정렬, bounds와 graph/policy/value/order 결합을 독립 검증한 뒤에만
가능하다.

사용자 제공 `srs_plus_srs_x_kick_tables.json`은 호환성 fixture와 upstream 생성 요청
사양의 설계 증거로 사용하며 단독 제품 권위로 사용하지 않는다. Clearra 소유의
대체 policy dataset을 만들지 않는다.

dataset 표시는 MIT이지만 `graph.bin` 원천인 randomidiot13/hydra와 관련 생성 도구는
GPL 계열이다. 이는 법률 결론이 아니라 release provenance 확인점이다. dataset 허가가
배포되는 graph/helper index까지 포괄한다는 증거를 남기고, 포맷·알고리즘 사실을
독립 구현하며 GPL 구현 코드를 Clearra에 복사하지 않는다.

### 5.2 Krylov 자격 조건

현재 공개 데이터의 `pi_policy_v3`, `k=14`, layer-0 quotient 817,740 states를 명시적
실험 공급자로 사용한다. 이 공급자는 empty/reset field 및 PC phase 0에서만 정의되고
중간 placement의 policy layer와 혼용하지 않는다. activation manifest는 `SURVKRY1`, state count, little-endian
f64, vector-major basis, ragged Hessenberg, `stored_basis_vectors=15`,
`queried_basis_vectors=14`를 검증한다. 현재 basis와 row order가 결합돼 있으므로
v0.9.0에서 추가 quotient 축소를 적용하지 않는다.

이 snapshot은 최종 policy가 아닌 `pi_policy_v3` 기반이고 per-state certified error
bound가 없다. N=1 `dpi`는 직접 hazard, N=2..100은 근사 projection으로 표시하며
`exact probability`, 최종 policy 기반 또는 임의 사용자 분포 결과라고 주장하지
않는다. stationary-start geometric 값과 사용자 boundary 결과도 혼합하지 않는다.

상태 축소 연구는 후속 과제로 둔다. Clearra 공개 의미에만 동등한 경우 별도 파생
cache를 검토하고, 모든 해법에 보편적으로 동등하며 유의한 축소가 가능한 경우에는
upstream graph/policy 재생성을 요청한다. 둘 다 아니면 quotient 계획을 취소하고
Markov 직접 계산을 검토하며, 불가능하면 기존 Krylov 상태를 유지한다.

### 5.3 snapshot 수명주기

HF SHA256 또는 commit을 제품 소스 상수로 고정하지 않는다. moving `main`은 discovery
전용이다. promotion workflow가 immutable revision, file OID/size/digest/schema/profile을
동적으로 검증해 서명된 activation manifest를 만든다. 요청은 시작 시 하나의
manifest와 snapshot을 pin하며 cache key에 generation, revision, schema, profile,
state를 포함한다. rollback은 이전 manifest로 전환한다.

Policy는 다섯 profile의 atomic generation만 활성화한다. source policy, schema,
rule/kick 또는 공개 의미가 바뀌면 자동 활성화하지 않는다.

### 5.4 실행 위치

- Pages GUI: browser Worker/WASM shared reader가 immutable HF Range를 직접 읽고 현재
  policy만 표시한다. 실제 Pages 환경에서 CORS/Range가 실패하면 v0.9.0을 차단하고
  승인 없이 Cloud fallback으로 바꾸지 않는다.
- CLI: shared native Rust reader가 immutable HF Range를 직접 읽는다.
- Discord: Oracle Gateway가 service-authenticated 전용 lightweight PC4 lookup Cloud
  Run을 호출한다. 공개 anonymous endpoint는 두지 않는다.
- dedicated service의 cache/derived layout은 폐기 가능한 최적화일 뿐 데이터 권위가
  아니며 모든 응답은 원본 HF snapshot provenance를 포함한다.
- 기존 8-vCPU heavy runtime은 일반 PC/Setup 검색만 소유한다.

policy 한 건은 전체 해법 O(1) 조회가 아니다. field-hash index, graph offset/record,
layer field block, quotient-chain ID, policy/value를 검증하는 bounded
`O(log fields + log blocks + log chains)` random access다. page cache는 round trip을
줄일 뿐 의미 권위가 아니다. Range adapter는 immutable revision URL, HTTP 206,
정확한 `Content-Range`/전체 크기, redirect 대상, short read와 non-zero Range의 200
full-body 거부, generation/revision/schema/profile/path/page cache key, bounded LRU 및
in-flight coalescing을 fail-closed로 소유한다. 전용 service는 arbitrary URL/Range
proxy가 될 수 없고 activation manifest allowlist 밖 byte를 읽지 않는다.

miss, offline, 429, timeout, truncated range, snapshot mismatch는 typed error로 끝난다.
CLI는 별도 명시 옵션 없이 offline exact search를 자동 실행하지 않는다.

### 5.5 기존 정적 베타 제거

다섯 policy profile이 qualification을 통과한 v0.9 migration에서만
`pc4-compact-exact-v12.bin`, web worker/static asset, Rust loader/runtime, CLI embed,
WASM/Discord packaging과 관련 impact mapping을 함께 제거한다. 기존 `--tablebase`는
의미가 다른 policy로 alias하지 않고 typed migration error와 `pc policy` 안내를
반환한다. 정적 beta와 온라인 policy를 두 개의 runtime 권위로 함께 활성화하지
않는다.

## 6. v0.9.0 검증과 배포

필수 검증은 다섯 profile manifest의 닫힌 집합, graph/policy/value/order 상호 결합,
u16 policy decode, profile별 합법 placement, upstream known-state KAT, layer 0..9 및
2LPC/4LPC terminal 전이, empty-hold qstate equivalence, PC phase와 bag prompt/inference,
unordered bag에서 임의 단일 continuation을 만들지 않는 계약과 reveal 뒤 재조회,
graph edge에서 Clearra placement로의 profile별 합법 materialization,
Krylov parser와 upstream 수치 KAT, layer-0/phase-0 경계 강제, 중간 field 거부, N=1/2/100,
invalid-float fail-closed, 정확한 206/`Content-Range`, 200/short-read/429/timeout 거부,
Range/cache/revision pin, 실제 Pages CORS, CLI direct-HF,
Oracle-to-Cloud auth와 anonymous rejection, heavy-job 비호출, static beta 부재를
포함한다. 배포 compliance evidence에는 graph/helper index의 dataset 허가 범위와
독립 구현 provenance도 포함한다.

배포 순서는 다음과 같다.

1. v080 전용 release helper를 version-neutral v2로 일반화하되 legacy v080 evidence와
   rollback reader는 유지한다.
2. 새 typed contract, shared reader, 표면 adapter와 dedicated lookup service를 구현한다.
3. 다섯 profile과 Krylov snapshot을 inert staging하고 qualification/KAT를 통과한다.
4. 정적 beta를 제거하고 dual authority가 없음을 확인한다.
5. exact v0.9.0 SHA에 canonical full gate를 실행한다.
6. Pages, CLI/Desktop, lookup Cloud Run, Oracle/Discord catalog를 선택 배포한다.
7. profile별 hit/miss, Range bytes, latency, cache, rate limit, invalid data와 Krylov 분포를
   canary 및 20분 이상 관찰한다.
8. rollback manifest를 실제로 검증한 뒤 `v0.9.0` tag와 immutable release를 게시한다.

다섯 profile 중 하나라도 없거나 provenance가 불완전하면 v0.9.0을 배포하지 않는다.

## 7. v0.9.x와 완료 판정

새로운 다섯-profile policy generation은 코드 변경이 없어도 항상 full gate를
실행한다. 특히 `no-kick`을 포함한 전체 generation이 완료된 경우 예외를 두지 않는다.
schema, reader, graph 의미, boundary, algorithm, source policy 또는 결과 계약 변경도
full gate 대상이다. `pi_policy_v3`에서 다른 policy로 바뀌는 survival 갱신도 같다.

fast patch는 이미 qualification된 동일 schema·동일 의미 generation의 재게시,
패키징 정정 또는 동등성이 증명된 snapshot 교체만 허용한다. 엄격한 diff allowlist,
data KAT, 관련 provider/client smoke, signed manifest와 이전 full-gate authority를
요구하고, 벗어나면 자동으로 full gate로 승격한다. application version과 dataset
generation은 별도 필드로 표시하며 unchanged binary는 accepted digest를 재사용한다.

새 비공개 값이 필요하면 source나 로그에 기록하지 않고 GitHub protected environment에
정확한 secret 이름과 소비 component를 먼저 정의한 뒤 값만 사용자에게 요청한다.
OIDC/WIF를 우선하며 GUI/CLI에 HF token을 내장하지 않는다.

완료는 계획 문구나 blocker 숫자가 아니라 다음 실제 증거로 판정한다.

- v0.8.0 회귀별 테스트, exact-SHA full gate, 선택 배포, 관찰, tag/release.
- v0.9.0 다섯-profile qualification, Krylov KAT, static beta 제거, surface/service smoke,
  exact-SHA full gate, 배포·관찰·tag/release.
- 각 명시 요구사항과 authoritative evidence를 일대일로 대조한 최종 감사에서 미완료,
  간접 증거 또는 검증 누락이 하나도 없음.
